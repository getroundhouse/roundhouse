# Driving the Claude CLI

How the worker runs the `claude` CLI, and how the CLI behaves.

The worker drives the CLI directly from Rust, without an SDK sidecar. It runs the user's installed `claude`, so there's nothing to redistribute, and it picks up their login and settings. The price is that a CLI upgrade can break the adapter, which the captured fixtures and contract tests are there to catch.

**Why.** The Agent SDK spawns this same CLI and talks to it over the same stdio protocol, as its flag list and `sdk.d.ts` show (read from `@anthropic-ai/claude-agent-sdk` 0.3.319, which isn't vendored here). Prompts, streaming, approvals, interrupts and resuming all work directly, with no JavaScript runtime to ship. Other features, such as `rewind_files` and hook callbacks, are control messages on the same stream, as `set_model` and `set_permission_mode` are. The SDK's in-process MCP tools have no direct equivalent, and nothing needs them.

**The main risk.** The control protocol is described by the SDK's types rather than the CLI's documentation. `crates/agents/tests/claude/contract.rs` checks the adapter against captured real output, and rerunning `tools/smoke/capture_claude_fixture.py` after a CLI upgrade shows what changed.

All of the following was observed on CLI 2.1.319 with Haiku, except where a row says otherwise:

| Behavior | What happens | What it means here |
|---|---|---|
| Launch | `-p --input-format stream-json --output-format stream-json --verbose --include-partial-messages --permission-prompt-tool stdio`, with one JSON message per line each way | The adapter's base flags |
| Conversation IDs | `--session-id <uuid>` sets the ID and `--resume <uuid>` keeps it. The context carried over | The hub's session ID doubles as the agent's |
| Wrong launch flag | `--session-id` on an existing ID exits with `is already in use`. `--resume` on a missing one exits with `No conversation found` | The adapter retries once with the other flag, and warns if the conversation was lost |
| Permission mode | With no flag, the user's settings decide: `bypassPermissions` on this Mac, so nothing asked for approval until `--permission-mode manual` was passed, which `init` reports as `default` | The mode shown to the user has to come from `init`, not from what was requested |
| Approvals | `control_request` with `can_use_tool`, answered by `control_response`. `allow` needs `updatedInput`, and `deny` takes a `message` the agent sees | Approvals are events in the log, and any client can answer |
| Interrupt | A `control_request` with `interrupt` ends the turn with `terminal_reason: aborted_tools`, and stops a running tool. The process stays up and takes the next prompt | Cancelling doesn't lose the warm process |
| Interrupt during an approval | The CLI sends `control_cancel_request` | Recorded as a cancelled approval |
| Changing the model or mode live | `control_request` with `set_model` or `set_permission_mode`. The CLI answers each with a `control_response`: in under 0.3 s before the first turn, and in under 5 s in the middle of one, which is as closely as that was timed. A bad value gets `subtype: error` and a reason | The hub saves a change only once a running agent has agreed, so what's shown is never ahead of what's true |
| Reporting the mode | `system/status` with `permissionMode` arrives in order for every change, including ones the CLI makes itself. `set_permission_mode` also takes `manual`, and reports it as `default` | `--permission-mode` lists `manual` and not `default`, so the adapter reports `manual`, the name a launch accepts |
| Full access | Switching a running agent to `bypassPermissions` stopped it asking, and switching back made it ask again. Without `--allow-dangerously-skip-permissions` the CLI refuses the switch and says why, so the adapter always passes it. It makes the mode available without turning it on. How that flag behaves under a managed policy that disables this mode wasn't tried | Full access can be chosen mid-session |
| Plan mode | The CLI writes the plan to `~/.claude/plans/` without asking, which is outside the worktree, then asks through `can_use_tool` for `ExitPlanMode` with `plan` and `planFilePath`. The input isn't streamed. Allowing it leaves plan mode, back to the mode before, including full access. Denying it ended the turn, and no change of mode was reported | The plan gets its own card, and the mode picker follows the CLI's report |
| Plan mode's model | With Haiku chosen, messages in plan mode came from Sonnet, while `init` still said Haiku. It went back to Haiku after the plan was approved. Seen in the fixture captures | A plan can cost more than the picker suggests. Whether this happens with other models wasn't tried |
| Questions | `AskUserQuestion` arrives as `can_use_tool` in every mode, full access included. Allowing it with `answers` in `updatedInput`, keyed by the question's text, delivers them. Allowing it without tells the agent "The user did not answer the questions" | A plain Allow button would silently throw the question away, so questions get their own card |
| Prompt sent mid-turn | The CLI reads it at once and takes it at its next request to the model: after a running tool finishes, along with any others sent meanwhile, and the turn ends with one `result`. Sent while the agent writes its last reply, it isn't folded in. That turn ends, and the prompt starts the next straight away, with a new `init` and no `session_state_changed` between | Counting `result` events can't give session status, and a prompt that starts a turn of its own has to say the agent is running again |
| Prompt lifecycle | A prompt sent with a `uuid` gets `command_lifecycle` lines naming it in `command_uuid`, with or without `--replay-user-messages`: `queued` when it's read, `started` when it's taken into the conversation, and `completed` or `cancelled` when that turn ends. Without a `uuid` there are none. Any string is taken as one. The CLI's own description of the line, in its binary, adds `discarded` and `refused` as ends, marks the line internal, and says a wrapper should count a prompt the process exits without ending as discarded. Its `init` lists `msg_lifecycle_v1` in `capabilities`, from a fixed list | The adapter sends a `uuid` with each prompt, records `started` as the prompt taken, and drops any it hadn't taken when the process exits. Nothing else says whether the agent has a prompt, so a CLI without these lines would leave every prompt waiting, and the queue too |
| The end of a turn | `session_state_changed` with `idle` comes just after the `result`, so a prompt sent the moment a turn ends is recorded before the `idle` of the turn before it. Seen through the hub, with a queued prompt | An `idle` with one of the agent's prompts still untaken is from before that prompt, so it doesn't make the session idle or let the queue go on |
| Interrupt with prompts waiting | With `cancel_queued`, a prompt that hadn't `started` gets `cancelled` before the turn's `result`, and the prompts it had taken get `cancelled` after. Without it, the waiting prompts ran next as one turn, joined into one message | A prompt cancelled before it started was never read, so the log says it was dropped |
| Status | `CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1` adds `session_state_changed` with `running`, `requires_action` and `idle`. The variable appears in the SDK's code but not its types | The adapter sets it. `result` still ends a turn if the variable stops working |
| Background tasks | `system/background_tasks_changed` lists every task the agent is running in the background, such as a command or a subagent, each time that changes. A turn can end with tasks listed. When one finishes, the CLI sends `task_notification` and the shorter list, then starts a turn by itself, which begins with `init` and no prompt or new state event. An interrupt while idle leaves them running | A session whose turn ends with tasks listed is `background`, which counts as at work, so an update waits on it. The composer still sends, since stopping a turn wouldn't reach them. `init` counts as running, since it's the only sign of a turn the CLI starts by itself |
| Stdin closed mid-turn | It finishes the whole turn, then exits 0. A 20 s tool took 19 s more | Closing stdin doesn't stop an agent quickly. It does mean an orphan eventually exits |
| SIGTERM | It stops its running tool and exits with 143 in about 0.5 s. Tools run in their own process groups. It stops background tasks too, sending `task_notification` with `status: stopped` for each, then a list without them, before it exits. That's the same whoever sent the signal | `stop` uses SIGTERM, and signalling the group wouldn't reach tools. The adapter says which tasks left the list stopped rather than finished, so an agent stopped with work in the background shows as interrupted, not done |
| Thinking | Blocks are empty without `--thinking-display summarized` | The adapter passes it |
| Files in a prompt | A `user` message's content can hold `image` blocks with base64 data, `document` blocks with a base64 PDF, and text blocks, and the agent read all three in one prompt. A message of only an image block worked too | Every file is in the worktree first, and comes before what was typed in an `attachment` tag with its name and full path. An image also goes in as an image block, just before its tag, and a text file up to 32 KB goes inside its tag, unless it holds the closing tag itself. Anything else is only the tag, for the agent to open. A prompt with files can have no text. How reliably the agent opens a file it's only given the path of hasn't been tried |
| A big image | A 14.5 MB, 2200×2200 PNG, well over the API's 5 MB, worked, and the CLI's own conversation file held it as a 466 KB JPEG, so the CLI shrinks an image itself before sending it | A prompt's images go to the CLI as they were attached, up to 32 MB between them, and any past that only by path. A PDF also goes only by its path, though the API takes one in a prompt: the API limits a PDF's pages, nothing here can count them, and what a conversation does after the API refuses a file in it wasn't tried |
| Order of a block | Deltas, then the finished `assistant` event, then `content_block_stop`, with one `assistant` event per block | The streaming tail depends on this, and so does the adapter, which takes a finished block's place in its message from the deltas before it. A contract test replays it |
| What a tool did | A `user` line with a tool's result also carries `tool_use_result`, the tool's own record of what it did. An edit's has `structuredPatch`: hunks with `oldStart`, `newStart` and `lines` marked ` `, `-` or `+`, numbered as in the file, sometimes with a `\ No newline at end of file` line. A write's has the same, and `type`, which is `create` for a new file and `update` for one it replaced, and a new file's patch is empty. A command's has `stdout`, `stderr` and `interrupted`, and no exit code: the result's text starts with `Exit code N` when it isn't 0. The edit's patch was read from a session's own log, and the write's is in the fixture | The adapter carries an edit's or a write's change on its result, so the transcript shows it with the file's line numbers. A command's exit code is read from the text |
| Subagents | An `Agent` call, which the CLI's tool list calls `Task`, starts one. In all 4 calls in the hub's own logs, on 2.1.319, it ran in the background whether or not `run_in_background` was set, so the result came back at once, saying "Async agent launched successfully", and its `tool_use_result` had `isAsync`. The subagent's `assistant` and `user` lines then carried `parent_tool_use_id` set to the call. They came for hundreds of events, mixed with the agent's own and with other subagents' when several ran at once, and its last text was its report. Progress came as `system` lines: `task_started`, which holds the prompt, `task_progress` and `task_notification`. One run in the foreground, seen in a Claude Code transcript rather than a stream, came back with the report in the result, wrapped in a note from the harness | The transcript draws a subagent's lines under its call, each in a row of its own, moved to follow the call. The report is the subagent's last text, and the result is shown only when none came |
| Tools on offer | 2.1.319's `init` listed `Task`, `Bash`, `Read`, `Write`, `Edit`, `WebFetch`, `WebSearch` and others, but no `Grep`, `Glob` or `TodoWrite`. None of the three appeared in this Mac's last 400 Claude Code transcripts either | The transcript draws `Grep` and `Glob` for a CLI that still has them, and nothing for a plan |
| Web | `WebFetch` takes `url` and `prompt`, and answers with what a model made of the page. A refusal, such as a 403, is the result's text. `WebSearch` takes `query`, and answers with a first line saying what it searched for, a `Links:` line of JSON with `title` and `url`, what a model made of them, and a closing `REMINDER:` to cite them. Read from Claude Code transcripts on 2.1.296 to 2.1.301 | The transcript reads the links from the `Links:` line, and leaves out the reminder, which is addressed to the agent |
| Other control requests | The CLI can also send `hook_callback`, `mcp_message`, `elicitation` and `request_user_dialog`, according to the SDK's types | The adapter answers these with an error so a session can't hang. None were seen in these runs |
| Environment | A parent Claude session's variables, such as `CLAUDECODE` and `CLAUDE_CODE_SESSION_ID`, are inherited by anything it starts | The adapter removes those by name, and passes login settings such as `ANTHROPIC_API_KEY` through |
| Model aliases | With Opus, on the owner's account: `--model opus` and no `--model` both report `claude-opus-5-5` in `init`, and a `contextWindow` of 1,000,000 in the result's `modelUsage`. The CLI also has `opus[1m]` aliases, and a message saying 1M "is not available for your account" | The picker's aliases give 1M context on an account that has it, with no `[1m]` needed. Another account may get a smaller window |
| A one-off call | `-p --model haiku --output-format json --tools "" --strict-mcp-config --setting-sources user --settings '{"disableAllHooks":true}' --no-session-persistence --disable-slash-commands --system-prompt <text>`, with the prompt on stdin, prints one JSON object with `type: result`, `subtype`, `is_error` and the answer in `result`. Run from an empty directory, a title took 1.1 s and $0.0002, with about 750 input tokens, and wrote nothing there. Hooks given in settings ran without `disableAllHooks`, and none ran with it. Logged out, it exits 1 with nothing on stderr, and says `Not logged in` in `result`, with `is_error` true and the subtype `success`. `--bare` would also skip hooks, but it reads only `ANTHROPIC_API_KEY`, not the login | How titles are generated, in `agents::claude::title_for`. The empty directory keeps a project's `CLAUDE.md` out of the call, and the user's hooks, which are for their own sessions, don't run. A failure's reason comes from `result` |
| Resources | An idle `claude` process used about 305 MB, against 11 MB for the hub and 8 MB for a worker (debug builds) | An idle agent costs far more memory than the hub and worker together |
