# Terms

What this project's words mean. Code, docs and the interface use each word only in the sense given here. A new term, or a new sense of one, goes here in the change that introduces it.

Start with "Easily confused" and "Ending things", which cover the words most likely to go wrong.

## Parts

| Term | Meaning | In code |
|---|---|---|
| Roundhouse | This product: the desktop app, the CLI, and the hubs and workers behind them. Capitalized as a name, and lowercase for a binary, but for the hub's copy of the daemon, `Roundhouse Hub` | `roundhouse`, `roundhoused`, `roundhouse-desktop` |
| Hub | The server that clients connect to. It owns workspaces, sessions and their logs, and leaves the work itself to workers | `hub` |
| Worker | The process that does a workspace's work: its agents, git and scripts. It reports to its hub. There's one per workspace | `worker` |
| Provider | A kind of place a hub can run workers, such as this machine, an Incus instance or a cloud sandbox. The local provider runs workers on this machine, and it isn't special | `Provider`, `LocalProvider` |
| Instance | Where a provider runs one workspace's worker | `instance_id` |
| State directory | Where a worker keeps its own files, outside the worktree: its lock and its record, its socket when it listens on one, the record of each agent, setup script and one-off call it runs, the setup log, and each run's files. Its provider names it. A local instance is a directory, and is its worker's state directory | `--state-dir`, `worker::Config.state_dir` |
| Provider adapter | The program that makes and ends a provider's instances. The hub runs it and talks to it over the provider protocol, and the local provider's is the daemon's `provider local`. Not built | `Provider` |
| Client | A program that talks to a hub, such as the desktop app or the CLI. Clients only talk to hubs | `client-core` |
| Agent | The coding agent a worker runs as a child process: the Claude, Codex or Antigravity CLI | `AgentKind`, `AgentProcess` |
| Subagent | An agent that the agent starts inside its own process to do part of the work, such as a search, with a tool call. It isn't one the worker runs, and its lines name it by the ID its agent gives it, which the hub records with each event, apart from the call that started it. The agent says when one starts, with what it was asked, how many tokens its conversation holds as it works, and when it ends, with its report, and the hub keeps a record of each. The transcript draws them in that call | `SubagentId`, `parent_tool_use_id`, `SessionEvent::subagent`, `SubagentStarted`, `SubagentContext`, `SubagentEnded`, `Subagent`, `Subagent::lately`, `CallKind::Subagent`, `calls::Recorded::hands_off`, `client_core::calls::agent` |
| Advisor | A stronger model the agent can ask for advice, which reads the whole conversation. The API runs it rather than the agent, so it's a tool call whose result comes in the agent's own messages, and the advice can come encrypted, for the model alone. A call the agent went on without, which it's been seen to do when it called one of its own tools first in the same message, is recorded as dropped | `CallKind::Advisor`, `ToolCall::Advisor`, `agents::claude::normalize::advisor`, `ContentBlock::ToolResult.encrypted`, `CallOutput::Encrypted`, `EventBody::ToolCallDropped` |
| Adapter | The code that runs one kind of agent and turns its output into events | `agents::claude` |
| Capability | Something an agent does, for the person or for Roundhouse, whose behavior is specified once for every agent, such as taking a prompt mid-turn. The set is the experience Roundhouse decides is best, which each adapter fits its agent to, not what agents share. Adapters implement the capabilities they claim; the areas still absent are marked *Not built* in [the architecture](architecture.md) | `capability::Capability` |
| Claim | A run's saying, through its adapter, that it delivers a capability, with what the hub or a client needs to know of it, such as whether a rewind puts files back. A run says its claims once, as it launches, and the hub records them and holds it to them while it runs, refusing a control they don't allow. A claim can need another, as a fork needs resuming, and a launch whose run claims one without what it needs is refused. A run of a worker of protocol 3 says them as it initializes, and a Claude run of a build from before claims says none, so it's sent the requests that came before controls | `Capabilities`, `Claims`, `Capabilities::unmet_needs` |
| Contract | What a capability promises once it's claimed, whatever the agent does underneath, which its variant's doc says | None |
| Law | A contract a session's log can be checked against by itself, such as a prompt being settled once | `capability::laws::Law` |
| Agent's description | What a kind of agent is called and offers, as its adapter describes it: what the interface calls it, the models, efforts and approval modes a chat can be given, what a chat runs with until another is chosen, what it does that not every agent does, such as compacting when asked, and what login a hub can hold for it: the command that makes its token, and how long one lasts | `AgentDescription`, `ModelChoice`, `AgentFeature`, `LoginDescription`, `agents::descriptions`, `ClientRequest::AgentList`, `client_core::Agents`, `Snapshot::agents`, `roundhouse agents` |
| Conformance | Whether a version of an agent's CLI does what Roundhouse needs of it, as scenarios played through its adapter check | `agents::conformance` |
| Scenario | Steps a driver takes with an agent, and checks of what its adapter made of them, in Roundhouse's terms, the same whatever it's played against. Each agent's binding gives it a script for the scripted model | `conformance::scenario::Scenario`, `conformance::scenarios` |
| Trial | One playing of a scenario, against the scripted model or the real one, or replayed from a capture. It can span several runs | `conformance::trial::Trial`, `Played`, `Report` |
| Driver | What plays a scenario's steps through `AgentProcess`, as the worker does, and keeps what the adapter said | `conformance::driver::Driver`, `Launcher` |
| Scripted model | A stand-in for the model's API on this machine, whose every reply a scenario's script makes. The real model is the real API, which costs money | `claude::conformance::messages::ScriptedModel`, `Script`, `Against` |
| Capture | What crossed a real agent CLI's stdio, kept as lines, such as what `tools/smoke/capture_claude_fixture.py` captures. A trial's capture is what its adapter did with the CLI, in order: each launch, with its arguments, each line it wrote and read, and each exit, and where a step saw what only the CLI's world shows. One kept for tests is a fixture, such as a scripted trial's | `conformance::capture::Entry`, `Tap`, `tools/smoke/capture_claude_fixture.py` |
| Replay | A trial that plays a scenario again through the adapter from a capture, with a stand-in for the CLI that writes what the CLI wrote, and fails where the adapter writes otherwise | `claude::conformance::replay`, `conformance::stand_in` |

## Work

| Term | Meaning | In code |
|---|---|---|
| Repository | A git repository added to a hub, whose record says where it is: its checkout on the hub's machine, its address, or both | `Repo`, `RepoOrigin` |
| Address, of a repository | Where a repository lives, as git names a remote's URL, such as `https://github.com/ada/roundhouse.git`, which a worker with no checkout of its own clones and fetches from. A checkout's is its `origin`'s, which a worker on the hub's machine reads, with whether a push from the checkout goes through the git credential workers are given, as only one to `https://github.com/` does, or round it. It never holds a credential | `RepoUrl`, `RepoOrigin::url`, `ReadRepoUrl`, `PushRoute`, the `repos` table's `push_around` |
| Project | What the interface calls a repository added to a hub: the entry that holds a codebase's workspaces and settings, with one git repository behind it, added by that repository's checkout on the hub's machine | `Repo` |
| Workspace | The unit of delegation: a name, a branch and a worktree in one repository, with its sessions and diff comments | `Workspace` |
| Worktree | A workspace's git worktree, the files on disk | `Workspace.path` |
| Repository source | What a worker is told to make a workspace's worktrees from: a checkout of the repository on its machine, or the repository's address, which it clones | `RepoSource` |
| Repository's clone | A worker's own copy of a repository it's told of by its address, which it makes the repository's worktrees from, as from a checkout. There's one for each address on a machine, in the clones directory the worker's provider names, which every worker the provider runs there shares. A worker makes it the first time a workspace needs it, and fetches it from then on. It's never the hub's. The local provider's clones directory is `clones/` in the hub's data directory | `RepoSource::Clone`, `worker::git::Clones`, `--clones-dir`, `worker::Config.clones_dir`, `Paths::clones_dir` |
| Child worktree | Another worktree of a workspace's repository, made for its work, in `.children/` beside the workspaces. The interface says "other worktree". Not built | `ChildWorktree`, `CreateWorktree`, `AddChildWorktree` |
| Title | What a workspace or a chat is called on screen. It's generated from the first prompt, generated again from every prompt when someone asks, or typed by hand, and one typed by hand is replaced only by one someone asks for | `Workspace.title`, `Session.title`, `TitleSource` |
| Base ref | What a workspace's branch was created from. Diffs are taken against it | `base_ref` |
| Branches | What a worktree's git says of its branches, as its worker last read them: which is checked out, and each branch the worktree has had checked out, with its newest commit and where it's pushed. A workspace's name is only the folder its branches go in | `Workspace.branches`, `Branches`, `Branches.had`, `WorkerRequest::WatchBranches`, `ChildWorktree.branches`, `WatchChildBranches`, `WorkerFrame::ChildBranches` |
| A branch's pull request, linked | The pull request that's a branch's: one the branch has been at a commit of, which the worker then links the branch to, as a setting of the branch in git's config, so it stays the branch's as it moves on. Not any pull request from a branch of the same name, which `gh` finds by the name | `pull_request::link`, `link::linked`, `link::has_been_at` |
| Base image | A VM that a repository's own script has set up, with its tools installed and its caches warm. A remote workspace's VM is made as a copy of its repository's newest one. Not built | None |
| Session | One conversation with one agent, with its log. A workspace can have several | `Session` |
| Terminal | A shell a workspace's worker runs in the worktree, which every client can attach to and type into. The worker keeps what it shows, and a client that attaches gets that as a screen, then what its program writes. The hub keeps its record while its shell runs. Not a session, which is a chat's. Not built in the app | `Terminal`, `TerminalId`, `TerminalUpdate`, `TerminalScreen`, `terminal_state::Mirror`, `WorkerFrame::Terminal`, `HubFrame::Terminal` |
| Run | One launch of an agent. A session can have many, because an agent can exit and be started again. Its ID never repeats, even across hub restarts | `RunId`, `AgentSpec.run` |
| Turn | From a prompt until the agent finishes responding. A run can have many. A prompt sent mid-turn folds into the running one if the agent has more to do, and otherwise starts the next. The agent starts one by itself whenever one of its background tasks finishes, to take in how it ended | `TurnEnded`, `Session.turn_started_at_ms`, `SessionStatus::in_turn`, `SessionStatus::between_turns` |
| Own turn | A turn the agent starts by itself, with no prompt, such as to take in how its background tasks ended. The agent's adapter records why as the turn starts, when it can tell then, naming each task, and the hub adds what it keeps of each wait among them | `EventBody::OwnTurn`, `capability::turns::OwnTurn`, `EndedTask`, `EndedWait` |
| Background task | Work an agent started that carries on after its turn ends: a command, a subagent, a monitor, or a wait on pull requests, which the hub keeps. Until it finishes, and the agent has picked up again after the last of them, the session is active, so an update leaves it running on the version it started with and closing asks, and only a subagent counts as the agent itself working | `AgentTasks`, `AgentTask`, `TaskKind`, `SessionStatus::Background`, `CallOutput::Backgrounded` |
| Monitor | A background task that watches for something, such as a check failing, and wakes the agent each time it happens. It does nothing meanwhile, and may never end | `TaskKind::Monitor` |
| Task group | The background tasks of one kind: subagents, commands or monitors. With more tasks than have a line each at the chat's end, a group with several has one line, which opens to theirs | `TaskGroup`, `TaskLine`, `transcript::task_lines` |
| Reply | What the agent said in a turn, as of the event that ended it, and how that turn ended. A turn the agent was cut off from isn't one | `Session.reply_seq`, `Session::has_reply`, `Session.reply_outcome` |
| Failed request | One of the agent's requests to its model that failed, as on a usage limit, which its CLI says in a message of its own in the model's place, and the chat shows as a red card. A turn mostly ends on one, and a subagent's leaves the agent going. The hub says when one of the agent's own repeats the one before, with nothing between them but a subagent's events and what the agent did by itself that came to nothing else, and the chat shows those in a row as one card, the newest's, with a line for what started each try | `EventBody::RequestFailed`, `RequestFailure`, `FailureKind`, `TurnEnded.request_failed`, `Again`, and in the transcript `Failures`, `Tries`, `Try` and `Started` |
| Stopped short | What a chat is when its agent went away mid-turn, or its newest turn failed, until a turn starts again. Its mark's turntable is red, it notifies, it holds its queue, and it needs the person | `Session::stopped_short`, `Session::turn_failed`, `Signal::Failed` |
| Prompt | What a person sends to an agent: what it says, and the files it carries, which pass from the client's bytes to the IDs it added them under, to the hub's record of each, to where the worker put each in the worktree. It's real once it's recorded, and until then a client shows it as pending, held as a queued prompt is, under the ID it'll be recorded under | `protocol::prompt::Prompt`, `UserPrompt`, `client_core::Written`, `SessionLog::pending` |
| Attachment | A file a prompt carries, of any kind, or an image a tool sent the agent, such as a screenshot it read. The worker puts a prompt's files in the worktree's `.context/attachments/`, and the hub keeps every image. The interface says "file" or "image" | `Attachment`, `AttachmentId`, `AttachmentFile`, `NewAttachment`, the `attachments` table |
| Context folder | The worktree's `.context/`, where what isn't the repository's goes: the files prompts carried, in `.context/attachments/`, and what an agent makes for its own use while it works, such as notes, logs and screenshots, in folders it names for what they hold, rather than in the system's temporary directory. The worker makes it before each agent starts, git is told to ignore it, and it's deleted with the worktree. Not an agent's context, which is what its model holds | `worker::context_dir::Folder::Context` |
| Draft | What's typed or attached in a chat's composer, or typed as an answer to its question, and not sent. The hub keeps what's typed and attached in the composer on the chat's session, and what's chosen and typed in answer there too, by position, as the answer is sent. For a request to use a tool, it keeps which answer is chosen, as client-core orders them, and what's typed to tell the agent instead. A workspace's row shows a pencil while one of its chats has one. A comment being written on a diff is kept the same way, on its workspace, and so is what's in the new-workspace dialog, as one record of the hub's, though neither is called a draft on screen. Unrelated to a pull request that's a draft, which is GitHub's | `Draft`, `DraftToKeep`, `Session.draft`, `SessionDraft`, `AnswerDraft`, `Session.answer_draft`, `client_core::ToolUseAnswer`, `SessionAnswerDraft`, `CommentDraft`, `Workspace.comment_draft`, `WorkspaceCommentDraft`, `NewWorkspaceDraft`, `NewWorkspaceDraftToKeep`, `Records.new_workspace_draft`, `NewWorkspaceDraftKeep`, `NewWorkspaceDraftFileAdd`, `NewWorkspaceDraftFileRead`, `NewWorkspaceDraftFileRemove`, `NewWorkspaceCreate`, `NewWorkspaceMade`, the `new_workspace_draft_files` table, `AttachmentRemove`, `client_core::Drafts`, `client_core::DraftKey`, `client_core::DraftChange`, `client_core::FilesFor`, `client_core::KeptDraft`, `client_core::ReadBack`, `Client::read_back`, `new_workspace::Keeping`, `WorkspacePane::has_unsent` |
| Tool call | An agent using one of its tools, such as running a command or editing a file, and the result it got back. They arrive as two events, and the transcript draws them as one line that opens to what the call did. The agent's adapter says what kind of call it is, such as a command, an edit or handing work to a subagent, which is apart from a subagent's kind of agent. Every client reads the call by that kind, and says what it's about in one line, the same way. A call recorded before adapters said is read from its tool's name. A call the person denied says so on its result, which isn't read as a failure. An adapter that types its calls records a typed call and result in their place, and every client reads what came back from either the same way | `ContentBlock::ToolUse`, `ContentBlock::ToolResult`, `ContentBlock::Call`, `ContentBlock::CallResult`, `calls::Returned`, `ToolUseId`, `CallKind`, `Asking::ToolUse`, `client_core::calls`, `calls::Recorded`, `ToolCall`, `ToolCall::summary`, `client_core::calls::older`, `Denied`, `ContentBlock::ToolResult.denied` |
| The worker's tools | Tools of Roundhouse's own, which a worker serves its agents over MCP on 127.0.0.1, and which the hub answers, such as `get_pull_request`. Each agent reaches them with a token of its session's. They're apart from the agent's own tools, such as running a command | `worker::tools`, `ToolsToken`, `WorkerRequest::ServeTools`, `agents::ToolServer` |
| Wait | An agent waiting on explicit pull requests and their lower stack dependencies to reach a condition or need attention, which the hub keeps and ends once. A chat can have several independent waits at once. Not a watch, since a monitor watches and wakes the agent each time | `Wait`, `WaitEnd`, `WaitUntil`, `hub::waits`, the `waits` table |
| Ask | What a worker asks its hub, for one of its tools, which the hub answers as a worker answers a call | `WorkerFrame::Ask`, `protocol::worker::Ask`, `Answer`, `WorkerAsk`, `AskAnswer` |
| Ask key | What a worker gives an ask that makes a worktree, so a hub that hears the ask again, as each new hub does what the last didn't answer, makes it once. A UUID, or the agent's ID for the tool call that asked, and unique within its session. Not built | `AskKey`, `CreateWorktree.key` |
| Job | Work the hub does on its own, which no request waits on, as `Jobs` runs it: on a task of its own, within a time limit, about one workspace, which has one at a time. Its after-step runs once its work has ended, however it ended, and what the work ran uncut has too, to put back what the work may have left, such as a worker it started. Reading a pull request nobody asked for is one. Not a background task, which is an agent's, nor a Windows job object, which holds a group of processes | `jobs::Jobs`, `JobKind`, `Limits`, `Ended`, `jobs::step`, `jobs::uncut` |
| Steer | Send a prompt while the agent works, which it reads at its next chance, such as when a running tool finishes. Until then the prompt is waiting, and a stop drops it. The session's record lists the prompts its agent has yet to take | `PromptTaken`, `PromptDropped`, `PromptState`, `Settlement`, `Session::untaken` |
| Queue | Prompts waiting for the agent to finish, on the session's record. The hub sends each as a turn of its own. It's held, waiting for the person, after a stop, once the agent goes away mid-turn, after a turn that failed, or after the hub couldn't give the agent the prompt that would start a turn. One being queued from a client shows at its end there, faint, until the hub has it | `Session.queued`, `Session.queue_held`, `QueuedPrompt`, `SessionQueue`, `SessionChangeQueued`, `SessionSendQueued`, `Client::queueing`, `SessionStatus::is_done` |
| Approval | An agent asking before it uses a tool, asking the person questions, or asking to have its plan approved. Its adapter says which, why the agent asks when it says, and which subagent asks when one does, and any client can answer. One is open from its request until it's resolved, and the session's record lists those that are. A tool's use asked about with full access is allowed by the hub as it's asked, when the hub's settings say, so it's never open, and its answer says the setting allowed it | `ApprovalRequested`, `ApprovalResolved`, `ApprovalResolved::by_setting`, `Asking`, `Session::open_approvals`, `OpenApproval`, `client_core::ToolUseAsked`, `client_core::Given` |
| Question | An approval where the agent is asking a person something, so it needs an answer rather than a yes. Several can be asked together, each with its text, a header that names it, the options it offers and whether several of them can be chosen, and each can be answered by typing as well. A client answers them by position, and the adapter tells the agent in its own form. A client asks a request to use a tool the same way, as a question of its own making with allowing and denying as its options, which isn't a question in this sense, since the agent asked none | `Asking::Questions`, `Question`, `QuestionOption`, `QuestionAnswer`, `ApprovalDecision::AnswerByPosition`, and `ApprovalDecision::AnswerByText`, which older clients send |
| Approval mode | How much an agent may do without asking. Every agent has full access, except in plan mode. A mode an agent went into by itself, such as the CLI's `default`, which asks before every tool, is unknown, and a chat can't be given it | `PermissionMode`, `permission_mode` |
| Full access | The approval mode in which an agent uses its tools without asking, except for what its CLI asks about in every mode, such as a removal Claude's can't rule out as dangerous, which the hub allows for the person when Skip Claude's safety checks is on | `PermissionMode::FullAccess`, the CLI's `bypassPermissions`, `HubSettings::allow_asked_in_full_access` |
| Safety check | Claude's CLI checking a tool's use that it won't make unasked in any mode, such as a removal whose target only the command knows, so it asks even with full access, and says why. Skip Claude's safety checks, in Settings, has the hub allow what these ask | The CLI's `decision_reason_type: "safetyCheck"`, `ApprovalRequested::reason`, `HubSettings::allow_asked_in_full_access` |
| Plan mode | The approval mode in which an agent works out a plan, and asks before changing anything until it's approved. It asks to have the plan approved with an approval of its own. `Shift-Tab` turns it on and off | `PermissionMode::Plan`, the CLI's `plan`, `Asking::Plan` |
| Instructions | What every agent, and each of its subagents, is told about working in Roundhouse, in its system prompt: where to keep what it makes for its own use, how to show the person an image, and when to use the worker's tools rather than `gh`. Written once for any agent, and built into the worker. A tool server's own instructions, which say what its tools are for, are another thing | `worker::instructions::instructions`, `AgentOptions.instructions`, `agents::Instructions` |
| Context | What an agent's model holds of its conversation: the system prompt, tools, messages and so on, counted in tokens, up to the most the model takes, or less when something such as a setting makes it smaller. How full it is, how much its model holds and what set the most belong to the session's record, as the agent last said, and aren't in the log. About how many tokens a subagent's holds is on the subagent's own record, from the agent's word on it, which is in the log | `ContextUsage`, `ContextPart`, `MaxSetBy`, `Session.context`, `WorkerFrame::AgentContext`, `SubagentContext`, `Subagent::context_tokens` |
| Prompt cache | What the API keeps of a chat's conversation between its agent's requests, so the next needn't send it again. It expires one TTL after the agent's newest request was sent, and a prompt sent after that writes the whole conversation again. What it holds belongs to the session's record, and a prompt that found it expired is in the log | `PromptCache`, `CacheTtl`, `CacheRequest`, `Session.prompt_cache`, `WorkerFrame::AgentCache`, `AgentOutput::Cache`, `CacheExpired` |
| Compaction | An agent swapping what its context holds of the conversation for a summary it writes, and carrying on from that, so its context has room again. It does it by itself as its context fills, or when someone asks, through the hub, which records the request and refuses one while the agent is on a turn, has a prompt it hasn't taken, or before it has had a turn. How an agent is asked is its adapter's to know, such as Claude's `/compact` | `session_compact`, `CompactionAsked`, `AgentProcess::compact`, `AgentCompacting`, `AgentCompacted`, `Session::compaction_waits` |
| Limit | How much of an account's use of its agent is left in a window, such as five hours or seven days, or one model's own week, such as Fable's, named as its provider labels the model, and when the window ends. It's the account's, not a session's, so the hub keeps it on the account's record | `UsageLimit`, `LimitWindow`, `ModelLabel`, `EventBody::AgentLimits`, `WorkerFrame::AgentLimits`, `AgentOutput::Limits`, `Account.limits`, the `account_limits` table |
| Account | The login an agent's CLI runs under, which its hub hands to its worker, or the one on the worker's machine: the model provider, the plan, and the email. Agents under one account share its limits, and there can be several accounts with one model provider. Its ID is the adapter's, opaque, and the same for every agent under that login, or the hub's, for a login it holds that doesn't say whose it is. The hub keeps a record of each, and a session's record names the one it's on, when its account source is the hub, or otherwise the one its newest launch ran under. Connecting a token in place of the login of an account whose ID the hub chose renews it, which keeps its limits and sessions. Agents in Settings lists them as Found and Added, with when each was last used in its row's card | `AgentAccount`, `AccountId`, `Account`, `Session.account`, the `accounts` table, `AgentLogin`, `HeldLogin`, `LoginToken`, `Account.login_agent`, `account_connect` and `account_disconnect` for a login the hub holds, `AccountConnect.account` to renew one, the hub's `logins`, which keeps them, `runs_under_logins`, the account whose login each run was given, and `SessionAccount`, which older clients ask for |
| Account source | Where the login a chat's agent runs under comes from: the hub, for the account the chat's record names, or ambient. A chat's first launch takes its kind's default, which puts it on the hub's for an added default, or on ambient while its kind has none, once the worker says whose they are, so a chat whose ambient credentials nobody can name, as with nobody logged in, stays on none. Only moving it changes that, to the hub's for the account it's moved to. Changing the default doesn't, and nor does adding a login. A chat on an account whose login has ended or been disconnected is blocked until the login is renewed or the chat is moved, and moving a chat whose agent counts as running under another account stops it only once the person confirms. A chat on none from before, such as one that ran under ambient credentials then, has none until its next launch, and so does one whose record says the hub's but names no account. | `AccountSource`, `Session.account_source`, `Session::hub_account`, `SessionAssignAccount`, and the hub's `SessionLogin`, which reads a record's source and account as one, `NoneYet` being on none |
| Ambient | Credentials an agent's CLI finds in the environment of the machine it runs on, such as a login the person made there, rather than a login the hub holds and hands it. The hub learns whose they are only from the worker, after a launch, so it may never know, and they can be another account's at the next launch, if someone logs in as another there. Agents in Settings lists the accounts found this way as Found, and its default row says Machine login while there's no added default | `AccountSource::Ambient` |
| Login | The credential an account is used with: a machine's own, which Roundhouse only reads, or one the hub holds. Each the hub holds is a file of its own in the hub's data directory, which only the hub's user can open, in a directory no other kind's are in, and what else there is to say of it is on its account's record, since the copies of the database from before each migration would keep it once it was disconnected. The hub hands an agent's account's to the workers it launches the agent on, and the default GitHub account's to every worker, as its git credential. A GitHub account's holds a token, a sign-in's tokens and when each ends, or an app's installation's token and when it ends, and an app of your own's key is kept the same way, in the same directory, though it's no account's. One in a form only a newer build reads is kept, rather than taken for one that holds nothing and deleted. GitHub's API calls a user's name its `login`, which here is a username, never a login. | `LoginSecret`, with `Stored` for what a file holds, the hub's `login_files` and `LoginFiles`, `GithubLogin`, the `logins` directory, which holds agents' tokens, and the `github-logins` directory, which holds GitHub accounts' |
| GitHub account | An account on GitHub that the hub holds, or held, a login for, connected with a token the person made on GitHub, by signing in with GitHub, or as an app of your own's installation, which agents push and open pull requests as while it's the default. It's a record of its own, with an ID the hub chose, since one GitHub user can be connected more than once, and who it is on GitHub: the user's number, which never changes, and its username, which can. | Feed | The hub-wide stream that says a record changed, for sidebars and the like | `subscribe_feed`, `HubNotice`, `RecordNotice` |
| Update feed | The signed list of published builds that the app checks to update itself. Always written in full, so it isn't confused with the hub's feed | `releases.osx.json`, `updates::source`, `UpdateFeedKey` |
| Record | Something a hub owns that changes in place, rather than being added to a log: a repository, workspace, session, subagent, comment or terminal, or per-user state such as unread. One of any kind is a `Record`, which its `RecordKey` names | `Record`, `RecordKey`, `Records`, `Repo`, `Workspace`, `Session`, `Subagent`, `DiffComment`, `Terminal` |
| Revision | When a record last changed, from one counter per hub, so a client can tell which of two copies is newer | `Rev`, `rev` |

## Easily confused

| Word | The senses | What to write |
|---|---|---|
| Capability | What an agent can do, in `protocol::capability`, and what a provider can, such as whether it takes snapshots | "Capability" alone for an agent's, and "a provider's capabilities" for a provider's |
| Contract | What a capability promises once it's claimed, the contract tests of Claude's adapter, which check it against the CLI's captured output, and what an item's doc promises | "A capability's contract", "contract tests", and an item's doc for what it promises |
| Law | A contract of a capability that a session's log can be checked against by itself, and a property that a property test checks | "Law" for a capability's, as in `capability::laws`, and "property" for what a property test checks |
| Note | A prompt added to an agent's conversation without starting a turn, and what the app's `--note` says of why a copy is open | "Note" alone for the prompt in code about agents, and the flag by its name, `--note` |
| Review | A turn that reviews changes, a reviewer deciding a use in the person's place, and a pull request's reviews | "Review turn", "reviewer" and "a pull request's reviews", unless the context says which |
| Session, chat, conversation | The same thing at three levels. A session is ours, a chat is what the interface shows, and a conversation is the agent's own record, which is what it resumes | "Session" in code and docs, "chat" in text people read, and "conversation" only for the agent's side, as in `agent_session_id` (even when an agent's wire protocol, such as ACP's `sessionId`, calls its side a session) |
| Workspace | Ours, or another tool's, such as a Cargo workspace | A bare "workspace" means ours. Always qualify the others |
| Project, repository | The same record. A project is what people see, and a repository is the git codebase behind it | "Project" in the desktop app and its spec, and "repository" in code, the CLI and the other docs, and wherever git itself is meant, as in "repository settings" |
| Claude, Claude Code | The agent, and Anthropic's own product, whose CLI it runs | "Claude Code" in the interface, as the agent's description names it, such as for its own login on a machine, and "Claude" where it's short, as in Skip Claude's safety checks. "Claude CLI" for the `claude` binary in docs |
| Antigravity | The agent, and Google's product, whose `agy` CLI it runs | "Antigravity" in the interface and docs, and "`agy`" or "Antigravity CLI" for the binary in docs |
| Checkout | A copy of this repository that the app is built from, and a repository's checkout on a worker's machine, which the repository's worktrees are made from unless it's a clone, such as the one on the hub's machine that a project is added by | "Checkout" alone for this repository's, as the app's sidebar names it. "A repository's checkout" for the other, as `RepoSource::Checkout` and `RepoOrigin::Checkout` are |
| Workspace, worktree, instance | The record, the files, and where its worker runs | The one you mean. Archiving removes the worktree, not the workspace |
| State directory, instance directory, data directory | Where a worker keeps its own files, a local instance, and where a hub or a client keeps its records and settings | "The worker's state directory", or "state directory" where whose is clear. "Instance directory" only for a local instance as the local provider makes, finds and removes it, as `instance_dir` does: what a worker keeps there is in its state directory, even where the provider reads it. "Data directory" only for a hub's or a client's. Another program's own directory, such as Codex's, is named with its owner |
| Terminal | A workspace's, which its worker runs, or a terminal app, such as Terminal or Ghostty, on someone's own machine | Say "a terminal app" for the other wherever a workspace's could be meant |
| Name, title | A workspace's name, such as `euston`, is its directory and the folder its branches go in, which is the part of a branch's name before its first slash, so it starts on `euston/start`, and never changes once it's made. Its title is what the sidebar shows | "Name" only for the directory and the folder of branches. Renaming a workspace changes its title |
| Worker, agent | A worker is our process, and an agent is the CLI it runs | The one you mean. A worker can outlive its agents, and agents can outlive a killed worker |
| Model, dictation's model | Which model an agent runs, against the model dictation hears with, whose files are downloaded to this device | "Model" alone means the agent's, as `ModelName`. Say "dictation's model" where it isn't clear, as `dictation::model`, `ModelFiles` and `ModelDownload` are |
| Model name, model label | What an agent is asked to run, such as `fable` or `claude-fable-5-1`, and how the model's provider names it for people, such as `Fable`, which a model's own limit is named by | "Model" for either where it's clear. `ModelName` and `ModelLabel` in code, which can't be mixed up |
| Agent, harness | What other tools call a harness, the program that runs a model with its tools, such as the Claude CLI, is an agent here | "Agent". "Harness" only as another tool's word |
| Guide | The guide is `docs/guide`, how to use the product, published as the site's `/docs/` pages. A guide is one of its pages under Guides, named for what someone gets done | "The guide" for the whole, and "a made-up guide" for one a test builds. Otherwise "a guide" only for one of those pages, and "a page" for any other |
| Hub, daemon | `roundhoused` is one binary that runs as a hub, as a worker, or as the local provider's adapter. A stamped build's hub runs from its copy of it, `Roundhouse Hub`, and so do the workers that hub starts | "Hub" or "worker". "Daemon" only for the binary |
| Run, turn | A run is a process's lifetime, and a turn is one exchange within it | The one you mean. Counting turns can't give a session's status, as a prompt mid-turn adds none |
| Row | A row of the transcript's list, which an event is drawn in, and failed requests in a row, one after another with nothing between them that ended the row | "A row" alone for the list's. For failures, "in a row", or "the row" only where the failures are what's being said, as in "ends the row" |
| Approval mode, permission mode | The same setting. `--permission-mode`, `permissionMode` and `bypassPermissions` are the CLI's names | "Approval mode" in docs and interface text, and `PermissionMode` and `permission_mode` in code |
| Status | `SessionStatus`, `WorkspaceStatus`, `SetupStatus`, `ChildStatus` or `GitStatus`, and the box that says how something stands, such as dictation under its setting, `StatusBox`, which a `Setting` gives as its `status_box` | Say which |
| Adapter | An agent's adapter runs one kind of agent and turns its output into events. A provider's adapter makes and ends its instances | "Adapter" alone means an agent's, except where only a provider's can be meant, as in "Providers" in `docs/architecture.md`. Otherwise "provider adapter" |
| Base | A workspace's base ref is what its branch was created from. A base image is what a remote workspace's VM is made from | "Base" alone means the base ref. Always "base image" for the other |
| Provider, model provider | A provider is where a hub runs workers. A model provider is who serves an agent's model | "Provider" alone only for the first. Always "model provider" for the second, in code and in the interface |
| Account | An agent's account is the login its CLI runs under. A GitHub account is one the hub holds a login for, which agents push as. A hub's accounts, once a hub serves several people, are who may use it | "Account" alone means the agent's, until hubs have their own. Then say which. Always "GitHub account" for the second, and `Github*` in code |
| Notice | `EventBody::Notice` is a message in a session's log. `HubNotice` is on the feed, and says a record changed | "Log notice" or "feed notice" |
| Snapshot | `session::Snapshot` is what a subscriber starts from. A provider's `snapshot` saves a filesystem, and isn't built | Say which |
| Frame, step, window | A protocol frame, one message on the wire, and, in `dictation`, a short stretch of audio measured as one: 30 ms of it for finding pauses, and 10 ms for the model's features. The model's encoder makes out a step of 80 ms, which is decoded as one, and its live encoder takes a window of 6.16 s at a time | "Frame" alone means the protocol's. In `dictation`, say what a frame is of, such as "the features' frames", and "step" and "window" for the encoder's |
| Record, recording | A hub's record, such as a session's, and the hub recording something, against a recording of what's said to dictate a prompt | "Record" and "recorded" for the hub's, and "recording" only for dictation's, as `dictation::Recording` |
| Restore | `workspace_restore` recreates an archived worktree from its branch, and the workspace's record says `WorkspaceStatus::Restoring` meanwhile. A provider's `restore` rolls back a filesystem, and isn't built | "Restore" alone means the workspace's |
| Log | A session's log, or a log file such as `hub.log` or the setup log | A bare "log" means a session's. Name the file otherwise |
| Position | Where an event is in a session log a client holds, as `session_log::Position`, or where a question is among those asked together, or an option among a question's, by which a client answers them, as in `ApprovalDecision::AnswerByPosition` | "Position" alone means an event's, in a client's log. Say "a question's position" or "an option's position" for the others |
| Reply | What the agent said in a turn, or what a hub, a worker or a provider's adapter answers a request with | "The agent's reply" or "the hub's reply", unless only one can be meant. In code, the agent's is `Session.reply_seq`, and a request's is the protocol's, as in `protocol::client::Reply`, `HelloReply` and `HubFrame::Reply` |
| Settings | The app's own, chosen in Settings and kept on this Mac, a hub's, chosen there too and kept by the hub that carries them out, or a repository's, in its `.conductor/settings.toml` files | "Settings" alone means what's chosen in Settings. Say "hub settings" for the ones a hub keeps, `HubSettings`, and "repository settings" for a repository's |
| Stand-in | A program a test runs in place of another, in `tools/stand-ins/`, such as the fake agent, `fake_claude`, and a stand-in for a part that a test makes in its own process, such as `client_core::stand_in_hub`, which answers a client as a hub would. The program `stand_in_hub` is a hub of another build | "Stand-in" for either, with the program or the type by its name where both could be meant. "The fake agent" for `fake_claude` |

## Ending things

These sound alike, and do different things.

| Word | Applies to | What it does | Afterwards |
|---|---|---|---|
| Cancel, a sign-in | A sign-in with GitHub | Ends a sign-in that's waiting, so the hub stops asking GitHub after it and keeps nothing GitHub gives for it. `github_sign_in_cancel`, `GithubSignInStatus::Cancelled` | Its record says so until another sign-in starts |
| Cancel | A turn | Ends the current turn and any setup still running. The agent's process stays up. `session_cancel`, `Control::Cancel` | It takes the next prompt |
| Stop, in the interface | A turn | The Stop button and `Cmd-.` mean cancel, not a process stop. On a wait's line, Stop calls the wait off | As for cancel |
| Call off | A wait | Ends a wait before its condition: by its agent, by the person, or by closing its chat or archiving its workspace. Starting another wait leaves it alone. `session_call_off_wait`, `WaitEnd::Cancelled`, `CalledOffByPerson`; `Replaced` is a historical ending from older hubs | The agent hears, in a turn of its own, unless it called it off itself, or its chat or workspace went with it |
| Interrupt | A turn | What the agent CLI calls a cancel. Only the adapter says this, as in `AgentProcess::interrupt` | As for cancel |
| Interrupted | A session | A status, not an action: the agent went away mid-turn rather than ending the turn, whatever the reason, as when it exits by itself, its worker goes, or it's stopped by closing its chat, archiving its workspace or stopping the hub. A cancel ends the turn first, so it doesn't cause it | The next prompt resumes the conversation |
| Stop, in code | A process | Ends it, and gives it time to finish. `AgentStop`, `Provider::stop` | The next prompt starts a new one |
| Hang up | A terminal's shell | Ends it as closing a terminal app's window does. The shell and the job it runs in front, which has what's typed, are sent a hangup, which the shell passes on to the jobs it runs behind, and whichever hasn't ended two seconds later is killed. A job started to outlive the terminal, such as with `nohup`, goes on. `TerminalStop`, `Signal::Hangup` | The terminal closes, and its tab goes |
| Kill | An instance | Like stop, without the time. For a worker that isn't responding. `Provider::kill` | The next prompt starts a new one |
| Close | A session | Stops its agent and hides it from the tabs. The history stays. `session_close`, `Session::is_open` | It can be reopened with `session_reopen` |
| Archive | A workspace | Removes its worktree, and any others made for its work, and keeps their branches. Refuses if work would be lost, unless forced. Its record says it's being archived until it's done, or put back. `workspace_archive`, `WorkspaceStatus::Archiving` | It can be restored |
| Destroy | An instance | Removes it. `Provider::destroy` | It's gone |
| Remove | An app of your own | The hub forgets the app's key and each installation's login, then its record, and deletes nothing on GitHub. Remove app, in the menus of its rows on Git. `github_app_remove`, `GithubAppRemove` | Its installations' accounts stay, as disconnecting leaves one, and one that's the default stays the default, so agents can't push until another is. The app stays on GitHub, for the person to delete there |
| Disconnect | An account's login, or a GitHub account's | The hub forgets the login it holds for the account, so no agent launched after runs under it. It doesn't revoke the token. `account_disconnect`, and `github_account_disconnect` | The account's record stays, and connecting a token to it gives it a login again. A default GitHub account disconnected stays the default, and every worker's git credential becomes a block, so what agents are already running pushes as nobody from its next `git`. An app's installation disconnected stays installed on GitHub, and the hub connects it again only when the person asks it to connect the app's installations |
| Discard | A half-made workspace | Removes a workspace that failed while being created, or was left by a crash. `discard_workspace`, `take_unfinished_workspaces` | It's gone |
