# Terms

What this project's words mean. Code, docs and the interface use each word only in the sense given here. A new term, or a new sense of one, goes here in the change that introduces it.

Start with "Easily confused" and "Ending things", which cover the words most likely to go wrong.

## Parts

| Term | Meaning | In code |
|---|---|---|
| Roundhouse | This product: the desktop app, the CLI, and the hubs and workers behind them. Capitalized as a name, and lowercase for a binary, but for the hub's copy of the daemon, `Roundhouse Hub` | `roundhouse`, `roundhoused`, `roundhouse-desktop` |
| Hub | The server that clients connect to. It owns workspaces, sessions and their logs, and leaves the work itself to workers | `hub` |
| Worker | The process that does a workspace's work: its agents, git and scripts. It reports to its hub. There's one per workspace | `worker` |
| Provider | A kind of place a hub can run workers, such as this machine, an Incus instance or a cloud sandbox. The local provider runs workers on this machine, and it isn't special | `Provider`, `LocalProvider` |
| Instance | Where a provider runs one workspace's worker | `instance_id` |
| Provider adapter | The program that makes and ends a provider's instances. The hub runs it and talks to it over the provider protocol, and the local provider's is the daemon's `provider local`. Not built | `Provider` |
| Client | A program that talks to a hub, such as the desktop app or the CLI. Clients only talk to hubs | `client-core` |
| Agent | The coding agent a worker runs as a child process. Today that's only the Claude CLI | `AgentKind`, `AgentProcess` |
| Subagent | An agent that the agent starts inside its own process to do part of the work, such as a search, with a tool call. It isn't one the worker runs, and its lines name the call that started it as their parent, which the hub records with each event. The agent says when one starts, with what it was asked, how many tokens its conversation holds as it works, and when it ends, with its report, and the hub keeps a record of each. The transcript draws them in that call | `parent_tool_use_id`, `SessionEvent::subagent`, `SubagentStarted`, `SubagentContext`, `SubagentEnded`, `Subagent`, `CallKind::Subagent`, `calls::Recorded::hands_off`, `client_core::calls::agent` |
| Advisor | A stronger model the agent can ask for advice, which reads the whole conversation. The API runs it rather than the agent, so it's a tool call whose result comes in the agent's own messages, and the advice can come encrypted, for the model alone. A call the agent went on without, which it's been seen to do when it called one of its own tools first in the same message, is recorded as dropped | `CallKind::Advisor`, `ToolCall::Advisor`, `agents::claude::normalize::advisor`, `ContentBlock::ToolResult.encrypted`, `EventBody::ToolCallDropped` |
| Adapter | The code that runs one kind of agent and turns its output into events | `agents::claude` |
| Agent's description | What a kind of agent is called and offers, as its adapter describes it: what the interface calls it, the models, efforts and approval modes a chat can be given, what a chat runs with until another is chosen, what it does that not every agent does, such as compacting when asked, and what login a hub can hold for it: the command that makes its token, and how long one lasts | `AgentDescription`, `ModelChoice`, `AgentFeature`, `LoginDescription`, `agents::descriptions`, `ClientRequest::AgentList`, `client_core::Agents`, `Snapshot::agents`, `roundhouse agents` |

## Work

| Term | Meaning | In code |
|---|---|---|
| Repository | A git repository added to a hub | `Repo` |
| Project | What the interface calls a repository added to a hub: the entry that holds a codebase's workspaces and settings, with one git repository behind it | `Repo` |
| Workspace | The unit of delegation: a name, a branch and a worktree in one repository, with its sessions and diff comments | `Workspace` |
| Worktree | A workspace's git worktree, the files on disk | `Workspace.path` |
| Child worktree | Another worktree of a workspace's repository, made for its work, in `.children/` beside the workspaces. The interface says "other worktree". Not built | `ChildWorktree`, `CreateWorktree`, `AddChildWorktree` |
| Title | What a workspace or a chat is called on screen. It's generated from the first prompt, generated again from every prompt when someone asks, or typed by hand, and one typed by hand is replaced only by one someone asks for | `Workspace.title`, `Session.title`, `TitleSource` |
| Base ref | What a workspace's branch was created from. Diffs are taken against it | `base_ref` |
| Branches | What a worktree's git says of its branches, as its worker last read them: which is checked out, and each branch the worktree has had checked out, with its newest commit and where it's pushed. A workspace's name is only the folder its branches go in | `Workspace.branches`, `Branches`, `Branches.had`, `WorkerRequest::WatchBranches`, `ChildWorktree.branches`, `WatchChildBranches`, `WorkerFrame::ChildBranches` |
| A branch's pull request, linked | The pull request that's a branch's: one the branch has been at a commit of, which the worker then links the branch to, as a setting of the branch in git's config, so it stays the branch's as it moves on. Not any pull request from a branch of the same name, which `gh` finds by the name | `pull_request::link`, `link::linked`, `link::has_been_at` |
| Base image | A VM that a repository's own script has set up, with its tools installed and its caches warm. A remote workspace's VM is made as a copy of its repository's newest one. Not built | None |
| Session | One conversation with one agent, with its log. A workspace can have several | `Session` |
| Terminal | A shell a workspace's worker runs in the worktree, which every client can attach to and type into. The worker keeps what it shows, and a client that attaches gets that as a screen, then what its program writes. The hub keeps its record while its shell runs. Not a session, which is a chat's. Not built in the app | `Terminal`, `TerminalId`, `TerminalUpdate`, `TerminalScreen`, `terminal_state::Mirror`, `WorkerFrame::Terminal`, `HubFrame::Terminal` |
| Run | One launch of an agent. A session can have many, because an agent can exit and be started again. Its ID never repeats, even across hub restarts | `RunId`, `AgentSpec.run` |
| Turn | From a prompt until the agent finishes responding. A run can have many. A prompt sent mid-turn folds into the running one if the agent has more to do, and otherwise starts the next. The agent starts one by itself whenever one of its background tasks finishes, to take in how it ended | `TurnEnded`, `Session.turn_started_at_ms`, `SessionStatus::in_turn`, `SessionStatus::between_turns` |
| Background task | Work an agent started that carries on after its turn ends: a command, a subagent or a monitor. Until it finishes, and the agent has picked up again after the last of them, the session is active, so an update leaves it running on the version it started with and closing asks, and only a subagent counts as the agent itself working | `AgentTasks`, `AgentTask`, `TaskKind`, `SessionStatus::Background` |
| Monitor | A background task that watches for something, such as a check failing, and wakes the agent each time it happens. It does nothing meanwhile, and may never end | `TaskKind::Monitor` |
| Task group | The background tasks of one kind: subagents, commands or monitors. With more tasks than have a line each at the chat's end, a group with several has one line, which opens to theirs | `TaskGroup`, `TaskLine`, `transcript::task_lines` |
| Reply | What the agent said in a turn, as of the event that ended it, and how that turn ended. A turn the agent was cut off from isn't one | `Session.reply_seq`, `Session::has_reply`, `Session.reply_outcome` |
| Failed request | One of the agent's requests to its model that failed, as on a usage limit, which its CLI says in a message of its own in the model's place, and the chat shows as a red card. A turn mostly ends on one, and a subagent's leaves the agent going | `EventBody::RequestFailed`, `RequestFailure`, `FailureKind`, `TurnEnded.request_failed` |
| Stopped short | What a chat is when its agent went away mid-turn, or its newest turn failed, until a turn starts again. Its mark's turntable is red, it notifies, it holds its queue, and it needs the person | `Session::stopped_short`, `Session::turn_failed`, `Signal::Failed` |
| Prompt | What a person sends to an agent: what it says, and the files it carries, which pass from the client's bytes to the IDs it added them under, to the hub's record of each, to where the worker put each in the worktree. It's real once it's recorded, and until then a client shows it as pending, held as a queued prompt is, under the ID it'll be recorded under | `protocol::prompt::Prompt`, `UserPrompt`, `client_core::Written`, `SessionLog::pending` |
| Attachment | A file a prompt carries, of any kind, or an image a tool sent the agent, such as a screenshot it read. The worker puts a prompt's files in the worktree's `.context/attachments/`, and the hub keeps every image. The interface says "file" or "image" | `Attachment`, `AttachmentId`, `AttachmentFile`, `NewAttachment`, the `attachments` table |
| Context folder | The worktree's `.context/`, where what isn't the repository's goes: the files prompts carried, in `.context/attachments/`, and what an agent makes for its own use while it works, such as notes, logs and screenshots, in folders it names for what they hold, rather than in the system's temporary directory. The worker makes it before each agent starts, git is told to ignore it, and it's deleted with the worktree. Not an agent's context, which is what its model holds | `worker::context_dir::Folder::Context` |
| Draft | What's typed or attached in a chat's composer, or typed as an answer to its question, and not sent. The hub keeps what's typed and attached in the composer on the chat's session, and what's chosen and typed in answer there too, by position, as the answer is sent. For a request to use a tool, it keeps which answer is chosen, as client-core orders them, and what's typed to tell the agent instead. A workspace's row shows a pencil while one of its chats has one. A comment being written on a diff is kept the same way, on its workspace, and so is what's in the new-workspace dialog, as one record of the hub's, though neither is called a draft on screen. Unrelated to a pull request that's a draft, which is GitHub's | `Draft`, `DraftToKeep`, `Session.draft`, `SessionDraft`, `AnswerDraft`, `Session.answer_draft`, `client_core::ToolUseAnswer`, `SessionAnswerDraft`, `CommentDraft`, `Workspace.comment_draft`, `WorkspaceCommentDraft`, `NewWorkspaceDraft`, `NewWorkspaceDraftToKeep`, `Records.new_workspace_draft`, `NewWorkspaceDraftKeep`, `NewWorkspaceDraftFileAdd`, `NewWorkspaceDraftFileRead`, `NewWorkspaceDraftFileRemove`, `NewWorkspaceCreate`, `NewWorkspaceMade`, the `new_workspace_draft_files` table, `AttachmentRemove`, `client_core::Drafts`, `client_core::DraftKey`, `client_core::DraftChange`, `client_core::FilesFor`, `client_core::KeptDraft`, `client_core::ReadBack`, `Client::read_back`, `new_workspace::Keeping`, `WorkspacePane::has_unsent` |
| Tool call | An agent using one of its tools, such as running a command or editing a file, and the result it got back. They arrive as two events, and the transcript draws them as one line that opens to what the call did. The agent's adapter says what kind of call it is, such as a command, an edit or handing work to a subagent, which is apart from a subagent's kind of agent. Every client reads the call by that kind, and says what it's about in one line, the same way. A call recorded before adapters said is read from its tool's name. A call the person denied says so on its result, which isn't read as a failure | `ContentBlock::ToolUse`, `ContentBlock::ToolResult`, `ToolUseId`, `CallKind`, `Asking::ToolUse`, `client_core::calls`, `calls::Recorded`, `ToolCall`, `ToolCall::summary`, `client_core::calls::older`, `Denied`, `ContentBlock::ToolResult.denied` |
| The worker's tools | Tools of Roundhouse's own, which a worker serves its agents over MCP on 127.0.0.1, and which the hub answers, such as `get_pull_request`. Each agent reaches them with a token of its session's. They're apart from the agent's own tools, such as running a command | `worker::tools`, `ToolsToken`, `WorkerRequest::ServeTools`, `agents::ToolServer` |
| Wait | An agent waiting on its workspace's pull request until it's done or needs the agent, which the hub keeps and ends once. A chat has one at a time. Not a watch, since a monitor watches and wakes the agent each time | `Wait`, `WaitEnd`, `WaitUntil`, `hub::waits`, the `waits` table |
| Ask | What a worker asks its hub, for one of its tools, which the hub answers as a worker answers a call | `WorkerFrame::Ask`, `protocol::worker::Ask`, `Answer`, `WorkerAsk`, `AskAnswer` |
| Ask key | What a worker gives an ask that makes a worktree, so a hub that hears the ask again, as each new hub does what the last didn't answer, makes it once. A UUID, or the agent's ID for the tool call that asked, and unique within its session. Not built | `AskKey`, `CreateWorktree.key` |
| Steer | Send a prompt while the agent works, which it reads at its next chance, such as when a running tool finishes. Until then the prompt is waiting, and a stop drops it. The session's record lists the prompts its agent has yet to take | `PromptTaken`, `PromptDropped`, `PromptState`, `Settlement`, `Session::untaken` |
| Queue | Prompts waiting for the agent to finish, on the session's record. The hub sends each as a turn of its own. It's held, waiting for the person, after a stop, once the agent goes away mid-turn, or after a turn that failed. One being queued from a client shows at its end there, faint, until the hub has it | `Session.queued`, `Session.queue_held`, `QueuedPrompt`, `SessionQueue`, `SessionChangeQueued`, `SessionSendQueued`, `Client::queueing`, `SessionStatus::is_done` |
| Approval | An agent asking before it uses a tool, asking the person questions, or asking to have its plan approved. Its adapter says which, why the agent asks when it says, and which subagent asks when one does, and any client can answer. One is open from its request until it's resolved, and the session's record lists those that are. A tool's use asked about with full access is allowed by the hub as it's asked, when the hub's settings say, so it's never open, and its answer says the setting allowed it | `ApprovalRequested`, `ApprovalResolved`, `ApprovalResolved::by_setting`, `Asking`, `Session::open_approvals`, `OpenApproval`, `client_core::ToolUseAsked`, `client_core::Given` |
| Question | An approval where the agent is asking a person something, so it needs an answer rather than a yes. Several can be asked together, each with its text, a header that names it, the options it offers and whether several of them can be chosen, and each can be answered by typing as well. A client answers them by position, and the adapter tells the agent in its own form. A client asks a request to use a tool the same way, as a question of its own making with allowing and denying as its options, which isn't a question in this sense, since the agent asked none | `Asking::Questions`, `Question`, `QuestionOption`, `QuestionAnswer`, `ApprovalDecision::AnswerByPosition`, and `ApprovalDecision::AnswerByText`, which older clients send |
| Approval mode | How much an agent may do without asking. Every agent has full access, except in plan mode. A mode an agent went into by itself, such as the CLI's `default`, which asks before every tool, is unknown, and a chat can't be given it | `PermissionMode`, `permission_mode` |
| Full access | The approval mode in which an agent uses its tools without asking, except for what its CLI asks about in every mode, such as a removal Claude's can't rule out as dangerous, which the hub allows for the person when Skip Claude's safety checks is on | `PermissionMode::FullAccess`, the CLI's `bypassPermissions`, `HubSettings::allow_asked_in_full_access` |
| Safety check | Claude's CLI checking a tool's use that it won't make unasked in any mode, such as a removal whose target only the command knows, so it asks even with full access, and says why. Skip Claude's safety checks, in Settings, has the hub allow what these ask | The CLI's `decision_reason_type: "safetyCheck"`, `ApprovalRequested::reason`, `HubSettings::allow_asked_in_full_access` |
| Plan mode | The approval mode in which an agent works out a plan, and asks before changing anything until it's approved. It asks to have the plan approved with an approval of its own. `Shift-Tab` turns it on and off | `PermissionMode::Plan`, the CLI's `plan`, `Asking::Plan` |
| Instructions | What every agent, and each of its subagents, is told about working in Roundhouse, in its system prompt: where to keep what it makes for its own use, and how to show the person an image. Written once for any agent, and built into the worker. A tool server's own instructions, which say what its tools are for, are another thing | `worker::instructions::INSTRUCTIONS`, `AgentOptions.instructions` |
| Context | What an agent's model holds of its conversation: the system prompt, tools, messages and so on, counted in tokens, up to the most the model takes, or less when something such as a setting makes it smaller. How full it is, how much its model holds and what set the most belong to the session's record, as the agent last said, and aren't in the log. About how many tokens a subagent's holds is on the subagent's own record, from the agent's word on it, which is in the log | `ContextUsage`, `ContextPart`, `MaxSetBy`, `Session.context`, `WorkerFrame::AgentContext`, `SubagentContext`, `Subagent::context_tokens` |
| Prompt cache | What the API keeps of a chat's conversation between its agent's requests, so the next needn't send it again. It expires one TTL after the agent's newest request was sent, and a prompt sent after that writes the whole conversation again. What it holds belongs to the session's record, and a prompt that found it expired is in the log | `PromptCache`, `CacheTtl`, `CacheRequest`, `Session.prompt_cache`, `WorkerFrame::AgentCache`, `AgentOutput::Cache`, `CacheExpired` |
| Compaction | An agent swapping what its context holds of the conversation for a summary it writes, and carrying on from that, so its context has room again. It does it by itself as its context fills, or when someone asks, through the hub, which records the request and refuses one while the agent is on a turn, has a prompt it hasn't taken, or before it has had a turn. How an agent is asked is its adapter's to know, such as Claude's `/compact` | `session_compact`, `CompactionAsked`, `AgentProcess::compact`, `AgentCompacting`, `AgentCompacted`, `Session::compaction_waits` |
| Limit | How much of an account's use of its agent is left in a window, such as five hours or seven days, or one model's own week, such as Fable's, named as its provider labels the model, and when the window ends. It's the account's, not a session's, so the hub keeps it on the account's record | `UsageLimit`, `LimitWindow`, `ModelLabel`, `EventBody::AgentLimits`, `WorkerFrame::AgentLimits`, `AgentOutput::Limits`, `Account.limits`, the `account_limits` table |
| Account | The login an agent's CLI runs under, which its hub hands to its worker, or the one on the worker's machine: the model provider, the plan, and the email. Agents under one account share its limits, and there can be several accounts with one model provider. Its ID is the adapter's, opaque, and the same for every agent under that login, or the hub's, for a login it holds that doesn't say whose it is. The hub keeps a record of each, and a session's record names the one its agent runs under. Connecting a token in place of the login of an account whose ID the hub chose renews it, which keeps its limits and sessions | `AgentAccount`, `AccountId`, `Account`, `Session.account`, the `accounts` table, `AgentLogin`, `HeldLogin`, `LoginToken`, `Account.login_agent`, `account_connect` and `account_disconnect` for a login the hub holds, `AccountConnect.account` to renew one, the hub's `logins` and `login_files` and the `logins` directory, where it keeps them, `runs_under_logins`, the account whose login each run was given, and `SessionAccount`, which older clients ask for |
| Model provider | Who serves an agent's model, such as Anthropic's own API or a cloud's. It's part of an account | `AgentAccount.model_provider` |
| Model | Which model an agent runs, by the name its CLI takes: an alias such as `opus`, or a full ID. Every session names one, and never `default`, which would leave the choice to the CLI | `ModelName`, `Session.model`, `AgentDescription.defaults`, `model_picker` |
| Effort | How hard an agent thinks before it answers, from Low to Max. Every session names one, as it names a model, so neither is left to the user's own Claude settings | `Effort`, `Session.effort`, `AgentDescription.defaults`, `model_picker` |
| Settings | What a session runs with: its model, approval mode and effort. A change to them names only what it changes | `SessionSettings`, `SessionSettingsChange` |
| Setup | What happens once a worktree exists: copying local files and running the repository's setup script | `SetupStatus`, `worker::setup` |
| Diff comment | A comment on one line of a workspace's diff, which can be sent to the agent | `DiffComment` |

## History and delivery

| Term | Meaning | In code |
|---|---|---|
| Event | One entry in a session's log | `SessionEvent`, `EventBody` |
| Log | A session's events, in order. It's the source of truth for what happened | The `events` table |
| Seq | An event's position in its log. The first is 1, and there are no gaps, so 0 is before the first, where no event is, such as how far a chat nobody has read is read | `Seq`, `Seq::FIRST`, `Seq::next` |
| Place | An event's position among the events from the same agent or subagent in its log, as `seq` is among all of them. The first is 1, and there are no gaps | `Place`, `Place::FIRST`, `Place::next`, `SessionEvent::place` |
| Position | Where an event is in a session log a client holds, which gives the row it's in: its `seq` in a log of every event, and its place in a log of one agent's or subagent's events. The first is 1, in the first row, and 0 is before it, where no event is | `session_log::Position`, `SessionLog::position` |
| Raw line | The agent's original output, stored beside the event made from it | `raw` |
| Tail | Text the agent is still writing, which isn't in the log yet. The end of the chat draws it, with the prompts the agent hasn't read yet and the working line | `Tail` |
| Delta | One change to the tail. Deltas aren't stored | `StreamDelta` |
| Transcript | What a person sees: the log and tail, drawn as rows | `crates/transcript` |
| Frame | One message on the wire, as one line of JSON | `protocol::frame`, `HubFrame`, `WorkerFrame` |
| Hello | The first request on a connection, which names the versions of the protocol its side speaks, so both can use the newest they share | `ClientRequest::Hello`, `WorkerRequest::Hello`, `ProviderRequest::Hello` |
| Protocol version | The number two peers compare in their hello: a client and a hub, a hub and a worker, or a hub and a provider adapter. Each protocol has its own, and it only changes for a real break. Which ones a side speaks, from its oldest to its newest, are its versions | `CLIENT_PROTOCOL_VERSION`, `WORKER_PROTOCOL_VERSION`, `PROVIDER_PROTOCOL_VERSION`, `Versions` |
| On-demand hub | One a client started because it needed one, as opposed to one someone chose to run. Only this kind can be restarted from a client | `HubStatus::on_demand`, `roundhoused hub --on-demand` |
| Build version | Which build a binary is, for people to read, and for a hub to tell a worker of another build, which it replaces once nothing in its workspace is at work. A package stamps its published version, `0.1.N`, an install the commit it came from, and anything else says `-dev`. Whether two binaries can talk is up to the protocol version | `protocol::Build::version` |
| Build number | Puts the builds an install or a package makes in order, so the app can tell a hub is older. Any other build has none, so it's never replaced | `protocol::Build::number` |
| Stamped build | A build stamped with both a build version and a build number, as an install or a package does. Any other build says `-dev` whatever its code | `protocol::StampedBuild`, `protocol::this_build!` |
| Checkout | A copy of this repository that the app is built from, such as one in a workspace. A build that isn't stamped names its checkout in the sidebar and the window's title, with the note it was opened with, so copies open at once can be told apart. As it quits it says on stderr whether someone quit it or it had done what it was opened for, since it exits with 0 either way | `desktop::checkout::Checkout`, `--note`, `desktop::why_quit` |
| Hub's copy | The copy of the daemon that a stamped build's hubs run from, at `daemons/<version>-<number>/Roundhouse Hub` in the data directory. A client that starts a hub removes the old ones nothing runs from | `Paths::hub_copy`, `Daemon`, `process::RunningFrom` |
| Subscription | A client following one session's log, from a given seq, or the agent's own events or one subagent's in it, from a given place, or a terminal's updates, from a screen of what it shows | `subscription_id`, `TerminalAttach` |
| Feed | The hub-wide stream that says a record changed, for sidebars and the like | `subscribe_feed`, `HubNotice`, `RecordNotice` |
| Update feed | The signed list of published builds that the app checks to update itself. Always written in full, so it isn't confused with the hub's feed | `releases.osx.json`, `updates::source`, `UpdateFeedKey` |
| Record | Something a hub owns that changes in place, rather than being added to a log: a repository, workspace, session, subagent, comment or terminal, or per-user state such as unread. One of any kind is a `Record`, which its `RecordKey` names | `Record`, `RecordKey`, `Records`, `Repo`, `Workspace`, `Session`, `Subagent`, `DiffComment`, `Terminal` |
| Revision | When a record last changed, from one counter per hub, so a client can tell which of two copies is newer | `Rev`, `rev` |

## Easily confused

| Word | The senses | What to write |
|---|---|---|
| Session, chat, conversation | The same thing at three levels. A session is ours, a chat is what the interface shows, and a conversation is the agent's own record, which is what it resumes | "Session" in code and docs, "chat" in text people read, and "conversation" only for the agent's side, as in `agent_session_id` |
| Workspace | Ours, or another tool's, such as a Cargo workspace | A bare "workspace" means ours. Always qualify the others |
| Project, repository | The same record. A project is what people see, and a repository is the git codebase behind it | "Project" in the desktop app and its spec, and "repository" in code, the CLI and the other docs, and wherever git itself is meant, as in "repository settings" |
| Claude, Claude Code | The agent, and Anthropic's own product. The Agent SDK's terms bar calling an agent in another product "Claude Code" | "Claude" or "Claude Agent" in the interface. "Claude CLI" for the `claude` binary in docs |
| Workspace, worktree, instance | The record, the files, and where its worker runs | The one you mean. Archiving removes the worktree, not the workspace |
| Terminal | A workspace's, which its worker runs, or a terminal app, such as Terminal or Ghostty, on someone's own machine | Say "a terminal app" for the other wherever a workspace's could be meant |
| Name, title | A workspace's name, such as `euston`, is its directory and the folder its branches go in, which is the part of a branch's name before its first slash, so it starts on `euston/start`, and never changes once it's made. Its title is what the sidebar shows | "Name" only for the directory and the folder of branches. Renaming a workspace changes its title |
| Worker, agent | A worker is our process, and an agent is the CLI it runs | The one you mean. A worker can outlive its agents, and agents can outlive a killed worker |
| Model name, model label | What an agent is asked to run, such as `fable` or `claude-fable-5-1`, and how the model's provider names it for people, such as `Fable`, which a model's own limit is named by | "Model" for either where it's clear. `ModelName` and `ModelLabel` in code, which can't be mixed up |
| Agent, harness | What other tools call a harness, the program that runs a model with its tools, such as the Claude CLI, is an agent here | "Agent". "Harness" only as another tool's word |
| Guide | The guide is `docs/guide`, how to use the product, published as the site's `/docs/` pages. A guide is one of its pages under Guides, named for what someone gets done | "The guide" for the whole, and "a made-up guide" for one a test builds. Otherwise "a guide" only for one of those pages, and "a page" for any other |
| Hub, daemon | `roundhoused` is one binary that runs as a hub, as a worker, or as the local provider's adapter. A stamped build's hub runs from its copy of it, `Roundhouse Hub`, and so do the workers that hub starts | "Hub" or "worker". "Daemon" only for the binary |
| Run, turn | A run is a process's lifetime, and a turn is one exchange within it | The one you mean. Counting turns can't give a session's status, as a prompt mid-turn adds none |
| Approval mode, permission mode | The same setting. `--permission-mode`, `permissionMode` and `bypassPermissions` are the CLI's names | "Approval mode" in docs and interface text, and `PermissionMode` and `permission_mode` in code |
| Status | `SessionStatus`, `WorkspaceStatus`, `SetupStatus`, `ChildStatus` or `GitStatus` | Say which |
| Adapter | An agent's adapter runs one kind of agent and turns its output into events. A provider's adapter makes and ends its instances | "Adapter" alone means an agent's, except where only a provider's can be meant, as in "Providers" in `docs/architecture.md`. Otherwise "provider adapter" |
| Base | A workspace's base ref is what its branch was created from. A base image is what a remote workspace's VM is made from | "Base" alone means the base ref. Always "base image" for the other |
| Provider, model provider | A provider is where a hub runs workers. A model provider is who serves an agent's model | "Provider" alone only for the first. Always "model provider" for the second, in code and in the interface |
| Account | An agent's account is the login its CLI runs under. A hub's accounts, once a hub serves several people, are who may use it | "Account" alone means the agent's, until hubs have their own. Then say which |
| Notice | `EventBody::Notice` is a message in a session's log. `HubNotice` is on the feed, and says a record changed | "Log notice" or "feed notice" |
| Snapshot | `session::Snapshot` is what a subscriber starts from. A provider's `snapshot` saves a filesystem, and isn't built | Say which |
| Restore | `workspace_restore` recreates an archived worktree from its branch, and the workspace's record says `WorkspaceStatus::Restoring` meanwhile. A provider's `restore` rolls back a filesystem, and isn't built | "Restore" alone means the workspace's |
| Log | A session's log, or a log file such as `hub.log` or the setup log | A bare "log" means a session's. Name the file otherwise |
| Position | Where an event is in a session log a client holds, as `session_log::Position`, or where a question is among those asked together, or an option among a question's, by which a client answers them, as in `ApprovalDecision::AnswerByPosition` | "Position" alone means an event's, in a client's log. Say "a question's position" or "an option's position" for the others |
| Reply | What the agent said in a turn, or what a hub, a worker or a provider's adapter answers a request with | "The agent's reply" or "the hub's reply", unless only one can be meant. In code, the agent's is `Session.reply_seq`, and a request's is the protocol's, as in `protocol::client::Reply`, `HelloReply` and `HubFrame::Reply` |
| Settings | The app's own, chosen in Settings and kept on this Mac, a hub's, chosen there too and kept by the hub that carries them out, or a repository's, in its `.conductor/settings.toml` files | "Settings" alone means what's chosen in Settings. Say "hub settings" for the ones a hub keeps, `HubSettings`, and "repository settings" for a repository's |

## Ending things

These sound alike, and do different things.

| Word | Applies to | What it does | Afterwards |
|---|---|---|---|
| Cancel | A turn | Ends the current turn and any setup still running. The agent's process stays up. `session_cancel`, `AgentCancel` | It takes the next prompt |
| Stop, in the interface | A turn | The Stop button and `Cmd-.` mean cancel, not a process stop. On a wait's line, Stop calls the wait off | As for cancel |
| Call off | A wait | Ends a wait on the pull request before what it waits for: by its agent, by the person, by a wait the agent starts after it, or by closing its chat or archiving its workspace. `session_call_off_wait`, `WaitEnd::Cancelled`, `CalledOffByPerson`, `Replaced` | The agent hears, in a turn of its own, unless it called it off itself, or its chat or workspace went with it |
| Interrupt | A turn | What the agent CLI calls a cancel. Only the adapter says this, as in `AgentProcess::interrupt` | As for cancel |
| Interrupted | A session | A status, not an action: the agent went away mid-turn rather than ending the turn, whatever the reason, as when it exits by itself, its worker goes, or it's stopped by closing its chat, archiving its workspace or stopping the hub. A cancel ends the turn first, so it doesn't cause it | The next prompt resumes the conversation |
| Stop, in code | A process | Ends it, and gives it time to finish. `AgentStop`, `Provider::stop` | The next prompt starts a new one |
| Hang up | A terminal's shell | Ends it as closing a terminal app's window does. The shell and the job it runs in front, which has what's typed, are sent a hangup, which the shell passes on to the jobs it runs behind, and whichever hasn't ended two seconds later is killed. A job started to outlive the terminal, such as with `nohup`, goes on. `TerminalStop`, `Signal::Hangup` | The terminal closes, and its tab goes |
| Kill | An instance | Like stop, without the time. For a worker that isn't responding. `Provider::kill` | The next prompt starts a new one |
| Close | A session | Stops its agent and hides it from the tabs. The history stays. `session_close`, `Session::is_open` | It can be reopened with `session_reopen` |
| Archive | A workspace | Removes its worktree, and any others made for its work, and keeps their branches. Refuses if work would be lost, unless forced. Its record says it's being archived until it's done, or put back. `workspace_archive`, `WorkspaceStatus::Archiving` | It can be restored |
| Destroy | An instance | Removes it. `Provider::destroy` | It's gone |
| Disconnect | An account's login | The hub forgets the login it holds for the account, so no agent launched after runs under it. It doesn't revoke the token. `account_disconnect` | The account's record stays, and connecting a token to it gives it a login again |
| Discard | A half-made workspace | Removes a workspace that failed while being created, or was left by a crash. `discard_workspace`, `take_unfinished_workspaces` | It's gone |
