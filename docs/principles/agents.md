# Agents, their adapters and the worker's tools

These rules say how the hub and clients deal with each kind of agent through its adapter, what a chat can ask of an agent, and how an agent uses Roundhouse's own tools. `docs/reference/` has what each agent's CLI does.

## Adapters

- **Only an agent's adapter knows that agent's protocol and its tools' names.** The adapter records each fact as a typed event or field, and the hub and clients read the typed form. For example, the adapter stores a tool call as a `Call` and its result as a `CallOutput`, so every client draws every agent's calls the same way. A tool with no kind of its own is a `Call::Other`.
- **An adapter drops a line only by naming its kind and why, never by a pattern.** A dropped line is gone. A line the adapter doesn't recognize becomes an `AgentOther` event with its raw line, for a later build to translate. So `AgentOther` holds only what isn't understood yet.
- **Agent output is untrusted input.** A normalizer, such as `agents::claude::normalize`, takes any line without panicking. When an agent's text names a file, the worker resolves every symlink before it checks that the file is inside the worktree.
- **What's specific to one kind of agent is in its adapter's description, and neither the hub nor a client branches on the kind.** The `agents` crate writes each kind's `AgentDescription` beside its adapter. The hub doesn't depend on `agents`, so the daemon's `main` passes the descriptions in, and clients get them from the hub with `agent_list`. No client keeps a list of its own of what an agent offers. For example, the command a person runs to make an agent's login token is a fact about the agent's CLI, so it's in the description.
- **An adapter turns off state its agent keeps past its process, where the agent allows it.** An agent's memories and schedules carry from one conversation to the next on the worker's machine. Roundhouse has no record of them, and an instance that's destroyed and created again loses them.

## What a chat asks of an agent

- **The hub checks what a client asks of an agent against what the agent's run claims, and rejects it before sending it.** A request the agent can't take is then rejected, and not lost on its way. For example, each `Control`, which is a request to a running agent, names the capabilities it needs, and the hub rejects one that the run doesn't claim. A client reads a run's claims from the session's record, and offers only what they allow.
- **What Roundhouse owns isn't a capability.** The queue, how conversations are named, worktrees and signing in to an account are Roundhouse's, so no agent keeps a second record of them.
- **Every session names its model, approval mode and effort, and every launch passes all three.** None is left to the agent's CLI.
- **Everything else an agent's CLI reads from its own settings, and Roundhouse keeps no copy of them.** The CLI reads them from the machine it runs on and from the repository. On a person's own machine, every account an agent runs under shares that machine's settings, such as `advisorModel`, which turns on Claude Code's advisor. On a worker the provider manages, a setting someone wants reaches the agent through the repository, such as in its committed `.claude/settings.json`. So each setting is changed in one place, the CLI's own, and Roundhouse doesn't keep a second copy in step across accounts and machines.
- **The hub's tool servers are apart from those in a CLI's own settings.** The hub sends its own to every worker, which passes them to each agent at launch. It never copies one from a CLI's settings, changes one there or turns one off, so what a person set up for the CLI works as it does in a terminal. For example, a person who has Linear in both has two servers, and where their names are the same, the CLI decides which it uses. `docs/decisions/hub-holds-tool-servers.md` has the design.
- **A running agent is asked to connect again to one of the hub's servers that's signed in to or edited, if it needs to and its run claims it can be.** Every agent is given every server at launch, signed in to or not, so its CLI has the server. The hub asks once for each change, once the agent's worker has said it has the server as it is, and only for a server its worker says is the hub's. An ask counts as that once only when it reaches the agent, as a person's Reload does: one that doesn't, as where the agent's turn has started or its worker's connection is lost, is asked again the next time the hub looks, and one the agent refuses, or takes and then fails to connect, isn't. A run that says it isn't connected to it needs to whatever changed but its name. One that is, and claims that, needs to for one whose tools may be others: one moved to another URL, one with another query, or one the person saved though the hub couldn't use it. It's asked once its turn ends, whatever changed, or at once if it's on none, since connecting can fail its calls to the server and holds up what the person sends it. Until then, what the hub keeps of its servers says which it's to connect to once its turn ends. Clients show what the hub says, and none works it out for itself. So a renewal, a rename and a key that its calls have already ask nothing, and no prompt waits behind a connection nobody needed. What comes of it is what the run says of its servers, and never an error in the chat. A person can have any of a run's servers connected to again too, and one it's connected to where the run claims that. It's never asked of the worker's own server, since where connecting fails, the Claude CLI doesn't ask after its running tasks again until it's connected to. A run that doesn't claim it isn't asked: Antigravity's CLI tries a failed server again by itself. *Unconfirmed:* asking a run once more after the hub restarts, since nothing keeps what it was asked.

## The worker's tools

- **A worker serves Roundhouse's tools to its agents, and the hub replies to each call from its own records.** The worker sends the hub an ask for each tool call. For example, the hub replies to `get_diff_comments` because the hub stores the comments.
- **A tool call reaches only the workspace of the worker that served it.** The hub knows which workspace each worker belongs to, and replies to an ask only for that workspace's sessions. A tool reaches more only if it's given more.
- **A tool's result is written for the agent, in full, separately from what the app shows.** An agent reads the result as text and misreads what a person wouldn't. For example, an agent reads a pull request that's in the merge queue as merged.
- **The instructions every agent gets don't depend on which of the worker's tools the agent has.** The system prompt states only what's true with or without the tools, because the Claude CLI keeps a chat's first system prompt until the chat is compacted, and an agent's tools are set at every launch. The system prompt and the instructions of the worker's own server describe the tools as a group, so adding a tool changes neither.
