# Outside systems and their credentials

These rules cover the systems this project doesn't own, such as GitHub, git and the place a provider runs its instances: where the code that talks to one goes, what the hub stores of what it reads from one, and how a credential for one is kept. `docs/principles/agents.md` has the rules for an agent's CLI.

- **Each outside system has one integration module, and nothing else knows its flags, wire format or retries.** `agents::claude`, `worker::git` and `github` are three. `github` is a crate that depends on `protocol` and on nothing of the hub's, so the compiler enforces the rule. It sends GitHub what the hub asks and returns what GitHub said. What the hub stores of that, and when, stays in the hub.
- **What the hub reads from an outside system is a cache, and what Roundhouse decides about it is the hub's own record, which keeps only the link.** Which pull request is a workspace's, and which account a project uses, are Roundhouse's decisions, so they're records and the truth. A workspace's record keeps its pull request's address, and what GitHub says of the pull request is in the cache. Everything in the cache can be read again, so losing it loses nothing. A record can't always be rebuilt: once a workspace's branch is deleted, or its name is used again, GitHub alone can't say which pull request the workspace had.
- **One module of the hub makes every read of GitHub, and keeps what it read.** Whatever needs GitHub asks it for what it needs, how old that may be, and how urgent the read is. It answers from what it keeps, joins a read under way, or adds the ask to its next query for that token. So a pull request that's a workspace's own and is named in a chat is read once, and the bar and the chip show the same. *Not built:* only reads of chips join one under way. Each read of pull requests, for the bar, waits, agents and the reads nobody asks for, is a query of its own, which keeps what it read in it.
- **What's kept is keyed by what it describes, in facets that each have the time they were read.** An issue or a pull request is keyed by its repository and number, which pull requests a branch has by its repository and name, and checks by the commit they ran on, so a new commit's checks are not known rather than the last commit's. A pull request's facets are its summary, which is its title and where it stands, and its checks, reviews, stack and comments, each a list that costs GitHub's points by its size. Every read takes the summary, which costs least, and a facet is read only when what asks needs it fresher. For example, a chip asks for the summary, so it costs no checks. *Not built:* a pull request's checks are kept by the pull request, with the commit they ran on, and only the last commit's. Its comments aren't kept. The bar, waits and agents read every facet each time, as of one read.
- **The cache is a file of its own, apart from the hub's database, which the hub empties rather than migrates.** It has a version of its own. When the version isn't the hub's, as after an update that changes the cache's form, the hub empties it and reads GitHub again, so the cache needs no migration and no copy before one.
- **A client says what it shows, and the hub sends it what changes, so no client asks again on a timer.** What's shown is also what the hub reads most often.
- **The hub holds no lock while it calls an outside system, and checks again after the call that what the response is about hasn't changed.** The hub calls, then takes the lock, checks again, and writes. So a GitHub that doesn't respond fails only the request that called it. For example, the hub discards a renewed GitHub token when the account was disconnected or signed in again during the call.
- **Work nobody asked for never delays or uses up what a person is waiting on.** For example, the hub's background reads of GitHub, and agents' reads, stop when a fifth of a login's hourly limit is left, and reads someone is waiting on continue until none is left.
- **A secret that opens an outside system, or the hub itself, is never kept in the database, in the worktree or on a command line.** The hub and a worker keep one in a file of its own that only its user can read, and a client keeps its hub's token in the system's credential store. The hub copies its database before each migration, and a copy would keep a token after its account was disconnected. An agent and git would see a file in the worktree. For example, the hub keeps each GitHub token in a file of its own in `github-logins/`. A token that only tells Roundhouse's own parts apart on one machine can be a row. For example, each session's token for the worker's tools is one, since it opens only that session's tools, from the worker's own machine. It still stays off the command line: Claude receives it in a file in the worker's state directory, through `--mcp-config`.
- **When the login someone chose can't be used, what needed it is blocked and says why, and never runs under another login.** For example, a default GitHub account whose token has ended stays the default, and agents on the providers Roundhouse sets up GitHub on push as nobody, not as the machine's own login. An agent kind's default account and a chat's account follow the same rule. *Unconfirmed.*
- **A repository's address is stored, sent and logged without a credential.** The worker removes any credential an address holds, such as a token in an `https://` URL, and the hub keeps no address that still has one.
- **A provider adapter holds its own credentials for the place where it runs instances, and the hub stores no secret for an adapter.** For example, an Incus adapter uses the Incus client's remotes, and an AWS adapter the standard AWS credentials.
