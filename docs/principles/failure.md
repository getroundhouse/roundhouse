# When a process dies or a peer is slow

These rules say what the system does when a hub, a worker, an agent or a client is killed, and how one slow process is kept from delaying the others.

## A process that dies

- **No process relies on another process exiting cleanly.** Any process can be killed at any moment, and the process that survives, or the next one to start, works out what happened from what was recorded. For example, a worker that's killed can't stop its agents, so it writes each agent's PID and start time to a file in its state directory, and the local provider stops every process still listed there before the next worker starts.
- **The hub records work before it starts the work.** A hub that stops part way then leaves a record of what may exist, and the next hub finishes the work or undoes it. Every client can also show the work in progress. For example, the hub records an instance before it asks a provider to create it, and records a workspace as archiving before it archives it. A hub that starts and finds a workspace archiving asks the workspace's worker whether the worktree still exists, then records the workspace as ready or as archived. A prompt is recorded the same way, before the hub tries anything else with it, and later failures go in the log.
- **A worker and its agents keep running when their hub goes away, and the next hub reconnects to them.** A local hub restarts for every update, and a remote worker's hub can be unreachable for as long as its machine sleeps. The worker numbers what it sends and keeps it until a hub confirms that it's recorded, and a hub that reconnects drops anything it has already recorded. So a hub records everything a worker sends exactly once. *Not built:* a remote worker, and a worker on Windows, which stops its agents when it loses its hub.
- **Nothing runs indefinitely with no hub to record it.** For example, `roundhouse hub stop` stops each workspace's worker, and the agents it runs, before the hub exits. A local worker that has had no hub for ten minutes stops its agents and terminals, then exits.
- **Stopping a process stops everything it started.** Workers, agents and setup scripts each start in their own process group, so a stop reaches the whole group. A provider's `stop` also ends anything the worker left behind.
- **A hub replaces a workspace's worker only when nothing in the workspace is at work.** Replacing the worker would end that work. The hub decides that a workspace is idle from its records, so a piece of work is on a record before the hub requests a worker for it. A workspace is at work while it has a session in a turn, waiting on an approval or with a background task, a setup script running, an open terminal, or a call to the worker that the hub still waits on.

## A peer that's slow

- **Every wait on another process or an outside system has a time limit.** For example, a call to GitHub gets 15 seconds, so a GitHub that doesn't respond fails only the request that called it. A worker gets ten seconds to reply to a `GitCredentialSet`, and the hub stops one that doesn't.
- **A slow or failing peer delays only itself.** For example, a slow client falls behind on the log and delays no other client, and a read of GitHub that hangs under one login delays no other login's read.
- **Work that no request waits on runs as a job of its own, with a time limit.** The code that decides what's due only starts jobs and never waits for one, so a job that hangs delays only itself. A job that reaches its limit is stopped, and the log records which job it was and how far it got. For example, the hub polls GitHub for each sign-in in a job of its own, so a sign-in that GitHub never responds to delays only itself. *Not built:* the hub's background work other than its reads of pull requests and its sign-ins. *Unconfirmed.*
