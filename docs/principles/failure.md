# When a process dies or a peer is slow

These rules say what the system does when a hub, a worker, an agent or a client is killed, and how one slow process is kept from delaying the others.

## A process that dies

- **No process relies on another process exiting cleanly.** Any process can be killed at any moment, and the process that survives, or the next one to start, works out what happened from what was recorded. For example, a worker that's killed can't stop its agents, so it writes each agent's PID and start time to a file in its state directory, and the local provider stops every process still listed there before the next worker starts.
- **The hub records work before it starts the work.** A hub that stops part way then leaves a record of what may exist, and the next hub finishes the work or undoes it. Every client can also show the work in progress. For example, the hub records an instance before it asks a provider to create it, and records a workspace as archiving before it archives it. A hub that starts and finds a workspace archiving asks the workspace's worker whether the worktree still exists, then records the workspace as ready or as archived. A prompt is recorded the same way, before the hub tries anything else with it, and later failures go in the log.
- **A worker and its agents keep running when their hub goes away, and the next hub reconnects to them.** A local hub restarts for every update, and a remote worker's hub can be unreachable for as long as its machine sleeps. The worker numbers what it sends and keeps it until a hub confirms that it's recorded, and a hub that reconnects drops anything it has already recorded. So a hub records everything a worker sends exactly once. *Not built:* a remote worker, and a worker on Windows, which stops its agents when it loses its hub.
- **Nothing runs indefinitely with no hub to record it.** For example, `roundhouse hub stop` stops each workspace's worker, and the agents it runs, before the hub exits. A local worker that has had no hub for ten minutes stops its agents and terminals, then exits.
- **A lock that more than one process takes is a lock on a file beside what it guards, and the file is never deleted.** The system releases the lock when its holder dies, so nothing has to clear a dead holder's lock, and every process on the machine finds it, whichever hub it belongs to. For example, a hub locks a file in its data directory, and a worker locks one beside a repository's worktrees while it adds one. The exception is a program's file that a process marks as in use: that lock is on the file itself, since the file is what gets removed. *Unconfirmed.*
- **A file that another process reads or runs appears under its name only once it's whole.** It's written under a temporary name beside it, then linked or renamed into place, so a process killed part way leaves nothing half-written where another would find it. For example, a client writes its build's copy of the daemon under a temporary name, checks that it's that build, and only then links it in as the copy a hub starts from. *Unconfirmed.*
- **A hub that stops waits only for work that can't be done again.** It ends everything else where it is, and the next hub does that work again or undoes it as it starts. For example, a stop waits for a GitHub token's renewal, because GitHub has already revoked the old token, and for a tool server's sign-in's, whose old refresh token may be refused the same way, and doesn't wait for a job or for an installation's token. *Unconfirmed.*
- **Stopping a process stops everything it started.** Workers, agents and setup scripts each start in their own process group, so a stop reaches the whole group. A provider's `end_worker` also ends anything the worker left behind.
- **A hub replaces a workspace's worker only when nothing in the workspace is at work.** Replacing the worker would end that work. The hub decides that a workspace is idle from its records, so a piece of work is on a record before the hub requests a worker for it. A workspace is at work while it has a session in a turn, waiting on an approval or with a background task, a setup script running, an open terminal, or a call to the worker that the hub still waits on.

## A peer that's slow

- **Every wait on another process or an outside system has a time limit.** For example, a call to GitHub gets 15 seconds, so a GitHub that doesn't respond fails only the request that called it. A worker gets ten seconds to reply to a `GitCredentialSet` or a `ToolServersSet`, and the hub stops one that doesn't. The exception is an agent's call to a tool server, which its CLI decides how long to wait for. Not every CLI closes its connection when it gives up or is stopped, so a call can last until the server ends it or the CLI exits. Connecting still has a limit. So that a server that never answers holds up only itself, a workspace's agents can have at most 8 requests under way to each server, and one past that fails at once, with an error that names the server. A stream of the server's events counts only until the server begins it, since each agent keeps one open for as long as it's connected. *Unconfirmed:* the number, and that a stream counts only until it's begun.
- **A slow or failing peer delays only itself.** For example, a slow client falls behind on the log and delays no other client, and a read of GitHub that hangs under one login delays no other login's read.
- **Work that no request waits on runs as a job of its own, with a time limit.** The code that decides what's due only starts jobs and never waits for one, so a job that hangs delays only itself. A job that reaches its limit is stopped, and the log records which job it was and how far it got. For example, the hub polls GitHub for each sign-in in a job of its own, so a sign-in that GitHub never responds to delays only itself. *Not built:* the hub's background work other than its reads of pull requests and of a workspace's changes, its sign-ins and its lookups of an agent's models. *Unconfirmed.*
