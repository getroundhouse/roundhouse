# Changing a protocol

These rules say how a protocol's forms change with no new version, so that peers on different builds keep working together. `docs/principles/versions.md` says what a break is, how two sides agree a version, and which versions work together. These rules hold for all three protocols that cross between processes: the client protocol, between clients and a hub, the worker protocol, between a hub and its workers, and the provider protocol, between a hub and its provider adapters. All three have the same problem, so nobody has to remember which rule applies where. *Not built:* the local provider as an adapter. The hub calls it directly, so the hub's side of the provider protocol ships, and no adapter that speaks it does.

## Changes that need no new version

- **Each message type has one serialized form: its serde form in `protocol`, on the wire and in the hub's SQLite columns.** So a change to a type also changes how stored rows deserialize.
- **A new field is `Option` or `#[serde(default)]`.** A message from an older peer, which lacks the field, still deserializes. So does a row stored before the field existed.
- **Every enum that's read as data has a `#[serde(other)] Unknown` variant, and an envelope type has none.** Statuses, kinds, events and blocks are read as data. Without the variant, one new value fails the whole frame. Envelope types, such as `HubFrame` and `ClientResponse`, have none, because a reader could do nothing sensible with an unknown one. A client receives a new kind of response only by sending a new request.
- **Code that receives `Unknown` never treats it as a value this build knows.** It skips the value, shows something neutral or rejects it, and it never panics. It checks that a value is known before comparing it with another that could also be unknown, because two `Unknown`s compare equal whatever they stood for. It doesn't send an unknown value to a peer to act on, because the peer would read only `Unknown`. *Not built:* a launch in an approval mode the hub doesn't know runs with full access, and a new workspace's first chat compares two efforts without checking that either is known.
- **A new request needs no new version, and its caller handles `ErrorCode::Unsupported`.** A hub, a worker or a provider adapter returns `Unsupported` for a request it doesn't know or can't deserialize, and keeps the connection open. A client checks `is_unsupported()` and hides or disables the feature that needed the request. A hub does without the request, or passes the error to whoever asked. No peer sends a list of what it supports until something needs one. For example, a client that gets `Unsupported` for `session_find` doesn't send it again until its next connection. A reply its reader can't deserialize ends the request with an error, so the request doesn't wait until the connection closes. *Unconfirmed:* a reply that can't be read.
- **A request that changes something is safe to send twice, and its reply reports only what the hub has recorded.** A sender can then retry after a disconnect or a lost reply. The request either has the same effect however often it's applied, such as `session_close`, or carries an ID its sender chose, which the receiver records once, as a prompt carries `client_msg_id`. Whatever happens after the reply reaches clients through the log and the records. A worker's asks to its hub follow the same rule, because a worker that outlives its hub sends each unanswered ask to the next one. What's pressed in a terminal is the one request that's never safe to send twice. *Not built:* cancelling a turn and running setup again carry no ID.
- **A request that ends with a record removed replies with the record as it last was, and the feed says the record is gone.** The reply keeps the form an older client expects. A client drops the older of the two, whichever arrives first. Sending the request again, or following the record, returns `NotFound`, which a client reads as the record being gone and doesn't report as a failure. For example, `session_close` on a chat nothing was sent in deletes the chat and replies with the session. *Unconfirmed.*
