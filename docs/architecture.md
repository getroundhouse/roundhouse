# Architecture

How the system fits together, and why. This is the agreed design, so it includes parts that aren't built, and those are marked. Where the code does something simpler for now, this says what.

## Core model

- **A hub owns state and serves the platform API.** It holds workspaces, sessions and event logs. Clients only talk to hubs, and a client can connect to several at once and merge them into one sidebar.
- **A worker does the work.** It runs agents, terminals and git for a workspace, and reports events to its hub.
- **A provider gives a hub somewhere to run workers.** Running on the same Mac is one provider, an Incus instance is another, and a cloud sandbox is another. No provider is special, and **any hub can use any provider**.
- **A client is an app for a family of devices, designed for each.** The desktop app runs on macOS, Windows and Linux, the CLI in a terminal, and one iOS app on phones, tablets and foldables. *Not built:* the iOS app. Every client shares `client-core`, the apps share the transcript and the design system in `look` too, and each app lays out its own screens, as "Each client" in `docs/spec/look.md` says.

## Where a hub can run

All of these are the same code and the same API. A workspace belongs to one hub.

| Hub | Runs on | Serves | Storage | Auth |
|---|---|---|---|---|
| **Local** | A Mac | One person | SQLite | A Unix socket only this user can open. The relay path needs its own |
| **Self-hosted** | Your own server | You or your team | SQLite, Postgres if it grows | Accounts or tokens |
| **Hosted**, if one is ever run | A shared service | Many users | Postgres | Accounts |

Any of them can use any provider. A hub is only reachable while its machine is awake, so persistent mobile access needs an always-on hub.

A local hub keeps its Mac awake while it has work, which `docs/spec/chats.md` defines, unless its settings say not to. It runs macOS's `caffeinate` for as long as there's any, starts it again if something else stops it, and has it stop when the hub does, so a hub that's killed can't leave the Mac awake. The hub does this rather than a worker or the app, because it outlives the app, knows what every session is doing, and sends queued prompts itself. A worker on another machine keeps its own awake. *Not built.*

## Platform API

The hub serves this API to the desktop app, mobile app, CLI and automation:

- **Workspaces:** create, list, archive and restore.
- **Sessions:** read history by range, list their prompts, subscribe to new events, send prompts and approvals, and cancel.
- **Per-workspace data:** diff comments, unread, pinned and drafts.
- **Live access:** attach to a terminal, and get diffs, git status, PR status and images in the worktree. The hub fetches or proxies these from the worker.

The hub doesn't do the work itself. When a workspace is created, it records it and tells a worker to create the worktree and start the agent. The worker reports events back, and the hub saves them and passes them to clients.

## Alternatives considered

- **The same full daemon everywhere,** with each sandbox owning its log and the control plane holding a copy. Simpler to start, but it means two copies of each cloud log and a second read path for sleeping sandboxes.
- **Separate local and cloud paths.** It would duplicate features.
- **Everything through a central sync engine.** It would break offline use and keeping local data on the device.
- **An off-the-shelf sync engine,** such as PowerSync, Electric or Turso's sync. They solve merging writes from clients that work offline, which a hub that's the only writer doesn't need. They need Postgres or copy a whole database to each client, and none covers a window of a log or a tail that isn't stored, while "Keeping clients in sync" needs only a revision and a few rules. Clients that write while offline would be the reason to look again.
- **CRDTs for session history.** They suit many people typing in one buffer, which isn't this product. Long sessions are remote, so clients read a log by range instead, and never hold a whole transcript.

## Dependency rules

```
apps/desktop ──> transcript, terminal-view ──> client-core ──> protocol
apps/desktop, transcript ──> dictation-ui ──> dictation, look
apps/desktop, transcript ──> look
apps/desktop ──> dictation, fetching
dictation ──> fetching, to download its model
apps/cli ─────────────────────────────────────> client-core
apps/desktop, apps/cli ──> local-hub ──> client-core, to start a hub on this machine
apps/daemon ──> hub ──> github ──> protocol
apps/daemon ──> providers ──> protocol
apps/daemon ──> worker ──> agents ──> protocol
worker, client-core, terminal-view ──> terminal-state
apps/daemon ──> agents, for their descriptions
hub, agents, providers, worker, local-hub, apps/daemon ──> process
hub, agents, worker, local-hub ──> private-files
```

1. **Clients only talk to hubs.** They never touch git, terminals or agents directly. The hub fetches or proxies live data from the worker.
2. **`protocol` has no IO and no UI.** Everything depends on it, so it needs to stay small and stable.
3. **The hub and worker must build on Linux without GPUI.** Nothing under `hub`, `github`, `worker`, `agents` or `providers` may depend on GPUI or gpui-kit.
4. **GPUI stays in `transcript`, `dictation-ui`, `terminal-view`, `look` and `apps/`.** `client-core` must stay free of it, and of any async runtime: it's blocking calls and channels, so GPUI's executor stays out, and a native mobile client remains possible if the GPUI path fails. `look` is a crate of its own because both the app and `transcript` draw with it, and `transcript` can't depend on the app. For the same reason it names the parts of the window tests find by where they're drawn, as `look::Region`, since both mark some. *Unconfirmed.* `dictation-ui` attaches dictation to an existing text field, shared by desktop and transcript so the latter need not depend on the app. The attachment owns its recording, tentative text, cancellation snapshot, visual response and tasks; the host owns its input, visibility and submission action. A single weak active-target reference arbitrates the microphone and receives key releases across dialogs. Desktop supplies recordings and owns model readiness and saved settings. Final words emit the input's normal change event, so the existing draft owner saves them and a question selects its written answer just as for typing. `dictation` stays free of GPUI, of any async runtime and of our other crates but `fetching`, which it downloads its model with under its `download` feature, since what it hears is the device's alone, and the iPhone app could hear with it too. Only a Mac hears the microphone, as `dictation::HEARS` says, and on Windows and Linux the app offers no dictation. Only a Mac mutes its sound output while it's dictated to, as `dictation::MUTES_OUTPUT` says, and elsewhere Settings doesn't offer to. *Unconfirmed.* `fetching` stays free of GPUI, of any async runtime and of our other crates, since it knows nothing of what it fetches, so the iPhone app could fetch with it too. *Unconfirmed.*
5. **The worker and provider boundaries are real.** Even on a Mac, the worker runs as a separate process, so remote workers only change the transport. The hub reaches the local provider the way it reaches any other, through the provider protocol, to an adapter in a process of its own, so the protocol is used by every workspace and a new provider is only a new adapter. *Not built:* the hub depends on `providers`, and runs the local provider inside itself.
6. **Exact pins for GPUI, and a copy of gpui-kit of our own.** Both are pre-1.0, so an upgrade should be deliberate and in one place. The kit is a copy, in `third_party/gpui-kit/vendor`, so that a change the app needs of it goes in with the app code that needs it, checked with the app, and is offered upstream from `third_party/gpui-kit/patches`. Only the kit is copied: GPUI comes unchanged from crates.io, and a change it needs goes to Zed.
7. **Nothing that ships is under GPL, AGPL or LGPL.** MPL-2.0 is allowed when it comes unchanged from crates.io, and everything else is permissive, such as Apache-2.0 or MIT. GPL or AGPL code would put the whole app under its terms, which would decide the project's own license and rule out closed or hosted versions, and GPL is widely seen as incompatible with the App Store. AGPL also reaches the hub over the network. LGPL expects users to be able to relink, which static linking makes awkward. MPL-2.0 only covers its own files (§3.3), and shipping it unchanged only means saying where its source is (§3.2), which goes in the notices every license needs anyway. A changed copy would have to be published, hence crates.io only. The one exception is the AppImage runtime, the program Velopack puts at the front of the Linux app, which mounts the app's files and starts it, and which has libfuse, under LGPL-2.1, built in. Every AppImage runtime uses FUSE, and an AppImage is the only package Velopack updates on Linux. The runtime is a program of its own, MIT and unchanged from upstream, so the LGPL covers only it, and nothing of ours links libfuse. Meeting it means the notices saying where the runtime's and libfuse's sources are.

`tools/policy/tests/policy/` checks rules 1 to 4 and 7 against the real dependency graph, so `cargo test` fails if a new dependency breaks one, and checks that the app builds gpui-kit from its copy, on the release `tools/kit-sync` pins. The license check covers what actually ships on each platform, not everything in `Cargo.lock`, with two gaps. The Mac app also ships `UpdateMac`, the updater Velopack builds from its own Rust and ships prebuilt, so the crates in it aren't in `Cargo.lock` and the check can't see them. The same goes for the `Update.exe` and the installer it ships for Windows, and for `UpdateNix` and the AppImage runtime it ships for Linux. Velopack itself is MIT. And the daemon, the CLI and the desktop app have Ghostty's terminal core built in, which the build script of `libghostty-vt-sys` fetches and builds with Zig, with the libraries it builds in, so none of them are in `Cargo.lock` either. Ghostty's `deps/libghostty-vt-third-party.json` lists them: Ghostty itself and translate-c are MIT, simdutf and Wuffs are Apache-2.0 or MIT, Highway is Apache-2.0 or BSD-3-Clause, and uucode is MIT and Unicode-3.0.

Someone else's files kept in the repo rather than taken from crates.io, such as the desktop app's file icons and the copy of gpui-kit, whose icons are under licenses its manifests don't name, aren't all in the dependency graph either, so the policy tests list each such folder with its license, and check that its license file says so, and that every license file in the repo is in a folder on the list, apart from those in hidden folders, in folders `.gitignore` leaves out, such as `node_modules`, and links, such as the one from a crate in the copy of gpui-kit to the copy's own license. *Unconfirmed.*

### Layers

Dependencies point inward, from handlers to operations to stores and integrations. A layer answers with a lower layer's type wherever it means the same, rather than copying it.

| Layer | What it does | Here |
|---|---|---|
| Handlers | Parse a request, call one operation, map its result | `hub::server`, `worker::serve` |
| Operations | One module per area, holding its logic | `hub` |
| Stores | All SQL, inline: a few dozen statements, with nothing to check them at compile time | `hub::store` |
| Integrations | One module per outside system. Nothing else knows its flags, wire format or retries | `agents::claude`, `worker::git`, `hub::worker_link`, `github`, `providers::local` |
| Edges | Configuration and telemetry, read from the environment and passed down | `main` in each app |

GitHub's integration is a crate of its own, `github`, which depends on `protocol` and nothing of the hub's, so the compiler keeps the layer's line: it asks GitHub what the hub asks and answers with what GitHub said, and what the hub keeps of it, and when, stays in the hub. Only the hub depends on it, and its stand-in for GitHub is behind its `testing` feature, which the hub's turns on.

Errors follow the layers:

- **Hub and worker operations return `protocol::client::ApiError`,** the error both protocols carry. Its `ErrorCode` is a closed set of meanings, such as `NotFound` and `Conflict`, not a transport status, so a second enum mapping onto it would only be a copy. Callers and tests match `code`, and `message` is for people. A condition callers must tell apart gets a new `ErrorCode`.
- **`hub::store` has its own enum,** because `ApiError` holds only text, and using it at the bottom would throw away the SQLite error.
- **Lower errors become `ApiError` in one place per crate,** an `impl From<…> for ApiError`, so the mapping reads as one table. `Internal` failures get logged there, with their source.

## State ownership

Each piece of state has one owner, and every other copy is a cache.

**What every client shows alike is the hub's, recorded rather than worked out or fetched live.** The test: should a second client, or this one after a restart, show the same thing? Then the hub owns it, and a client only draws it. A client keeps or works something out only when it's about its own device, as the table says. A fix that finds a client doing more than that moves the state to the hub, even when that's the bigger change. A protocol change is the normal way to do it, and "Changing the protocol" says how to make one, mostly without a version bump.

## Keeping clients in sync

A client's copy of a hub's state has to stay correct through lag, reconnects and restarts at either end, without each view working out how. Everything a hub serves is one of three kinds, and each kind has one way to tell a newer copy from an older one, and one way to recover.

| Kind | What | Newer or older | Recovering |
|---|---|---|---|
| Log | A session's events, or only the agent's own or one subagent's | By `seq`, or by place among the events from the same agent or subagent, neither of which has gaps | Subscribe again from one past the last `seq` or place, or read it again from a hub of another build |
| Record | Repositories, workspaces, sessions, comments, a hub's settings, the accounts its agents run under, the GitHub accounts it holds, the sign-ins with GitHub it has started, the GitHub login found on each provider's machines, the apps of your own it holds the key of and whether the default can push to each repository, per-user state and a workspace's terminals, and each session's subagents and proposals, which are listed by session. *Unconfirmed:* GitHub accounts, each a record of its own, and apps of your own, each a record of its own, apart from its installations' accounts, and a workspace's terminals | By revision, `rev`, from one counter per hub that moves in the same transaction as the change | List again, and keep whichever copy has the newer revision |
| Live | Output that isn't stored, such as the tail, and a terminal's. *Unconfirmed:* a terminal's | Nothing to compare. It belongs to one run of an agent, or one terminal, and arrives in order on one connection | Replace it with a new snapshot |

- **For logs and records, which copy is newer is decided per item, so the order things arrive in doesn't matter.** A duplicate or an older copy is dropped by its `seq` or revision, so a client doesn't depend on how a list and a feed notice interleave, which a relay or a second connection could change. A list is read in one transaction and carries the revision it was read at, so a record missing from it is gone, unless the client holds a newer copy from the feed. Removing a record is a change like any other, with a revision of its own. A session's newest event isn't announced, so it isn't part of its revision, and the log says how far a session has got.
- **A log's events don't change once recorded, except in a migration,** which can rewrite events stored in an older form, as the hub's `typed_calls` migration types the calls Claude's adapter recorded before it typed them, as the typed `Call` of "What each kind of agent can do". A rewritten event keeps its `seq` and place, so catching up from one past the last would keep the copy a client holds. So a client that reaches a hub of another build than the one it read a log from, as each hub's hello says, reads the log again, each event where it is, and keeps drawing the copy it holds until the new one comes, so a chat stays on screen through an update. A hub migrates before it answers a hello, so no client reads a log part way through. It goes by the build, which every hello already says, rather than something the hub keeps of its migrations, so every update reads each open chat again, though few rewrite anything, since that's a window of each, once. Builds are told apart as a hub tells its workers apart, so two builds that say `-dev` are taken for one, though a migration can come between them. A migration that rewrites a record moves its revision, as any change to a record does, so a client lists it again as usual. *Unconfirmed:* keeping the copy it holds drawn.
- **The hub's feed never tells of a copy of a record that's no newer than one it has told of,** so a client hears each record's copies once each, in the order of their revisions, though it doesn't depend on that. Several of the hub's tasks can announce one record, each with a copy read at or after its own change, so two can carry the same copy, or finish in the other order. The feed leaves out a copy no newer than the last it told of that record, or of its removal, and checks and sends under one lock. *Unconfirmed.*
- **A client following one agent or subagent gets only what that one writes, and the tail it leaves.** The hub sends it only that one's deltas, and when another's event ends what that one was writing, as the end of a turn ends a message from a subagent in the foreground, or a subagent's end ends its own, the hub sends it a new tail, since it never sees that event.
- **Only the current run's live output reaches clients.** The hub knows which run it's starting before it launches it, and drops live output from any other, so a replaced agent can't clear or add to its replacement's tail. A replaced run's events are history, so they go in the log as usual, as "When a process dies" says. A run's ID doesn't repeat within its session, even across hub restarts, so this holds once workers outlive their hub. Each event and delta carries its run, and the end of a turn or of an agent clears what its run or an earlier one left open, never a later run's, so a client that sees a replaced run's last events keeps the same tail as the hub. The end of a turn leaves what a subagent in the background is writing, since it carries on after the turn, and the tail says which subagents those are, so a client that joins later keeps the same tail too. The end of the agent clears that as well. A later launch always has a higher run ID.

**Every ID has one allocator, and is unique only within its scope,** so nothing is taken as unique where it might not be.

## Paired hubs

The desktop can select a hub on another machine over direct TLS 1.3. It uses the mobile pairing protocol: **Pair a device with this Mac…** in the hub switcher, or `roundhouse phone pair` on its machine, asks the local hub for a single-use link valid for ten minutes. The link carries candidate addresses and the SHA-256 fingerprint of the hub's public key. The client verifies that key before sending the code, receives a per-device token, and authenticates with it before hello on subsequent connections. The hub stores only the token's hash. Local clients can list and revoke devices; revocation closes their connections. Network clients cannot stop or restart the hub or manage paired devices. They can use a workspace's terminals, as they can prompt its agents. *Unconfirmed:* terminals over the network.

The listener starts for pairing, or at startup when devices are paired. `ROUNDHOUSE_LISTEN` chooses its address or port; the defaults are port 7867 for release builds and 7868 for development. There is no relay or NAT traversal: the machines must be directly reachable, for example over a LAN or tailnet.

Workspace state remains on its hub. The desktop keeps a separate view and client-core state for each opened hub, keyed by its pinned public key rather than its device authorization. Pairing again with the same key replaces authorization on the existing view and reconnects its draft keeper. A changed key is a separate trust identity. Background views keep updating their own records and drafts, but only the selected view can take focus or present a dialog; pending dialogs wait for that hub to be selected. Saved names, addresses, fingerprints and selected hub are per-device settings; tokens are in the OS credential store, scoped to the local data directory so development checkouts cannot reuse installed credentials. Quitting considers unsent work across all opened hubs. These desktop storage and view details are *Unconfirmed*.

Pairing, or authentication and hello together, have ten seconds after TLS connects. Each outgoing frame has ten seconds to finish, including a peer that stays connected but stops reading. Expiry closes the connection and releases its pending calls. Idle connections can wait for events without a read deadline; TCP keepalive detects a machine that disappears. These timeout choices are *Unconfirmed*.

## Wire format and event log

Details are in `crates/protocol/`.

- **Newline-delimited JSON over any byte stream,** with a Unix socket or Windows named pipe for local clients, TLS for paired remote clients, and stdio for workers. It works over anything, it can be read by hand, and agent output is already JSON.
- **Versioning:** both sides say hello first and agree on a protocol version. "Changing the protocol" says how, and what needs a bump, which is rare.
- **`hub_status`, `hub_shutdown` and `hub_restart` work without a hello,** so a client of any version can see a hub, and stop or restart it. That's how `roundhouse hub status`, `roundhouse hub stop` and the app's `Restart the hub` work across a real break, and how the app restarts a hub to update it, and it's why the app can say how many agents would stop. Anyone who can reach the socket is this user. A connection from elsewhere, once there are any, shouldn't get this. *Unconfirmed:* `hub_restart`.
- **On Windows a client's byte stream is a named pipe,** since neither tokio nor stable Rust has Unix sockets there. A pipe has no place in a directory, so it's named for the hub's data directory, one for each, and a checkout's hub stays out of an installed app's reach. The name comes from the path as it's spelled, so the data directory has to be an absolute path there. It has the permissions Windows gives a pipe by default, which let this user, administrators and the system send requests, and anyone else only read. Another user on the machine can make a pipe of that name first, and a client takes it for its hub and sends it prompts, so this isn't safe on a machine with other users. A client checking who serves the pipe would close that. *Unconfirmed.*
- **The database only migrates forward.** Migrations run in order, each in its own transaction, and a database from a newer build is refused rather than damaged.
- **A hub saves a copy of the database before migrating it,** and doesn't start if it can't. Any update can bring a migration without anyone choosing it, and the build before can't open what it leaves. The copies are in `backups/` in the data directory, and each of the last three schema versions copied keeps its newest, so retrying an update that stopped part way can't push out the copy from before it. *Unconfirmed.*
- **The agent's adapter says what each line its agent writes is, and what leaves nothing in the record isn't stored.** Only the adapter knows its agent's protocol. Each line it knows becomes an event, live output such as a delta, or nothing: a heartbeat, a notification of what a finished item says whole, or state the agent keeps for its own interfaces. It names each kind it drops, with why, rather than dropping by a pattern, since a dropped line is gone. A line it doesn't know is an `AgentOther`, with its raw line, for a later build to translate, so `AgentOther` is what isn't understood yet, not a place for what is. The hub records what it's sent, and an event's place says whose it is, not whether it's worth showing. Whether an event draws anything is the client's to say.
- **Each event has a normalized body, plus the agent's raw line in a separate column.** Agent output is untrusted input, so `agents::claude::normalize` takes any line without panicking. Clients read the normalized form. The raw line means views can be rebuilt if normalization was wrong, and range reads don't load it. An image a tool sent back is the one thing left out of it: the adapter puts the ID of the attachment that keeps the image wherever its base64 was, so a rebuild finds the image among the session's attachments rather than in the line. The CLI sends a read screenshot twice in one line, as about a megabyte, so kept whole, a few dozen reads can outweigh every other line in the database. *Unconfirmed.*
- **The agent's adapter types each tool's use,** as a `Call`, such as a command, a read, an edit, a search or handing work to a subagent, since only the adapter knows the agent's tools, and what came back for it as a `CallOutput`. ### Changing the protocol

These rules let peers on different versions keep working together. They hold for all three protocols that cross between processes: the client protocol, between clients and a hub, the worker protocol, between a hub and its workers, and the provider protocol, between a hub and its providers' adapters. All three meet the same problem, so one set of rules covers them, and nobody has to remember which applies where. *Not built:* the provider protocol. The stream a provider opens for preflight carries one question and its answer, with no hello, so the question carries a version of its own, which goes up only for a break, and an endpoint refuses one newer than its own with `Unsupported`. A question or a field is added to it as to the others.

- **Each shape has one form.** It's the serde form in `protocol`, on the wire and in the hub's SQLite columns, so changing a type also changes how old rows read.
- **A new field is `Option` or `#[serde(default)]`,** so a message from an older peer still decodes. The same goes for old rows.
- **Every enum read as data has `#[serde(other)] Unknown`:** statuses, kinds, events and blocks. Without it, one new value fails the whole frame, which `client-core` drops, failing the call if it was a reply. Code that receives `Unknown` skips it, shows something neutral or refuses it, and never treats it as a value this build knows. Before comparing a value with another that can be unknown too, it checks that the value is known, since any two unknowns are equal whatever they stood for. It passes no unknown to a peer to act on, since the peer would read it only as `Unknown`. It never panics. *Not built:* a launch in an approval mode the hub doesn't know runs with full access, since `Unknown` also stands for a mode the agent went into by itself, and the new workspace's first chat takes an effort picked as the chat's own when the two are equal, without checking that either is known.
- **Other envelopes have no `Unknown`.** That covers `HubFrame`, `ClientResponse` and the like, since there's nothing sensible to do with one. A client only gets a new response by making a new request.
- **A new request doesn't need a bump, and whoever calls it has to expect a refusal.** A hub, a worker or a provider's adapter answers a request it doesn't know with `ErrorCode::Unsupported`, and carries on. That includes a known request with a value in it the reader doesn't know, since either comes from a newer peer, and its caller handles both the same way. A client checks `is_unsupported()`, and hides or disables whatever needed it. A hub does without it, or passes the refusal on to whoever asked. There's no list of what a peer supports until something needs one. Each reads a frame's `id` before its request, so it can refuse one it can't read as a whole, once it has checked what it checks of any request, such as that the hello came first. A frame that names no call closes a client's connection. A reply the reader can't read ends the call it was for with an error, rather than leaving it to wait until the connection closes. *Unconfirmed:* refusing a known request with a value the reader doesn't know, and ending the call a reply that can't be read was for.
- **A version bump means a real break,** meaning a change that a peer on the last version can't read under these rules. The rules above cover most changes, so it should be rare.
- **Each protocol has its own version,** so a break in one doesn't break the other.
- **A hello says which versions its side speaks, and both sides use the newest they share.** It names the newest and the oldest, and the reply names the one chosen. A hello that names only one speaks only that one, as a peer from before ranges does, so that peer still gets an answer. A side whose hello is answered with a version it doesn't speak goes no further. *Unconfirmed:* going no further.
- **The hub speaks the current and the previous version of each protocol, and clients, workers and provider adapters speak only their own.** The hub is the one party that meets skew in both directions, since clients only talk to hubs, a worker only to the hub that started it, from that hub's build, as "Providers" says, and a provider adapter only to the hub that runs it. So the code for an old version lives in one place, and only until the next break. A hub speaks protocol 4 of workers as well as 5, reading the frames protocol 4 has for what its agents report, where protocol 5 has a report, with `protocol::worker::previous`, from the places that ask `WorkerLink::speaks_previous`.
- **A protocol breaks whenever a change needs it,** however soon after its last break. A hub speaks no version older than the one before its own, so a worker or a client two breaks behind it is cut off. The hub ends such a worker as it starts, and its agents with it, as it does after a rollback past a break, and such a client says it can't talk to the hub. The app's update crosses one break at a time, as "Managing a hub" says, so it cuts off none of its hub's workers, and the app updates with the hub it starts, so it's never a client two breaks behind it. That needs a published release between each two breaks in the worker protocol, for the app to step to, on each platform whose apps step, so a break in the worker protocol waits in the merge queue until each of those has published a release with the last one, as "Updating the app" says. A published break in the worker protocol is fixed forward rather than reverted, since an app with a worker of the break and an older one at work would take the revert, and its hub would end the newer worker, with its agents, but for one that got past the merge queue's check, which only a revert can get publishing again. Each break costs the app's update a step, and the feed a release it keeps for good, so the breaks one change needs, a stack's included, are made as one, as "Splitting a change" in `docs/pull-requests.md` says. Clients and provider adapters that can't all be updated with their hub, such as an iPhone app waiting on App Store review, or the apps of everyone sharing a hub, would need a hub that keeps speaking each version for a while after the one that replaces it.
- **The hellos, `hub_status`, `hub_shutdown`, `hub_restart` and refusals can't change form, even in a real break.** The hellos are how two versions find one they share, and the rest let a client see a hub, and stop or restart it, across a break. `crates/protocol/tests/compatibility/` spells them out, so changing one fails it. *Unconfirmed:* the hellos, and `hub_restart`.
- **A break is tested against the version before it.** The change that makes it keeps the previous version's wire form of each message it changes, spelled out as `crates/protocol/tests/compatibility/` does, and tests that the hub still reads and answers it. CI also runs a hub through a turn with the workers of two older releases: the one before it, and the oldest from the week before it whose protocol the hub still speaks. A worker lives through every update made while its workspace is at work, and a hub can come to rely on something recent workers send, which a worker from before them doesn't, so testing only against the release before would miss it. *Unconfirmed:* a week. *Not built.*

Between them, these rules give each pairing this:

| Pairing | An additive change | A break |
|---|---|---|
| Older client, newer hub | Works. The client ignores what it doesn't know | The hub speaks the client's version until its next break |
| Newer client, older hub | Works. The client hides what the hub refuses | The client says the hub is too old. The desktop app replaces a local hub it started, through `hub_status` and `hub_shutdown`, as "Managing a hub" says |
| Newer hub, older worker | Works. The hub does without what the worker refuses, and replaces the worker with its own build once the worker's workspace is idle | The hub speaks the worker's version, and replaces the worker with its own build once the worker's workspace is idle, so updating a hub never stops an agent, as long as it crosses one break at a time, as the app's update does |
| Older hub, newer worker, after a rollback | Works, and the hub replaces the worker with its own build once the worker's workspace is idle | The hub stops the worker, and its agents with it |

A worker's hello names its build, and a hub that carries on with a worker of another build replaces it once two looks in a row, five seconds apart, find nothing at work in its workspace: no session in a turn, waiting on an approval or with work in the background, no setup script, no terminal open, and no call to the worker that the hub still waits on. Two looks, so a moment with nothing at work, as just before an agent picks up again by itself after its work in the background, isn't taken for the workspace being idle. Whatever starts work records it before it asks for the worker, as a prompt is recorded before it's sent, so once the hub has decided, whatever wants the worker gets none, and waits for the worker of the hub's own build that the next request starts. Each session lets go of its agent before the worker stops it, so the agent's exit changes nothing, even with a prompt just sent, and a chat says nothing of the exit. The next prompt resumes the conversation on the new worker. Each agent's start records the build it runs on, and the build the chat's agent last ran on when that's another, so a chat says it was updated where its agent next starts, however many updates came before then, and a worker started again on the same build says nothing. While the hub carries on with a worker of another build, the workspace's record says which build it is, so every client can say which build its agents are on. A worker the hub starts is always its own build, so that's the only time the two differ, and a starting hub forgets what the last one recorded before it carries on with any. Builds are told apart by their build version, older or newer, so a rollback moves a worker too, and two builds that say `-dev` are taken for one. *Unconfirmed.* On Windows a worker still stops when it loses its hub, as "Providers" says, so a hub there never meets an older worker.

- **Not everything works with everything.** Clients and workers don't carry old versions, and a rollback past a break stops agents, as does replacing a hub across two breaks other than with the app's update, such as a build installed by hand, a hub someone runs themselves, or an update by an app from before updates stepped, which takes the newest. Doing better would put old code in more places, or more versions of it in the hub, for cases that are rare or that updating fixes.
- **The wire format stays as it is.** A schema format such as Protobuf has the same rules for additive changes that serde has with the ones above, and neither helps with a change of meaning, which is what a break is.

## Terminals

- **A workspace's terminals are shells its worker runs,** each in a PTY in the worktree, with the environment the hub gives its agents, such as the workspace's ports, and as with an agent, without a parent Claude session's variables, which a hub started from inside one has, nor what a terminal app it was started from says of itself, such as tmux's, which would make tmux take a terminal here for one inside itself. The shell is the user's own, started as a login shell, as a terminal app starts it, so it reads their profile, and it's told the terminal is `xterm-256color`, which every system knows, and, through `COLORTERM`, that it takes any colour. On Windows it's `cmd.exe`, or whatever `ComSpec` names, which reads no profile. The worker keeps what each shows, from everything its program writes, with `terminal-state`, on Ghostty's terminal core, and a client keeps its own copy the same way to draw it. *Unconfirmed.*
- **The worker's copy answers what the program asks of its terminal,** such as where the cursor is or what the terminal is, so each question is answered once, whether several clients are attached or none, and a shell that asks as it starts doesn't wait on a client. A client's copy answers nothing. *Unconfirmed.*
- **A terminal's record is the hub's, kept in memory rather than stored,** since its shell lasts only as long as its worker, and a stored record of one whose worker is gone would only go stale. A client opens one with an ID it chose, and the hub announces its record on the feed, with a revision from the counter every record's comes from, so clients keep it as they keep the rest. Since no transaction holds it, a terminal's record changes and takes its revision under a lock that listing the records takes too, so a list has every terminal its revision takes in. A hub that starts with workers it carries on with asks each for its terminals, as it asks for its agents, and announces them again. *Unconfirmed.*
- **Attaching is a subscription to a terminal's updates.** First comes a screen: the bytes that make a fresh terminal of its size show what the worker's does, with its history, colours, cursor and modes, and the part of a sequence its program stopped partway through. Then come what the program writes, new sizes and the shell's end, in order. The worker numbers each update, and says how many a screen takes in, so the hub sends a client only what comes after its screen, whichever reaches the hub first. Every update counts, not only output, so a new size the screen already has isn't sent after it again. A client that falls too far behind gets a new screen rather than every byte, so nothing queues for it without limit, as the Live kind above says. *Unconfirmed.*
- **client-core keeps a client's copy of a terminal on the thread it follows the terminal on,** since Ghostty's terminal can't leave the thread that makes it. The thread takes in what comes, does what a view gives it, such as keys, which it turns into what's typed by the modes the program set, and builds the view a plain copy of what it shows, from the rows that changed, once the view has taken the last one, so frames never queue, and nothing is held for a view that isn't drawing. It does what a view gives it while there's no connection too, so the history scrolls, and drops what that would send the hub. A terminal whose record has gone has ended, though its end may have come while there was no connection to hear it. *Unconfirmed.*
- **A view paints the frames client-core builds of its terminal,** as `docs/performance.md` says, and gives client-core's copy the keys, pastes, turns of the wheel and what the pointer does that it takes, and the room it has, and asks it for what's selected, to copy. *Unconfirmed.*
- **A client takes its terminal to the size its view has room for,** as the view is laid out and each time it attaches, but keeps a size another client gave it until the view's room changes, so two clients showing one terminal don't take it from each other on every update. *Unconfirmed.*
- **A key is turned into what the program reads on the client,** since what it reads depends on the modes the program set, which the client's copy knows. Every key is the program's but the app's on Command on a Mac and on Ctrl-Shift elsewhere, and Ctrl-Tab and Ctrl-Shift-Tab on both, which terminal apps keep for themselves, as Ghostty does. So copy, paste and select all are Command's on a Mac and Ctrl-Shift's elsewhere, and off the Mac the app leaves its other shortcuts out of a terminal, as `keys.rs` does and `docs/spec/menus.md` says. Option types a character, as in other Mac apps and in Ghostty by default. The keys Ghostty gives a meaning on a Mac, Command with Left, Right or Backspace, and Option with Left or Right, send the text that means, such as Control-A for the start of the line, as it is, whatever the modes, as Ghostty does. The wheel scrolls through the history, or is sent to a full-screen program as arrow keys, as terminal apps do, unless the program asked for the mouse, when it's sent nothing. A paste has Escape, Backspace, Delete and the control characters a terminal acts on, such as Control-C, swapped for spaces, as xterm does, so it can't end its own marks early or stop the program, and is marked as pasted for a program that asks. Unmarked, each line ends as Return does, so a shell runs it. *Unconfirmed.*
- **What's selected in a terminal is the client's,** as per-device state is, so none of it reaches the hub. The client's copy keeps it, as Ghostty's own selection, which stays on the same text as the terminal scrolls, and a new copy, made from a new screen, starts with nothing selected. Copying to the clipboard asks client-core for the text, since only the thread it keeps the copy on can read it. *Unconfirmed.*
- **What's typed is sent once, and in order.** It's the one request that's never safe to send again, since typing twice isn't typing once, so a client drops what's typed while it can't reach the hub, as a terminal over SSH does. - **A terminal has one size, the last a client gave it,** and every client attached is told of each new size in order with the output, so each shows what the program draws for it, whoever resized it. *Unconfirmed.*

Quitting the app doesn't end it, and neither does restarting the hub, since the worker carries on, but stopping the worker does, as archiving the workspace does. On Windows a worker stops with its hub, as "Providers" says, so restarting the hub there ends its terminals. *Unconfirmed:* the shell's end closing it.

A hub's status counts them, as it counts the agents at work, so a client can say what stopping the hub would end. *Unconfirmed:* counting them.

A shell passes the hangup on to the jobs it runs behind, so those end too, but for one started to outlive the terminal, such as with `nohup`, which goes on as it would after a terminal app's window closed. *Unconfirmed.*

A job in front leads a group of its own, and the shell starts one whenever a command is typed, so the worker looks at which is in front once a second, on the terminal's thread, and records it there once another is. On Windows only the shell is recorded, since there's no job in front to ask for. ## The worker's tools

Agents call tools of Roundhouse's own, such as one that says where the workspace's pull request stands, and the hub answers them.

- **The worker serves them over MCP, on 127.0.0.1,** as Streamable HTTP, with each request answered as JSON. Protocol `2026-07-28` offers discovery and, when the client advertises MCP tasks, background waits; `2025-06-18` offers initialization and ordinary tools, for clients such as Codex. A request selects its protocol by its version, without per-client state. Clients that do not offer MCP tasks, such as Codex on `2025-06-18` and Antigravity on `2026-07-28`, receive pull-request lookup without background waits, which need the tasks extension. The CLI reconnects to an HTTP server by itself, and there's no process of its own to die, as `docs/claude-cli.md` says. A server on the CLI's stream ends with the agent's process, and a stdio server that the CLI starts strands what waits on it when it dies. *Unconfirmed.*
- **Only the worker's own agents reach them.** Each request carries a token that the hub gave the agent, which says whose it is, and one without a token of the worker's is refused. So is one sent to another name than the worker's address, or from a web page, which says where it's from, since a page can reach 127.0.0.1 under a name of its own that leads there. *Unconfirmed.*
- **The hub keeps the port each workspace's worker serves on, and each session's token,** so every launch of an agent gets the same, since a resumed CLI picks up a call it left waiting only from the same address with the same token. A worker the hub starts again listens on the port its workspace's was on, whose connections can still be closing, so it reuses the port unless something else answers there, and listens on another if it can't have it. Neither is on a record, since no client is shown them. *Unconfirmed.*
- **The adapter gives the CLI its tools without putting their token on the command line.** Codex and Antigravity receive their URL and authorization header over stdin when starting or resuming a conversation. Claude receives a file of the run's own through `--mcp-config`. Claude's file is in the worker's state directory rather than the worktree, where the agent and git would see it, and on Unix only its user can read it. It goes once the agent exits, or with the records of a killed worker's agents. An agent whose file can't be written, or whose worker doesn't serve the tools, goes without them. *Unconfirmed.*
- **A worker asks its hub, as well as answering it.** For a tool, it sends an ask, numbered apart from the hub's calls, naming the agent's session, and the hub answers it. The hub knows which workspace a worker is for, so it answers only for that workspace's sessions, and a tool reaches that workspace and nothing else unless it's given more. A hub refuses an ask it doesn't know as `Unsupported`, one it can't read as a whole included, as it does a request, and the worker gives up on one with no answer after a minute, or ten for one that makes or removes a worktree, which is all a hub from before asks gives it. A worker that outlives its hub asks each hub that connects whatever is still waiting for an answer, since the last hub may not have heard it, or went before answering, so every ask has to be safe to ask twice, as reading the pull request is. *Unconfirmed.*
- **A wait on pull requests is the hub's.** `wait_for_pull_requests` takes explicit PR numbers in the workspace's repository, expands their open lower native GitHub stack dependencies, and pins the repository and requested numbers. `get_pull_requests` uses the same reader and expansion. The worktree's checked-out branch and unpushed changes do not change an explicit wait. Each call starts independently; retrying the same session and tool-call ID reuses its original wait, with the lookup and insert in one transaction. A fresh read must succeed within forty seconds before a wait starts; invalid inputs and failed starts leave other waits alone.
- **Every watched PR must reach the requested condition, and one blocker ends the wait.** The conditions are effective required checks, all currently reported checks, or merged. Required checks come from the stack's trunk, including active rules and classic protection; missing required checks remain pending. Optional failed checks end an all-checks wait, but not a required-checks wait. Unknown mergeability, requirements or checks do not mean success. A draft permits a checks wait but ends a merge wait. Conflicts, a proven non-linear stack or a required update of the base, closure without merging, a new request for changes and queue rejection end early. Existing reviews and queue removals are baselined by GitHub's timestamps. A known queue entry takes precedence over transient conflicts; entering it is not merging.
- **Observations are bound to remote revisions.** Every connection is paged before evaluation; reported checks name the head or its current test-merge commit. Heads, bases and stack topology are re-read before accepting a snapshot. New pushes replace observations. Main advancing alone does not end a wait. Expected retargeting after a lower PR merges continues; inserting, reordering or replacing a lower dependency, or changing the destination, ends as `stack_changed`. An upper PR added above a requested target never broadens its scope. Endings and their diagnostic snapshots are written together, and cancellation wins over a late read.
- **A workspace's waits are read with its own pull request, and overlapping waits share an ask.** Each connected group of overlapping scopes within a workspace and pinned repository is one ask of the workspace's read, and the workspace's own pull request goes in the ask of the group that has it, or else in one of its own. So the bar and every wait on a pull request go by one reading of it, and a wait's stack is always read from one moment, since a reading of part of it can't tell a lower pull request merging from one leaving the stack. A workspace with a wait is read even without a client connected, normally every two minutes, however long it has come back the same, and one whose own pull request or waits couldn't be read waits longer each time, up to thirty minutes. Every workspace due as one token, the default account's or a provider's machines' own, is read in one read, a job of its own, as "When a process dies" says, across workspaces and repositories, so a hundred workspaces' waits cost a few queries a round. A token whose read hangs holds up no other token's, and a read that doesn't finish in time counts as a temporary failure of each of its workspaces' waits. Disjoint scopes are separate asks, so a pull request that can't be read fails only the waits that watch it. A read superseded by a changed revision keeps the normal cadence instead of increasing outage backoff. Schedules are recreated on restart with every workspace due; persisted waits and deadlines are unchanged. A read doesn't start while GitHub last said its token's limit is down to the final fifth, and stops asking once an answer says so. Temporary failures keep the last successful observation and expose the error and attempt time. A token that can't be had or that GitHub refuses, and a default that blocks, are temporary, since `gh` can log in again and the default can change: a machine's own token that was handed as none, or refused, is asked of the workspace's worker again at the next read. Lost access to the repository or pull request ends as unavailable. An optional absolute deadline is persisted, with no default, and a separate timer expires it even during a stalled read or a spent limit. Closing a chat or archiving its workspace cancels all its waits. *Unconfirmed:* the two-minute cadence and backoff ceiling, reading by token, a token's trouble being temporary, and reading waits with their workspace's own pull request.

A wait that ended as it started is answered at once, with no task. A chat's record shows every wait it has open, as the hub keeps it, so a client shows a wait from that rather than from the CLI's list of its tasks, which still lists one that has ended until it next asks. A chat whose turn had ended with only a wait in the background stays at work in the background across a restart, with the wait still listed and its queue not held. A hub that restarts or dies leaves its agent running, as it does every agent, so the next hub carries on with it, and its CLI goes on asking after the task. One whose agent has gone as the next hub starts, since the last hub stopped, as `roundhouse hub stop` stops it, or went with its workers, as when the machine goes down, isn't marked interrupted, since nothing it was doing was cut off. When a wait ends with its agent not running, in a chat that's idle or at work only in the background, with its queue not held, the hub starts the agent, and the workspace's worker with it if none is running, and its CLI, which lists its tasks again, asks after the task and starts a turn by itself to say how it ended. A chat that was cut off, or is held for the person, hears with their next prompt, since its CLI lists its tasks again then too. Archiving a workspace calls off its waits before its archive script runs, so none ending meanwhile starts an agent in a worktree that's going. *Unconfirmed:* starting the agent without asking. The Claude adapter tells a wait's task from the agent's other work in the background by how the CLI describes it, as the tool that started it, `roundhouse/wait_for_pull_requests`, or the singular `wait_for_pull_request` that older workers served, whose task a CLI resumed from before can still list, which the list says each time, so it does after a `--resume` too, when the call was another process's. ## The worker's git credential

Agents push and open pull requests with whatever git and `gh` find, so the hub sets what every process a worker starts uses for github.com, from the default GitHub account, rather than leave it to each machine's own login.

- **It's worker state the hub sets on each worker's link, with `GitCredentialSet`,** not a field of each launch, since a workspace's worker needs it without any launch, for its clones and fetches, its reads of pull requests and its scripts, and a token that ends has to be renewed under an agent that's running.
- **The hub works out what every worker is sent in one place, from its own state, under the GitHub logins' lock, as each change to them is made:** the machine's own while the default is, the default's username and token, read from its file, a sign-in's access token as a token's, while its login can be used, with its commit identity, and otherwise a block, whose reason says why and what to do in Settings: renew the account, connect it again, sign in with GitHub again, or choose another default. So connecting, renewing or disconnecting the default, a sign-in approved as it or making it, the hub renewing its sign-in's token, or asking GitHub again who it is, choosing another, and the default's token ending each change what every worker is sent. A default that's an app's installation is sent as `x-access-token`, with the app's bot as its commit identity, as below, and blocks once its token ends, saying the hub is making the next, and once it's uninstalled there, saying to install the app again. A default that's a sign-in's blocks once its access token ends, saying the hub is renewing it while what renews it hasn't ended, as after a Mac wakes from a sleep past the token's end, until a check renews it, and once it needs signing in again, saying to sign in again. A default whose record or file the hub can't read blocks too, never the machine's own in its place, and so does one whose file is in a form only a newer build reads, as "GitHub accounts" in "State ownership" says. *Unconfirmed:* a default the hub can't read blocking.
- **The hub sends it as each link opens, queued right behind the hello, before the hello's answer, and waits for the set's answer before the link is used,** so nothing reaches the worker before it, not even what answers the worker's first ask, which can come with the hello's answer. After that, each link follows it on a task of its own, through a `watch` that every change writes under the lock, and sends each it sees once the worker has answered the last, so each link gets the sets in the order they were made, a slow worker holds up only its own link, and one that's applying a set when two changes come is sent only the newer after it. Nothing is sent to a worker under the lock, and nothing that changes the logins waits on a worker. *Unconfirmed:* the `watch`, and queueing the set before the hello's answer, which a worker whose hello then fails is sent too.
- **A worker has ten seconds to answer each set, and one that doesn't, or that answers anything but `Unsupported` or `Unavailable`, is ended, as one that doesn't answer its hello is,** so it can't go on pushing as a default that's since been disconnected. As when any worker goes, its sessions are told, and the next worker started there is sent the credential as its link opens. One that answers `Unsupported`, as a worker from before `GitCredentialSet` does, is said in the hub's log once a link, one that answers `Unavailable` each time, with why, and both are used on, with the machine's own.
- **The hub checks the GitHub logins by the wall clock, as it starts and every minute after: whether the default's token has ended, and which sign-ins to renew,** rather than waiting until a token's end, since tokio's timers don't count the time a Mac sleeps, so a wait would come late by as long as the Mac slept. So a token's end reaches every worker within a minute of it, or of the Mac waking, and a sign-in slept past its token's end is renewed then. Each check also makes the next token of each app's installation that's due, looks for where each app is installed, and asks GitHub who each token's and sign-in's account is that it last asked a day before or more, or never, all at once with its renewals, as "GitHub accounts" in "State ownership" says. Each check waits for the renewals it starts, each within the call's time limit, before the next, as "GitHub accounts" in "State ownership" says. *Unconfirmed:* once a minute.
- **The worker applies each set on its connection's own loop, as it handles a hello and a stop, before it reads the next frame,** so sets apply in the order sent, a link's last applies before the worker serves the next link, and what's asked after a set is answered has it.
- **It's the machine's own, an account, or a block.** Under the machine's own, the worker writes nothing that changes what git or `gh` use. An account is a username and a token, and a commit identity, a name and an email, which the git config sets as git's own in a repository on github.com, so `git commit` works there on a clean machine or VM with no git config of its own, and commits are by that GitHub account rather than whoever the machine's own git config says. ## When a process dies

Any process can die at any point, so nothing depends on a clean exit. Whatever survives works out what happened from the records.

- **A hub is a separate process that outlives its clients,** so closing the app doesn't stop its agents. A client connects, or starts a hub if there's none, and a lock keeps each data directory to one hub.
- **A hub stops writing its database before it lets go of its lock, and lets go of the lock before its connections close.** A client that asked it to stop starts the next hub once its connection closes, and that hub can take the lock at once, then copy the database and migrate it, while what the last one started can run on for up to a second, until its process exits. A write it asks for then is never made. *Unconfirmed.*
- **A prompt is recorded before anything else is tried,** and the client gets its reply at that point. Later failures go in the log, where every client can see them.
- **A client that quits finishes sending what it was asked to do first, and briefly waits for the replies.** The hub carries out each request it receives on its own, so one received runs to the end whether or not its client is still there, and a prompt sent just before quitting is still recorded. The app waits at most GPUI's 200 ms. *Unconfirmed.*
- **A hub that starts connects again to the workers the last one left running, and cleans up after the rest.** Each worker says which agents it's running and what they're doing, and sends what it kept while there was no hub, so their sessions carry on as they were, with their open approvals and the prompts they haven't taken, and so do agents that were idle. Each says which terminals it runs too, which keeps it as an agent does, and their records come back, as "Terminals" says. Only a session whose worker has gone has its open approvals closed, and is marked `Interrupted`. So is one whose worker can't be reached, such as one that's stopping, and the hub ends that worker and its agents, as it does a worker that nothing carries on with. But one whose only work was a wait, which is the hub's, is still at work in the background, as "The worker's tools" says. It does this before it serves, so no client finds a session half carried on, and gives each provider five seconds to list its instances and to say how to reach each worker, so a slow one can't keep every client waiting. The hub also fails setups that were cut off, and discards half-made workspaces. A workspace it was archiving or restoring stays recorded as that until the hub is serving, and its worker is kept, even with no session to carry on with. Then the hub asks that worker whether the worktree is there, and records the workspace as ready if it is and archived if it isn't, whichever it was doing. The worker answers once it has finished any removing or putting back it was still doing, which is why it has to be the same worker. If it can't say, the workspace goes back as it was before. An archived workspace's worker is then stopped. *Unconfirmed:* five seconds, ending a worker that nothing carries on with, and settling such a workspace from its worktree once the hub is serving. *Not built:* on Windows, where workers exit with their hub, it treats every active session as one whose worker has gone. Once it's serving, it destroys the instances the last run was making or destroying, and keeps the record of one it can't, for the next start.
- **A worker keeps its agents running when it loses its hub, and keeps what they say until a hub has it.** A local hub restarts for every update, and a remote worker's hub can be away for as long as its Mac sleeps. The worker numbers what it sends, and its hub says what it has recorded, so nothing is lost, and the next hub drops what it's sent again that it has, so nothing is recorded twice. A hub says so as it goes, once each session has recorded what went to it, with one answer for whatever came while it last said so, and again as it leaves the worker for the next hub, when it waits for the worker to answer that it has let go of it, so the next hub isn't sent it again. - **A worker also keeps what each agent is still writing, for the next hub.** A delta isn't recorded, so it isn't kept, but the tail the deltas so far make is, with the subagents the agent runs in the background and its compaction under way, whether or not a hub was there to be sent them, and it goes once nothing is being written. ## Managing a hub

Who starts, updates and stops a hub is a separate role from the hub itself, and what fills it depends on where the hub runs. The app replaces an older local hub as soon as it finds one, when it connects or while it stays open. It asks the hub to restart, which leaves its workers running for the next hub to connect to again, so that stops nothing, and the hub restarts once no setup script is running. A hub from before agents could outlive it refuses the restart, as it does any request it doesn't know, and since stopping one of those stops its agents, the app replaces it only once nothing is running on it. So does a hub on Windows, whose workers stop with it, as "Providers" says, and whose status says so. With a setup script running, the app goes on using the hub until it has gone, and then connects to the next one. *Unconfirmed.* An agent whose only work is waits on its pull request doesn't count, since the next hub keeps the waits and starts it again once one ends, as "The worker's tools" says. For a hub that waits for its agents, the hub has the last word on whether nothing is running: the app asks it to stop only if that cuts nothing off, which is nothing running and no request but its own under way, whoever else is connected, since another client only connects again, and the hub decides as it stops, because a prompt can be sent between the app seeing it idle and stopping it. A hub that's busy after all refuses and carries on. One from before hubs could decide is stopped on what it last said was running.

| | Local hub started on demand | A hub you run yourself, here or on a server | Hosted, if one is ever run |
|---|---|---|---|
| **Starts it** | Whichever client needs it | You, systemd or Docker | The service |
| **Updates it** | The desktop app, as soon as it has updated. *Not built:* when nothing is running or when you choose to restart it | You or your package manager | The service |
| **When versions differ** | Keeps working, and the app replaces the hub | Keeps working, and the app says the hub is older | Keeps working |

- **The app takes the newest update whose hub speaks every worker its own hub is running.** A hub speaks no version of the worker protocol older than the one before its own, so an update across two breaks would end every worker from before the first, with its agents, as the hub started. The hub's status says the oldest worker version among the workers it's running, counting its own, which every worker it starts speaks, and the app reads the update feed without each release whose hub doesn't speak that version, as "Updating the app" says. So an update crosses at most one break. Right after two close together, it's the last release before the second, whose hub speaks both, so it stops nothing, and once no workspace is left on an older worker, it's the newest. The app reads the status as it connects, again whenever fewer workspaces are on a worker of another build, and once an hour while the hub runs older workers, for one that goes without its workspace's record changing, such as one the hub ends as it starts. It looks for an update again at once whenever what it read changes, and older workers to keep than before drop the update that's ready, which may not keep them, so a quit before that look ends nothing. Until it has heard from the hub, and for a hub from before it said, the app takes the hub's workers to be as old as its own build's hub speaks, so it crosses no break. Only a hub the app restarts with its workers running counts, so a hub someone runs themselves, one on Windows, and a paired hub on another machine put no limit on the update. An update never jumps further, even with nothing at work, since the old hub goes on after the app quits, and starts workers of its own build whenever something asks for one, such as an agent whose wait on its pull request ends. *Unconfirmed:* reading the status again as workspaces move, and each hour, and how old the workers are taken to be before the hub says.
- **A hub knows nothing about what manages it.** It offers its status and stops cleanly on `SIGTERM`, which is what systemd and Docker use. There's no desktop mode, and it doesn't exit when the app closes.
- **Stopping a hub stops its agents, and restarting it doesn't.** `roundhouse hub stop` stops each workspace's worker, and the agents it runs, before the hub exits, and says how many agents that stopped, so nothing is left running with no hub to record it. So does `SIGTERM`, since systemd and Docker send it to stop a hub, and can't say whether another is coming. A restart, which the app asks for when it updates, leaves the workers running, and the next hub connects to them again within moments. *Unconfirmed:* that `SIGTERM` stops agents.
- **A client never needs one exact hub version.** It hides or disables what an older hub doesn't support, as "Changing the protocol" describes, and only a real break stops it. This stays as simple as it can, and gets revisited if it turns out complicated.
- **A client only replaces a hub that says it's replaceable.** A hub started on demand reports that in its status, and one you started yourself gets left alone, even on the same Mac. Only the desktop app replaces a hub, and only an older one, so two versions can't keep replacing each other's.
- **Only a local on-demand hub that's older than the client can be restarted from it.** A client's own hub might not be able to open what a newer one has written. The app offers to restart one that's waiting on its agents, so nobody has to wait for it to be idle. A remote mismatch only gets an explanation. Stopping a shared hub is for its admins, not for any client whose version differs.
- **The app ships a default hub, and that's the only link between them.** The hub doesn't depend on the app.
- **`tools/install.sh` copies release binaries into `roundhouse-builds/<version>/`,** and a `current` link names the one to start. Keeping versions gives rollback by moving the link, and past a migration, the database goes back to the copy the hub saved before it, as the README says. A client resolves the link when it starts, so it stays on its version when the link moves, and rebuilding or archiving the worktree it was built in can't touch it. Its hub stays on one build through its own copy, as "Updating the app" says.
- **A package stamps its published version through `ROUNDHOUSE_BUILD`, and an install its commit,** and any other build says `0.1.0-dev`. The app and `roundhouse hub status` show it, and say so when the app and hub differ, because a bug report has to say which code it came from, and the version is the name of what people download. Version `0.1.N` is the Nth commit on `main`, which `git rev-list --reverse main | sed -n Np` prints. With uncommitted changes, the build also says when it was built, so two different builds never show the same. A build script would rebuild the crates above it on every commit, for builds nobody needs to identify.
- **An install or a package also stamps an order through `ROUNDHOUSE_BUILD_NUMBER`:** when its commit was made, or when it was built if it has uncommitted changes. Any other build has no number, so it's never replaced. Replacing only an older hub needs an order, and a commit hash has none. Install time would let installing an older commit replace a newer hub, whose database it might not be able to open, and commit counts disagree across branches. Rolling back keeps its older number, so the app leaves the newer hub alone until it's stopped.
- **Only a binary reads the stamp, and its `main` passes the build down,** so every library compiles the same whatever the stamp, and the next install or package recompiles only the crates its commit changed, and the binaries. A library that read it would be recompiled for every build, with every crate above it. `tools/check-stamp.sh` checks it, in CI's lint job. *Unconfirmed.*

What someone using the app sees during an update is in `docs/spec/updates.md`. Workers outlive their hub, as "When a process dies" says, which lets the app replace a hub without stopping its agents, and "Changing the protocol" says how a hub works with the older workers that leaves it.

### Updating the app

The app is signed and notarized, you download it, and it updates itself as changes land on `main`, so staying current needs no checkout or toolchain. `tools/install.sh` stays the way to install a build of a checkout, as above, for working on Roundhouse.

- **Velopack packages, installs and updates the app.** One tool packages the app and makes its updates for macOS, Windows and Linux, and an update downloads only what changed. Sparkle signs its updates but covers only the Mac, and an updater of our own would have to redo what Velopack does on Windows.
- **The Windows app is an installer you download once, which then updates itself as the Mac app does.** Its binaries are built on Windows, and `vpk` packages them on Linux, which it can for Windows, so the keys stay in the one kind of job that publishes. It has a feed of its own, `releases.win-amd64.json`, in the same bucket and signed with the same key, and jobs of its own, so neither platform's release waits on the other's or fails with it. It installs for one user, in `%LOCALAPPDATA%\Roundhouse`, without an administrator. Nothing signs it, so Windows warns whoever downloads the installer. ARM64 Windows gets the same, built on an ARM64 runner and published under a channel of its own, `win-arm64`. An app looks for updates in the channel it was packaged for, so each gets its own processor's. One packaged while amd64 Windows' channel was `win` still looks there, so each amd64 release also signs `releases.win.json`, offering only its own full package. Such an app takes it as an update, and since that package was made for `win-amd64`, it looks there from then on. *Unconfirmed.*
- **The Linux app is an AppImage, which updates itself as the Mac app does.** It's one file that runs on most distros without installing, and the one package Velopack updates on Linux. Flatpak's sandbox would keep the app from the host's git, shells and agents, which it runs all the time, and a `.deb` or `.rpm` would hand its updates to a package manager. Its binaries are built in Ubuntu 22.04, so they need no glibc newer than 22.04's 2.35, and the app runs there and on every distro since. It can't be wholly static, since GPUI loads the system's Vulkan driver, which is built against the system's glibc. `vpk` packages it on Linux, in jobs of its own, with feeds of its own: `releases.linux-amd64.json` for amd64 and `releases.linux-arm64.json` for ARM64. Velopack moves the new AppImage over the old one, and where this user can't change the folder it's in, asks for an administrator's password through `pkexec`, so the app says it can't update there instead, as "Nothing about updating is a native dialog" in `docs/spec/updates.md` needs. Velopack would keep downloads in `/var/tmp`, which every user on the machine shares, so the app has it keep them in the data directory. *Unconfirmed:* that check, and where downloads go.
- **CI builds, signs and publishes every merge to `main`.** The merge queue has already run the checks on Linux by then.
- **A published build is versioned `0.1.<commits on main>`,** such as `0.1.50`, which is what Velopack orders updates by. It's short and readable, every merge adds one, it leaves 0.2 and 1.0 free to mean something later, and each part fits the 16 bits of a Windows version field. A count can't be the build number, because counts differ across branches, but only `main` publishes, and its history only grows.
- **The update feed is signed, and the app checks the signature before trusting anything in it.** Velopack only checks each package against a checksum in the update feed, so without a signature, whoever controls the host controls the app.
- **The update feed keeps the newest 10 releases, and, for good, the last release before each break in the worker protocol.** Each release's full package says there which versions of the worker protocol its hub speaks, which only the build can say, so `tools/build.sh --package` asks the daemon it has built, with its hidden `worker-versions` command, on the platform it was built for. A hub speaks no worker version older than the one before its own, so the last release before a break is the newest whose hub speaks the workers from before it. That's the release an app steps to while workers that old are at work, so the update ends none of them. The release workflow can pass over a build for a newer one, so a change whose hub doesn't speak the workers of the newest release published for each platform whose apps step waits in the merge queue until it does, which `tools/update-steps` checks, reading each one's feed, for a change to the worker protocol. A Windows hub's workers stop with it, so its apps take the newest, and its feeds aren't checked. Should such a change get past the check, `tools/package/publish.py` refuses it, and each release after it, on a platform without the step, and only reverting it gets that platform publishing again. Velopack reads only the fields it knows, so an app from before stepping reads the feed as before. *Unconfirmed:* the hidden command, and which changes the check runs for.
- **A hub a client starts runs from its own copy for each build, outside the app's install directory.** An update replaces that directory, so a hub running from it would start its next workers from different code, and on Windows Velopack first kills everything running from it, which would stop the hub and its agents. On Linux the AppImage's files are only there while the app runs, which keeps the mount, the variables and the `PATH` entry its launcher left it out of what it starts, the hub included. Velopack's updater is the exception: it runs from inside the mount and finishes after the app quits, so the app lets it hold the mount up. *Unconfirmed.*
- **A client that starts a hub removes the copies nothing runs from anymore,** once they're a day old, but its own build's, since every update leaves one behind. Each process of the daemon marks the file it runs from with a shared lock for as long as it runs, and a copy is removed only under a lock that shuts out the shared one, so a worker that outlived the hub of its build keeps that build's copy. The day is for what marks nothing, a process of a build from before processes marked their files, since a worker outlives as many hubs as its workspace stays at work through. A client that can't start its hub, as when another removed the copy it was about to start, joins the hub that's up if there is one. *Unconfirmed.*
- **On Windows a hub runs from one path whichever build it is, `daemons\Roundhouse Hub.exe`, and its workers from its build's copy.** The firewall gives a program leave to listen by its path, so a hub with a paired device, which listens for it, would be asked about again after every update if it ran from its build's copy. The path is a second name, a hard link, for the build's copy, so the lock that marks one marks the other. The client that starts a hub links its own build's copy under a name of its own, renames that over the path, which Windows allows while a hub runs from what's there, and starts the hub from there. So the path always holds a whole hub, and what it held stays its build's copy. It does so each time, which is only when a hub starts, and removes any link left on the way that nothing runs from, as it does the copies. One that can't falls back to the build's copy, and says why in the hub's log, so the firewall asks that once. Windows goes on giving a program the path it was started from after it's moved, which would be another build's by the time a worker starts, so a hub running from the path starts its workers from its build's copy. Only Windows does this, since a Mac's firewall goes by a program's signature and Linux's by its port. *Unconfirmed.*
- **The copy is named `Roundhouse Hub`,** so that's what its hub and the workers it starts are called wherever a process is named for its file, such as `ps`, Activity Monitor and 1Password's prompt to use an SSH key. The daemon in the app's install directory is still `roundhoused`, and so is one started where it is. The copies of builds from before the name are `roundhoused` too, and are removed the same way. The copy isn't an app that registers itself with macOS, though that would put the app's icon on the prompt too, because 1Password holds back the prompt of an app that isn't in front, as a hub never is, so an agent's push would wait unseen and then fail.
- **On Windows a hub keeps its data in `%LOCALAPPDATA%\roundhouse-data`,** not `roundhouse`. Velopack installs an app in `%LOCALAPPDATA%\<its name>`, with its updater and packages, and Windows ignores case, so the two would be one directory. *Unconfirmed.*
- **The app decides when an update installs,** so an update doesn't interrupt what someone is doing.

## Providers

Every provider has an adapter: a program the hub runs, which makes and ends the provider's instances. The hub talks to it over the provider protocol:

| Operation | Purpose | Required |
|---|---|---|
| `create` | Make an instance, from a base image and at a size where the provider takes them, and place the worker binary in it | Yes |
| `start`, `stop` | Wake and sleep. Stopping also ends anything the worker left behind | Yes |
| `kill` | Like `stop`, without giving a worker that isn't responding time to finish | Yes |
| `connect` | Return the command that opens a byte stream to the worker | Yes |
| `open_preflight` | Return the command that opens a byte stream for preflight in the prospective launch environment | Optional |
| `destroy` | Remove the instance | Yes |
| `list` | Say which instances exist, so a hub that starts finds those that outlived it | Yes |
| Base images | Build one with a repository's script, list them, and delete one | Optional, declared by the provider |
| `snapshot`, `restore` | Preserve or roll back the filesystem | Optional, declared by the provider |

An adapter also tells the hub, unasked, when an instance is about to end or has gone, such as when a cloud takes back a spot instance or a host goes down, rather than leaving the hub to find out when the worker's stream breaks.

- **Workers only need a byte stream.** `connect` answers with a command, and the hub runs it, with its stdin and stdout as the worker's stream. That can be `incus exec`, SSH or anything else, including the adapter's own program where it has to carry the stream itself. The hub dials out, so workers don't need to reach the hub, and an adapter that carries no streams can stop without taking its workers with it.
- **Every worker has a state directory, which its provider names in the command `connect` answers with.** The worker claims the instance there, so it has one worker, and keeps there what has to be outside the worktree, where the agent and git would see it: the record of each agent, setup script and one-off call it runs, the log of the setup and archive scripts, and the files each run's CLI reads. So the daemon's `worker` takes `--state-dir` however it reaches its hub. A local instance is a directory, and is its worker's state directory. *Unconfirmed.*
- **An adapter is a separate program, over stdio.** The hub runs each as one long-lived child, beside itself, and starts it again if it stops. Instance operations name their instance. A request to open preflight names the project and the kind of agent. The provider can relay the stream using its own transport. The hub and the process at the other end speak the preflight protocol. Both are safe to repeat after a restart. Adapters can be written in any language without rebuilding the app, and one written in Rust implements the `Provider` trait and has `providers` serve it. A gRPC API may come later, so the contract is defined as messages, independent of the transport.
- **The local provider's adapter is the daemon's own `provider local`,** so it ships with every hub, and its instances are directories and its workers processes on this machine.
- **A local worker runs on its own, so it can outlive its hub.** The local provider's `connect` answers with the daemon's own `worker --attach`, which connects its stdin and stdout to the worker serving `worker.sock` in its state directory, and first starts that worker if none is serving it. The worker is in a session of its own, so nothing that ends the hub, or the command the hub runs, reaches it. It runs in its state directory, and it and the command name the socket relative to it, since a socket's path can be at most 103 bytes on macOS and a state directory's can be longer. A worker that's stopping removes its socket first, and while it still holds the instance the command fails rather than starting another, since it may be stuck, and the hub ends it, as it ends whatever it finds on an instance it doesn't know of. On Windows, which has no Unix sockets in tokio, a worker still runs on its hub's pipes, so it stops with its hub. *Unconfirmed.*
- **An adapter keeps its own access to where it runs instances,** such as the Incus client's remotes or the usual AWS credentials, so the hub holds no secrets for it. The hub's settings name each provider, the command that runs its adapter, and which one new workspaces go to. *Not built:* until they do, `providers.json` in the hub's data directory names them, and the hub reads it as it starts.
- **Stopping a worker is split between the hub and the adapter.** The hub closes the worker's stream and gives it time to stop its agents, which works the same over any transport. The adapter then ends the instance and anything the worker left behind: for the local provider, the worker's process group and every process recorded in its state directory, such as its agents, each with its group, and for Incus, the VM.
- **A worker always runs its hub's build.** Starting a worker puts the hub's worker binary in the instance first, if it holds a different one, so an instance that slept through an update doesn't wake with an old worker. The only older worker a hub meets is then one that outlived the hub before it, which it replaces once nothing in its workspace is at work, as "Changing the protocol" says. The local provider has no copy to replace, since it starts the hub's own executable. *Unconfirmed.*
- **Providers declare their capabilities,** such as which systems and architectures they run, whether the filesystem survives a stop, and whether they build base images or take snapshots. Persistent instances don't need snapshots to sleep, while ephemeral sandboxes do.
- **Providers also declare their workers' environment at hello, apart from their capabilities:** whether workers share the hub's filesystem (`WorkerFilesystem::Hub` when they do, `Separate` when they don't) and whether a repository's clone survives archiving a workspace (`ClonePersistence::Persistent` on a single host, `Ephemeral` on VMs, sandboxes or a pool of machines). Omitted defaults to `Separate` and `Ephemeral`, so an adapter that doesn't declare one never receives a path on the hub's disk. At workspace creation, the hub settles the workspace's `RepoSource` and `WorkerEnvironment` and records them on the workspace in SQLite (not on the client-facing record), so later launches, terminals, setup, archiving, restoring and child worktrees never contact the adapter or flip between a checkout and a clone if the repository or adapter changes. On `Separate` compute, the hub sends `RepoSource::Clone` with the repository's remote address (never a hub checkout path), sets `CONDUCTOR_IS_LOCAL=0` and omits `CONDUCTOR_ROOT_PATH`. On `Hub` compute, a checkout is used when the repository has one (with `CONDUCTOR_ROOT_PATH` pointing to it) and `RepoSource::Clone` otherwise (omitting `CONDUCTOR_ROOT_PATH`).
- **An archived workspace on ephemeral compute keeps its unpushed commits in a capped hub bundle.** Before removing the worktree and destroying an `Ephemeral` workspace's instance (when its repository source is a `Clone`, never for a hub checkout), `CaptureArchive` captures every local branch and a git bundle of commits not reachable from `origin`'s default branch (`--branches --not refs/remotes/origin/HEAD`), capped at 128 MiB raw (`MAX_ARCHIVED_BUNDLE_BYTES`). Above the cap, archiving refuses with `NeedsForce` (combined with any uncommitted-work losses before touching the worktree) unless forced, in which case the oversized bundle is omitted (`bundle_omitted: true`). The hub writes the raw bundle to `bundles/<workspace_id>.bundle` and hub-owned metadata to `bundles/<workspace_id>.json` atomically before calling `RemoveWorkspace`, closing the worker and destroying the instance, and completes archiving even if `provider.destroy` transiently fails (leaving the instance `Destroying` for startup or restore to finish). Restoring creates a fresh instance (or restores in place if an older build archived the workspace without a bundle and left its instance `Ready`), passes the saved payload in `RestoreWorkspace` so the worker ensures a bare clone exists, unbundles the commits, creates missing branch refs without overwriting existing ones (falling back to `origin/<branch>` or `origin/HEAD` if an oversized bundle was omitted) and checks out the worktree, and deletes both files once `Ready` is committed in SQLite. On hub startup, each interrupted ephemeral move settles its own unfinished instance (`Creating` or `Destroying`) without holding up local workspaces, and stale bundles are tidied once moves settle.
- **A remote workspace runs in a VM of its own, made from its repository's newest base image, and destroyed when it's archived.** A VM is as flexible as a real machine: an agent can run containers in it, and the services and kernel features its project needs, which are hard to get from inside a container. It's also a stronger wall between workspaces whose agents run unattended with credentials, and nothing one workspace leaves behind reaches another. A base image is a VM that a script of the repository's own has set up, with its tools installed and its caches warm, so a workspace made from it starts with a warm build rather than a cold one. *Not built.*
- **Availability follows the hub.** A hub on an intermittently available machine, such as a Mac, is only reachable while that machine is awake. Agents on remote workers keep running and catch up later. Persistent mobile access needs a hub on an always-on machine.
- **Each workspace gets its own worker process and provider instance,** so a crash in one doesn't touch the others. This matches sandboxes, where each workspace has its own machine. A worker uses about 8 MB, so this is cheap on a Mac.
- **The local provider is inside the hub for now,** which calls it directly, through the `Provider` trait, while it reaches the others through their adapters. The trait has the protocol's requests, one method each, with their rules. `snapshot` and `restore` come with the first provider that uses them.
