# Architecture

How the system fits together, and why. This is the agreed design, so it includes parts that aren't built, and those are marked. Where the code does something simpler for now, this says what.

## Core model

- **A hub owns state and serves the platform API.** It holds workspaces, sessions and event logs. Clients only talk to hubs, and a client can connect to several at once and merge them into one sidebar.
- **A worker does the work.** It runs agents, terminals and git for a workspace, and reports events to its hub.
- **A provider gives a hub somewhere to run workers.** Running on the same Mac is one provider, an Incus instance is another, and a cloud sandbox is another. No provider is special, and **any hub can use any provider**.

## Where a hub can run

All of these are the same code and the same API. A workspace belongs to one hub.

| Hub | Runs on | Serves | Storage | Auth |
|---|---|---|---|---|
| **Local** | A Mac | One person | SQLite | A Unix socket only this user can open. The relay path needs its own |
| **Self-hosted** | Your own server | You or your team | SQLite, Postgres if it grows | Accounts or tokens |
| **Hosted**, if one is ever run | A shared service | Many users | Postgres | Accounts |

Any of them can use any provider. A hub is only reachable while its machine is awake, so persistent mobile access needs an always-on hub.

A local hub keeps its Mac awake while it has work, which `docs/spec/chats.md` defines, unless its settings say not to. It runs macOS's `caffeinate` for as long as there's any, starts it again if something else stops it, and has it stop when the hub does, so a hub that's killed can't leave the Mac awake. The hub does this rather than a worker or the app, because it outlives the app, knows what every session is doing, and sends queued prompts itself. A worker on another machine keeps its own awake. *Not built.*

## Platform API

The hub serves this API to the desktop app, mobile app, CLI and automation:

- **Workspaces:** create, list, archive and restore.
- **Sessions:** read history by range, list their prompts, subscribe to new events, send prompts and approvals, and cancel.
- **Per-workspace data:** diff comments, unread, pinned and drafts.
- **Live access:** attach to a terminal, and get diffs, git status, PR status and images in the worktree. The hub fetches or proxies these from the worker.

The hub doesn't do the work itself. When a workspace is created, it records it and tells a worker to create the worktree and start the agent. The worker reports events back, and the hub saves them and passes them to clients.

## Alternatives considered

- **The same full daemon everywhere,** with each sandbox owning its log and the control plane holding a copy. Simpler to start, but it means two copies of each cloud log and a second read path for sleeping sandboxes.
- **Separate local and cloud paths.** It would duplicate features.
- **Everything through a central sync engine.** It would break offline use and keeping local data on the device.
- **An off-the-shelf sync engine,** such as PowerSync, Electric or Turso's sync. They solve merging writes from clients that work offline, which a hub that's the only writer doesn't need. They need Postgres or copy a whole database to each client, and none covers a window of a log or a tail that isn't stored, while "Keeping clients in sync" needs only a revision and a few rules. Clients that write while offline would be the reason to look again.
- **CRDTs for session history.** They suit many people typing in one buffer, which isn't this product. Long sessions are remote, so clients read a log by range instead, and never hold a whole transcript.

## Dependency rules

```
apps/desktop ──> transcript, terminal-view ──> client-core ──> protocol
apps/desktop, transcript ──> look
apps/cli ─────────────────────────────────────> client-core
apps/daemon ──> hub ──> protocol
apps/daemon ──> providers ──> protocol
apps/daemon ──> worker ──> agents ──> protocol
apps/daemon ──> agents, for their descriptions
agents, providers, worker, client-core, apps/daemon ──> process
```

1. **Clients only talk to hubs.** They never touch git, terminals or agents directly. The hub fetches or proxies live data from the worker.
2. **`protocol` has no IO and no UI.** Everything depends on it, so it needs to stay small and stable.
3. **The hub and worker must build on Linux without GPUI.** Nothing under `hub`, `worker`, `agents` or `providers` may depend on GPUI or gpui-kit.
4. **GPUI stays in `transcript`, `terminal-view`, `look` and `apps/`.** `client-core` must stay free of it, and of any async runtime: it's blocking calls and channels, so GPUI's executor stays out, and a native mobile client remains possible if the GPUI path fails. `look` is a crate of its own because both the app and `transcript` draw with it, and `transcript` can't depend on the app. For the same reason it names the parts of the window tests find by where they're drawn, as `look::Region`, since both mark some. *Unconfirmed.*
5. **The worker and provider boundaries are real.** Even on a Mac, the worker runs as a separate process, so remote workers only change the transport. The hub reaches the local provider the way it reaches any other, through the provider protocol, to an adapter in a process of its own, so the protocol is used by every workspace and a new provider is only a new adapter. *Not built:* the hub depends on `providers`, and runs the local provider inside itself.
6. **Exact pins for GPUI and gpui-kit.** They are pre-1.0, so upgrades should be deliberate and in one place.
7. **Nothing that ships is under GPL, AGPL or LGPL.** MPL-2.0 is allowed when it comes unchanged from crates.io, and everything else is permissive, such as Apache-2.0 or MIT. GPL or AGPL code would put the whole app under its terms, which would decide the project's own license and rule out closed or hosted versions, and GPL is widely seen as incompatible with the App Store. AGPL also reaches the hub over the network. LGPL expects users to be able to relink, which static linking makes awkward. MPL-2.0 only covers its own files (§3.3), and shipping it unchanged only means saying where its source is (§3.2), which goes in the notices every license needs anyway. A changed copy would have to be published, hence crates.io only. The one exception is the AppImage runtime, the program Velopack puts at the front of the Linux app, which mounts the app's files and starts it, and which has libfuse, under LGPL-2.1, built in. Every AppImage runtime uses FUSE, and an AppImage is the only package Velopack updates on Linux. The runtime is a program of its own, MIT and unchanged from upstream, so the LGPL covers only it, and nothing of ours links libfuse. Meeting it means the notices saying where the runtime's and libfuse's sources are.

`tools/policy/tests/policy.rs` checks rules 1 to 4 and 7 against the real dependency graph, so `cargo test` fails if a new dependency breaks one. The license check covers what actually ships on each platform, not everything in `Cargo.lock`, with one gap. The Mac app also ships `UpdateMac`, the updater Velopack builds from its own Rust and ships prebuilt, so the crates in it aren't in `Cargo.lock` and the check can't see them. The same goes for the `Update.exe` and the installer it ships for Windows, and for `UpdateNix` and the AppImage runtime it ships for Linux. Velopack itself is MIT.

Someone else's files kept in the repo rather than taken as a crate, such as the desktop app's file icons, aren't in the dependency graph either, so the policy tests list each such folder with its license, and check that its license file says so, and that every license file in the repo is in a folder on the list, apart from those in hidden folders and in folders `.gitignore` leaves out, such as `node_modules`. *Unconfirmed.*

### Layers

Dependencies point inward, from handlers to operations to stores and integrations. A layer answers with a lower layer's type wherever it means the same, rather than copying it.

| Layer | What it does | Here |
|---|---|---|
| Handlers | Parse a request, call one operation, map its result | `hub::server`, `worker::serve` |
| Operations | One module per area, holding its logic | `hub` |
| Stores | All SQL, inline: a few dozen statements, with nothing to check them at compile time | `hub::store` |
| Integrations | One module per outside system. Nothing else knows its flags, wire format or retries | `agents::claude`, `worker::git`, `hub::worker_link`, `providers::local` |
| Edges | Configuration and telemetry, read from the environment and passed down | `main` in each app |

Errors follow the layers:

- **Hub and worker operations return `protocol::client::ApiError`,** the error both protocols carry. Its `ErrorCode` is a closed set of meanings, such as `NotFound` and `Conflict`, not a transport status, so a second enum mapping onto it would only be a copy. Callers and tests match `code`, and `message` is for people. A condition callers must tell apart gets a new `ErrorCode`.
- **`hub::store` has its own enum,** because `ApiError` holds only text, and using it at the bottom would throw away the SQLite error.
- **Lower errors become `ApiError` in one place per crate,** an `impl From<…> for ApiError`, so the mapping reads as one table. `Internal` failures get logged there, with their source.

## State ownership

Each piece of state has one owner, and every other copy is a cache.

**What every client shows alike is the hub's, recorded rather than worked out or fetched live.** The test: should a second client, or this one after a restart, show the same thing? Then the hub owns it, and a client only draws it. A client keeps or works something out only when it's about its own device, as the table says. A fix that finds a client doing more than that moves the state to the hub, even when that's the bigger change. A protocol change is the normal way to do it, and "Changing the protocol" says how to make one, mostly without a version bump.

| State | Examples | Owner |
|---|---|---|
| Session history | Agent events, prompts, approvals | The workspace's hub |
| Workspace records | Branch, status, notes, diff comments | The workspace's hub |
| Per-user workspace state | Unread, pinned, drafts | The workspace's hub, stored per user. One a hub too old to keep drafts refuses waits for the next connection, which may be to one that does. It keeps an answer being typed, a comment being written, and what's in the new-workspace dialog with its files, the same way, each apart, and a hub that keeps chats' drafts but not those refuses only them, so the rest goes on. A client shows a chat's draft as the feed tells of it changing elsewhere, unless one of its own for the chat is still on its way, which then replaces it. client-core keeps the last copy of what's in each place that the client and the hub agree on, a chat's draft, an answer, a comment or the new-workspace dialog, the one the hub gave back as it kept the client's or one the client took, so a record is a change from elsewhere only when it's newer and what it says is there isn't that copy, whatever else on it changed. Once its own has arrived, the client looks again. *Unconfirmed:* that thread, the count, the wait, the copy agreed on, that a draft on its way replaces one made elsewhere, and that a hub that keeps chats' drafts but not answers, comments or the dialog refuses only those. The dialog's copy goes with the connection, since the dialog is the same place on every hub. *Not built:* a local hub has one user, so how far a session is read, and what's typed and attached in its composer, are kept on the session. The app has no pinned yet. What's in the new-workspace dialog is one record of each hub's, since one person writes one at a time, kept by the hub a client would make the workspace on, the one it's connected to. The hub lets go of one nothing has named for a day too, such as one a client took out without the hub hearing, counting the day again as a workspace is made from it, and of bytes with no file as it starts. *Unconfirmed:* that record, that it keeps the repository, model, effort and plan mode as well as what's typed and attached, that the hub makes the workspace and gives the new chat the files, that it empties the dialog only once the chat has the prompt, and the day. A hub too old to make it so is sent it a step at a time, by a client that reads back the files it keeps for the dialog and sends them itself. A client keeps and shows it as it does a chat's draft, and reads back its files. *Unconfirmed:* that the hub lets go of an answer being typed as its question is answered or cancelled, and of a comment being written as it's saved |
| Instances | Which instances the hub asked each provider for, and whether each is being made, made or being destroyed | The hub, which records each before it asks for it, so it knows which are its own whatever a provider lists, and destroys one that a crash left part way, whether it was being made or destroyed. Whether an instance exists, and whether it's running, is its provider's |
| Live processes | Running agents, terminals, run scripts | The worker |
| Filesystem | Uncommitted files, dependencies, agent session files | The worker's machine, kept across sleep by the provider |

- A session has one writer, so events get a simple sequence number and no merge logic is needed.
- A prompt or approval only becomes real once it's recorded. Until then, the UI shows it as pending.
- **Which approvals the agent is waiting on is on its session's record,** changed in the same transaction as the event that asks or answers one, so a client reads them rather than finding them among the events it has loaded, which can miss one whose answer is in a page it hasn't loaded. What it has loaded after the copy of the record it has says what has changed since, until the feed brings a newer copy. A record from a hub too old to say says nothing rather than none, and a client of that hub finds them among what it has loaded, as before.
- **A workspace is the hub's record from the moment it's asked for.** The hub records it before it fetches and makes the worktree, which can take a while, and announces it then, so every client can show it on its way, in the place it will have, and none has to work out which new workspace is the one it asked for. The hub asks the workspace's worker which names git has: the first part of each branch's name, here and among `origin`'s as last fetched, each remote's name, `HEAD` where there's a remote, and each directory where the repository's workspaces go. The hub counts them whatever their case. A name git has is refused before anything is made, and the next name skips all of them, so the record takes it in place and keeps its ID. Its instance is destroyed and made again under the new name, since a provider's own tools call it by the name it was made with, and it's recorded again first, as any instance is. One that can't be made is removed, which is announced too. *Unconfirmed.*
- **Whether a workspace is being archived or restored is on its record,** from the moment it's asked until it's done, and announced, so every client shows it on its way out or back, wherever it was asked for. The hub records it before anything else, and only one request can, so a second is refused. One that's refused or fails part way, as when archiving would lose work, puts the record back as it was, which is announced too. Meanwhile the workspace isn't ready, so the hub refuses what needs it to be, such as a prompt or a read of its worktree, which is about to go or isn't back yet.
- **A workspace's other worktrees are the hub's records, and their files the worker's.** The hub chooses each one's branch and where it goes, numbering a name that's taken, and the workspace's worker makes it there, refusing a path that isn't a directory of its own in the workspace's folder of `.children/`, and what git can't make. The hub records it as being made before it asks, under the key the worker gave the ask, so a hub that stops meanwhile, or loses the worker before it answers, leaves a record of what may be there. Asked again, the next hub asks the worker for it where it was to be, and the worker answers with what's there on its branch, waiting for an add of it that's under way, rather than making another. A worker waits ten times as long for an ask to make or remove one as for others, since either can take minutes. A record is forgotten when the worker answers that it couldn't make it, and one stays once its worktree is removed, with its branch. Each one's branches are watched as the workspace's own are, and kept on its own record. Whenever the hub has a worker watch the workspace's branches, as when it connects to one again, starts one, or has put the workspace's worktree back, it settles the others' records from what's there, as it settles a workspace left part way through being archived. One recorded as there that has gone is recorded as removed. One being made is recorded as there if the worker has it, on its branch, and forgotten if nothing is there, or the worker says something else is. A worker that can't say what's there settles nothing. Making one waits while one is removed, the records are settled or the workspace is archived, and those wait for any being made, so nothing is removed or forgotten as it's made and left there unrecorded. Archiving records that it's under way first, as it does for every client, and then waits for those, so one asked for meanwhile waits too, and is refused once it can look, as everything that needs a ready workspace is, unless archiving was put back. Then archiving checks every worktree for work it would lose before anything changes, and refuses with all of it, naming each other worktree, so forcing past one's doesn't lose another's untold. It removes the others before the workspace's own, so a hub that stops part way leaves the workspace's own worktree until last, and the next, which settles the workspace from whether that one is there, finds an archived workspace's others gone. One that can't be removed, such as a directory that's no longer a worktree, refuses as work that would be lost does, since forcing goes on past it, as past a failing archive script, and leaves it recorded as there. The worker does one thing at a time to each worktree: making another of the workspace's, removing any, or putting the workspace's own back. Each worktree is apart from the others, so removing one waits for an add of it, and the question of whether one is there waits for either. *Unconfirmed.*
- **The hub keeps what GitHub says of each workspace's pull request on the workspace's record,** read through the workspace's worker within a budget of calls to GitHub. A worker the hub starts only for such a read is stopped once it's done, unless something else has wanted it meanwhile, so workspaces nobody is using don't keep one running each.
- **Which pull request is a branch's is the worker's to judge, and it keeps what it judged as a setting of the branch in the repository's git config,** `branch.<name>.roundhouse-pull-request`, the pull request's URL. `gh` finds one by the branch's name, which is only one repository's, so another computer's branch of the same name can have it. A setting of the branch, rather than a record of the hub's, since git renames and deletes it with the branch, so nothing has to keep it in step, and a branch made again by an old name starts with none, even outside the app. It's written only when it changes, since every worktree of the repository shares the config, and a write takes its lock. *Unconfirmed:* that the commit a branch was made at from another remote branch doesn't count, and that it's written only when it changes.
- **Each worktree's branches are watched by its worker, and the hub keeps the newest on the workspace's record:** which is checked out, and each branch the worktree has had checked out, with its newest commit and where it's pushed. Which it has had is git's own record, the worktree's reflog, so a branch checked out from a terminal counts, and so does one checked out while no worker ran. The list is for showing each branch's own pull request, and what each chat changed, which aren't built. Once git has stopped writing, it runs git to read them, and it reads them every five minutes anyway, since the OS can drop what it says, and some filesystems, such as a network's, don't say. Where the OS's watcher can't be had, `notify`'s own looks at the files every second instead. A workspace is ready with its branches, read as its worktree is made, and a restored one is announced once its worker has read them, so its record says which it's on from the start. The worker sends them whole, so the newest frame replaces every one before it, and the hub takes them only from the worker the workspace has now. The next hub has a worker it carries on with watch them again, since the worker sends only what changes, and what it read while there was no hub went to no one. So agents commit, switch branch and push, and the record says so at once, rather than when a turn ends. A pull request is its branch's, so the hub records which branch each was found on, and reads it again when the worktree checks out another branch, unless a read since found that branch's, and when the branch checked out is pushed to its upstream, though not when it's pulled. Those reads are the agent's doing, so they're spaced out and kept from the last of GitHub's limit, as an agent's own are. One found on another branch than the one checked out isn't the workspace's, so it's read in turn even when it's merged or closed, which a read that failed would otherwise leave. None found on no branch, as where `gh` can't work at all, isn't another branch's, since checking out another changes nothing there. *Unconfirmed.*
- **A chat chooses its model, approval mode and effort, and a running agent has the last word on whether it took them.** Every chat names all three and every launch passes them, so none is left to the agent's CLI. A change goes to a running agent first and is saved only once it agrees, so what's shown is never ahead of what's true. The agent also changes its mode by itself, such as leaving plan mode when its plan is approved, and reports every change of mode, which the hub saves. With no agent running, the hub saves a change at once, and records a change of mode in the log itself, since no agent will. *Unconfirmed:* the hub's record of a change.
- **What each kind of agent is called and offers is its adapter's to say, and reaches clients through the hub.** The `agents` crate writes a description of each kind beside its adapter: what the interface calls it, the models, efforts and approval modes a chat can be given, what a chat runs with until another is chosen, and what it does that not every agent does, such as compacting when asked. It also says what login a hub can hold for the kind, which is the command the person runs to make its token and how long one lasts, since both are facts about the agent's CLI, so neither the hub nor a client matches on the kind for them. The hub doesn't depend on `agents`, so the daemon's `main` passes them in, as it passes in the rest of the hub's configuration. The hub gives a new chat what its kind's description says for whatever the request leaves out, refuses a kind it has no description of, an effort or a mode the agent isn't offered, and a compaction of an agent that doesn't compact when asked, and answers `agent_list` with them, which doesn't change while it runs. So no client keeps a list of what an agent offers, and none keeps what a chat starts with. An agent runs on its worker's machine, from the worker's build, so once a worker can be from another build than its hub, its agents could offer something the hub's descriptions don't say. client-core asks for them on each connection, with the records, and holds them beside them, since they aren't records, and a new chat runs the first kind the hub describes. A hub too old to describe its agents describes none, and a new chat there runs Claude, the only kind such a hub runs. The model picker offers what a chat's agent is offered, and with no description, only the model and effort the chat runs, since a picker can't be hidden and nothing else is known to be one the agent takes. The new-workspace dialog then leaves both to the hub until one is picked, and nothing an agent might not do is offered, such as `Compact now`, so a typed `/compact` goes as a prompt. *Unconfirmed:* that the description says what login a hub can hold.
- **Whether the agent has a prompt is recorded, not worked out.** The hub records a `PromptTaken` or `PromptDropped` for every prompt: the agent's own word, or the hub's where the agent can't say, such as when its worker is lost. So no client has to guess from the rest of the log, and every client shows the same. A chat draws a prompt where the last of those is, since that's where the agent read it, and the hub's list of a chat's prompts says where that is for each, and which of the two it is, so the outline can jump to one whose events aren't loaded, and a chat says whether it was dropped without them. *Unconfirmed.*
- **When the person last did something in a workspace, and in each of its chats, is on their records,** by the hub's clock. A chat's moves when the person sends its agent something: a prompt, as it's sent or queued, or an answer to a question or an approval. A workspace's moves when it's made, when a chat is made in it, and with each of its chats', in the same transaction as the event, the queue or the chat that moves it, and the feed announces each. A queued prompt counts once, as it's queued, so the hub sending it later, with nobody there, doesn't count again, which a client couldn't tell from the log. Every client sorts workspaces by the workspace's, and so agrees, rather than each working it out from whichever chats it has. *Unconfirmed.*
- **Whether the agent went on without a call's result is recorded too.** Nothing an agent sends says so, and telling takes knowing how that agent behaves, which only its adapter does. So the adapter records a `ToolCallDropped`, and a client reads it rather than working it out from what came next. The adapter only sees what came next itself, so a result recorded afterwards stands. *Unconfirmed.*
- **What an approval asks is said by its adapter, not worked out from the agent's tool, and so are the words the agent is told of what the person decided.** Only the adapter knows its agent's tools, so it says of each request whether it asks to use a tool, asks questions, each with its text, its header, the options it offers and whether several can be chosen, or asks to approve a plan, with the plan. The request keeps the tool and its input too, which text is found in, and which a tool's use is drawn from, by the kind of call the request says it is, as "Wire format and event log" says. One recorded before adapters said says nothing of what it asks. A client answers questions by position, the way it keeps an answer being typed: for each question in turn, the options chosen, by their place among its options, and what was typed. The adapter tells the agent in the agent's own form, such as Claude's, which keys each answer by its question's text, and the hub records the answers as they came, so the transcript says what was decided from the questions the request asked. A client that says no sends no words of its own unless the person wrote some, and the adapter tells the agent as fits what was asked: a tool not to be used, a plan to keep working on, or questions the person chose not to answer. The hub and adapters still take answers by text and a refusal's words, which clients from before send, and a client sends them for a request that doesn't say what it asks, since only an adapter from before sends one now. client-core's `Approval` says what a request asks, and makes the decision that answers it in the form its adapter takes, and `Answered` says what the record that closed it keeps of the answers, in either form, so every client reads them the same way. A request from before is read from its tool and input by `client_core::approval::older`, as Claude's adapter sent them then, and that module writes the forms from before too. With `client_core::calls::older`, which reads calls from before, it's the only place a client knows an agent's tools.
- **Which subagent an event is from is recorded, not worked out, and so is what each subagent has done.** The hub records with each event the call that started the subagent it's from, or none for the agent's own, and its place among the events from the same agent or subagent, which has no gaps. A client reads and follows the agent's own events or one subagent's by that place, and recovers as it does by `seq`, so the chat never pages through a subagent's work. The hub also keeps a record of each subagent, changed in the same transaction as the event that changes it: the call that started it, what it's for, what it was asked, whether it's working, when it started and ended, the model its newest reply came from, how many calls it's made, about how many tokens the agent last said its conversation holds, its latest call, its report, and while it works, what it's done lately: its newest few calls, with what came back and what it wrote just before each, the texts cut short, since every change to a record goes to every client. A session's subagents are listed apart from the other records, since a session can have many, and the feed says when one changes. A subagent that never said it ended went with its agent, so the agent's exit ends it. So the chat draws a subagent's call from its record without reading its work, and every client shows the same. The chat follows the agent's own events, and the subagent tab one subagent's. From a hub that can't read by place, the agent's own events are every event, read by `seq`, and there are no records, so the chat gathers each subagent's work into its call from the events it has loaded, as it did before, until a new connection reaches a hub that can. The agent says what a subagent's conversation holds unasked, on a line of its output, which the log keeps anyway, so that's an event, which changes the record as the others do, where what the agent's own context holds is an answer the worker asks for. *Unconfirmed:* the tokens.
- **A compaction is asked of the hub, and what it answers is recorded, not worked out.** A client asks the hub, which records a `CompactionAsked` and passes it on, and the agent's adapter asks the agent in its own way, since that's the agent's to know, such as Claude's `/compact`. The hub refuses one while the agent is on a turn or has a prompt it hasn't taken, since the agent would only compact once that's done, and before the agent has had a turn, since there's nothing to compact. The agent takes it or drops it as it does a prompt. Only the adapter knows which recorded request each line it sent is, and whether the turn that followed did anything else, so it names the request on the compaction, with what it said to keep, and marks the end of a turn that was only that compaction. A client draws each from its own record, rather than searching the events around a prompt for the compaction that answered it. What the hub refuses one on is on the session's record: the prompts the agent has yet to take, a compaction asked for included, and whether it has had a turn, so a client can tell whether one can be asked without asking.
- **What the API's cache holds of a chat's conversation is on its record, and a prompt that found it expired is in its log.** Only the adapter knows its agent's format, so it says of each of the agent's own requests what it read and wrote, for how long, how long ago it was sent, and whether it's the first request for a prompt. The hub times it by its own clock and keeps what the newest left on the session's record, which moves the record's revision. The feed announces it with the turn's end rather than with each request, since a turn makes many, and at once when the agent isn't working. The hub records a `CacheExpired` when the first request for a prompt read less than half of what the request before it left in the cache, since only the hub knows what that was and when it was sent, whichever process sent it. A compaction, or choosing another model, leaves the record with nothing cached. A client works out from the record only how long is left by its own clock, as the working line counts a turn. *Unconfirmed.*
- **A queued prompt belongs to the hub, on its session's record,** so it's sent when a turn ends with no client there, and every client shows the same queue. The hub sends it once the agent is idle and has taken every prompt it was sent, because one sent sooner folds into the turn the agent is about to start. Whether the queue is held is on the record too, so a restart neither sends what the person stopped for nor holds what they didn't, and a starting hub sends any queue left ready. A queued prompt's files are added to the session as it's queued, and the hub keeps them until it's sent, as it does any prompt's. *Unconfirmed.*

## Keeping clients in sync

A client's copy of a hub's state has to stay correct through lag, reconnects and restarts at either end, without each view working out how. Everything a hub serves is one of three kinds, and each kind has one way to tell a newer copy from an older one, and one way to recover.

| Kind | What | Newer or older | Recovering |
|---|---|---|---|
| Log | A session's events, or only the agent's own or one subagent's | By `seq`, or by place among the events from the same agent or subagent, neither of which has gaps | Subscribe again from one past the last `seq` or place |
| Record | Repositories, workspaces, sessions, comments, a hub's settings, the accounts its agents run under, and per-user state, and each session's subagents, which are listed by session | By revision, `rev`, from one counter per hub that moves in the same transaction as the change | List again, and keep whichever copy has the newer revision |
| Live | Output that isn't stored, such as the tail | Nothing to compare. It belongs to one run, and arrives in order on one connection | Replace it with a new snapshot |

- **For logs and records, which copy is newer is decided per item, so the order things arrive in doesn't matter.** A duplicate or an older copy is dropped by its `seq` or revision, so a client doesn't depend on how a list and a feed notice interleave, which a relay or a second connection could change. A list is read in one transaction and carries the revision it was read at, so a record missing from it is gone, unless the client holds a newer copy from the feed. Removing a record is a change like any other, with a revision of its own. A session's newest event isn't announced, so it isn't part of its revision, and the log says how far a session has got.
- **The hub's feed never tells of a copy of a record that's no newer than one it has told of,** so a client hears each record's copies once each, in the order of their revisions, though it doesn't depend on that. Several of the hub's tasks can announce one record, each with a copy read at or after its own change, so two can carry the same copy, or finish in the other order. The feed leaves out a copy no newer than the last it told of that record, or of its removal, and checks and sends under one lock. *Unconfirmed.*
- **A client following one agent or subagent gets only what that one writes, and the tail it leaves.** The hub sends it only that one's deltas, and when another's event ends what that one was writing, as the end of a turn ends a message from a subagent in the foreground, or a subagent's end ends its own, the hub sends it a new tail, since it never sees that event.
- **Only the current run's live output reaches clients.** The hub knows which run it's starting before it launches it, and drops live output from any other, so a replaced agent can't clear or add to its replacement's tail. A replaced run's events are history, so they go in the log as usual, as "When a process dies" says. A run's ID doesn't repeat within its session, even across hub restarts, so this holds once workers outlive their hub. Each event and delta carries its run, and the end of a turn or of an agent clears what its run or an earlier one left open, never a later run's, so a client that sees a replaced run's last events keeps the same tail as the hub. The end of a turn leaves what a subagent in the background is writing, since it carries on after the turn, and the tail says which subagents those are, so a client that joins later keeps the same tail too. The end of the agent clears that as well. A later launch always has a higher run ID.

**Every ID has one allocator, and is unique only within its scope,** so nothing is taken as unique where it might not be.

| ID | Chosen by | Unique within |
|---|---|---|
| Repository, workspace, session, comment | The hub, as a UUID | Everything, so one sidebar can merge several hubs |
| Child worktree | The hub, as a UUID, since a path names a new one once the last there is removed. *Unconfirmed* | Everything |
| Ask key | The worker, for an ask that makes a worktree, as a UUID or the agent's ID for the tool call, so asking each new hub again makes it once. *Unconfirmed.* *Not built* | A session, as a tool use is |
| `seq`, run | The hub | A session |
| Place | The hub | The agent's own events, or one subagent's, in a session |
| Revision | The hub | A hub |
| `client_msg_id` | A client | A session |
| Attachment | A client, or the worker for an image a tool sent back, each as a UUID, so neither takes the other's. *Unconfirmed* | A session |
| Wait | The hub, as a UUID. *Unconfirmed* | Everything |
| `client_request_id` | A client | A hub |
| Subscription | A client | A connection |
| Message, tool use, approval | The agent | A session. Nothing promises an agent won't reuse one elsewhere, so they're never keys outside it |
| Account | The agent's adapter, from the login, and the same in every build, so the hub keeps limits under it across updates. Or the hub, for a login it holds that doesn't say whose it is, which starts with the kind's name too, in a form no adapter's takes. | An agent's kind. Each kind's adapter starts it with the kind's name, so one kind's can't be taken for another's |

- **An item keeps one identity through every state it passes through.** A prompt is its `client_msg_id`, from pending to recorded. A block of the agent's output is its message ID and index, from its first delta to the event that records it. Anything with no identity before it's recorded is its `seq`, and its position in that event. The transcript makes the element IDs of what each item shows from these in one function, so nothing on screen resets when a prompt is recorded or a block finishes. Its buttons belong to one event and never change state, so they're keyed by that event.
- **A command is safe to repeat, and its reply says only what the hub has recorded.** Each request that changes something either has the same effect however often it's applied, such as closing a session, or carries an ID the client chose, as a prompt carries `client_msg_id`. Whatever happens after the reply reaches every client through the log and records, not through the reply. Each request in `protocol::client` says which kind it is. *Not built:* cancelling a turn and running setup again carry no such ID, so sent again later, they act again.
- **A command that ends in a record being removed replies with the record as it last was, and the feed's removal is what says it's gone.** So the reply keeps the form older clients expect, such as a session for closing a chat that's deleted instead, and a client's copy drops the older reply whichever arrives first. Repeating the command, or following the record, is then refused with `NotFound`, which a client takes as the record being gone rather than as a failure to report. *Unconfirmed.*
- **client-core keeps each hub's copy, and views only read it.** For each hub a client is connected to, client-core holds the records and a window of each open session, and does all the subscribing, fetching and recovering, reconnects included. It applies updates as they arrive and tells a view what changed, combining whatever the view hasn't looked at, so a slow view sees the latest state rather than a backlog, and nothing queues without limit. Views keep only per-device state, such as scroll position and selection, keyed by the IDs above, so it survives a reconnect. That way the CLI, the desktop app and a native mobile app make the same guarantees without each implementing them. *Not built:* the desktop app makes the new connection itself, since it knows how to start its hub, and hands it to client-core.
- **client-core sends each chat's prompts in the order they were written.** A prompt takes its place in its chat's line as it's sent or queued, adds its files, and only then waits for the prompts before it, so files upload side by side and a prompt with a large file isn't overtaken by one sent after it. The hub records prompts in the order they reach it, so the order has to be kept before then, and client-core keeps it so every client does. *Unconfirmed.*

## Wire format and event log

Details are in `crates/protocol/`.

- **Newline-delimited JSON over any byte stream,** which is a Unix socket for clients and stdio for workers. It works over anything, it can be read by hand, and agent output is already JSON.
- **Versioning:** both sides say hello first and agree on a protocol version. "Changing the protocol" says how, and what needs a bump, which is rare.
- **`hub_status`, `hub_shutdown` and `hub_restart` work without a hello,** so a client of any version can see a hub, and stop or restart it. That's how `roundhouse hub status`, `roundhouse hub stop` and the app's `Restart the hub` work across a real break, and how the app restarts a hub to update it, and it's why the app can say how many agents would stop. Anyone who can reach the socket is this user. A connection from elsewhere, once there are any, shouldn't get this. *Unconfirmed:* `hub_restart`.
- **On Windows a client's byte stream is a named pipe,** since neither tokio nor stable Rust has Unix sockets there. A pipe has no place in a directory, so it's named for the hub's data directory, one for each, and a checkout's hub stays out of an installed app's reach. The name comes from the path as it's spelled, so the data directory has to be an absolute path there. It has the permissions Windows gives a pipe by default, which let this user, administrators and the system send requests, and anyone else only read. Another user on the machine can make a pipe of that name first, and a client takes it for its hub and sends it prompts, so this isn't safe on a machine with other users. A client checking who serves the pipe would close that. *Unconfirmed.*
- **The database only migrates forward.** Migrations run in order, each in its own transaction, and a database from a newer build is refused rather than damaged.
- **A hub saves a copy of the database before migrating it,** and doesn't start if it can't. Any update can bring a migration without anyone choosing it, and the build before can't open what it leaves. The copies are in `backups/` in the data directory, and each of the last three schema versions copied keeps its newest, so retrying an update that stopped part way can't push out the copy from before it. *Unconfirmed.*
- **Each event has a normalized body, plus the agent's raw line in a separate column.** Agent output is untrusted input, so `agents::claude::normalize` takes any line without panicking. Clients read the normalized form. The raw line means views can be rebuilt if normalization was wrong, and range reads don't load it. An image a tool sent back is the one thing left out of it: the adapter puts the ID of the attachment that keeps the image wherever its base64 was, so a rebuild finds the image among the session's attachments rather than in the line. The CLI sends a read screenshot twice in one line, as about a megabyte, so kept whole, a few dozen reads can outweigh every other line in the database. *Unconfirmed.*
- **The agent's adapter says what kind of call each tool's use is,** such as a command, a read, an edit, a search or handing work to a subagent, since only the adapter knows the agent's tools. It says so on the call, on its result and on a request for approval, and the hub copies it onto a subagent's record of its calls. A client draws kinds of call rather than tools, and needs no agent's names for its tools. It reads each kind's input by the agent's own keys, such as a command's `command`, since the input stays the agent's own: a typed copy beside it would store a write's content twice in every event. Every result an adapter records says a kind, the kind of the call it answers, or that it's unknown when the adapter no longer knows the call, such as one the agent answers after it was started again. Such a result holds what came back alone, with how a command exited beside it rather than in its text. A request for approval says the kind of the call it asks to make, by the kind a tool's use says or by being questions or a plan. So a call, a result or a request with no kind is one recorded before adapters said. It's read by `client_core::calls::older`, from its tool's name and its text as Claude's were then, which nothing recorded since goes through. *Unconfirmed:* which kinds there are, in `protocol::event::CallKind`, their stored form, and a result saying unknown rather than nothing.
- **How full an agent's context is isn't an event.** The worker asks the agent as it works and sends each answer in a frame of its own, with its run, and the hub keeps the newest on the session's record, if it's from the run going and says something new. Only the newest matters, nothing in the log would read it, and the answer it comes from holds much that's personal, so there's no raw line worth keeping. *Unconfirmed.*
- **What an agent hears of its account's limits is an event, and the newest is on the account's record.** The agent was told it as it worked, so it goes in the log, and the hub also keeps the newest by account, which the feed announces whenever what's left or when it resets changes. Claude's CLI says it only once a process, so the worker also asks it while it works, at most every five minutes, and sends the answer in a frame of its own, as it does how full the context is, and the hub keeps it the same way. Hearing the same again isn't a change to the record, though the hub keeps when it was heard, so something heard earlier never replaces it. The line doesn't name the account, so the hub asks the session's worker which account the agent runs under as each launch starts, and keeps who it is on the account's record and which account it is on the session's. So limits are kept and read under one name, and every client sees them as soon as any agent under the account hears them. *Unconfirmed.*
- **Live deltas aren't stored.** The finished message arrives as a durable event and replaces them. A client attaching mid-message gets a snapshot of the streaming tail, then deltas, and `protocol::tail` holds the rules so the hub and clients can't disagree. A worker applies them too, to what its agents are writing, and a hub that connects to it gets a snapshot of that in the same way, as "When a process dies" says. *Unconfirmed.*
- **Subscribers read from the log, and live updates only say that it moved.** A slow client can fall behind and catch up without losing anything, and it holds back only itself.
- **A status change commits in the same transaction as its event,** so a client reading status after an event can't see an older value.
- **Prompts carry an optional `client_msg_id`,** and the same ID is only recorded once, so a client can retry safely after a disconnect.
- **A prompt's files go to the worktree, and the hub keeps only what the transcript draws.** A client adds each file to the session with an ID it chose, then sends the prompt naming them, so a retry sends nothing twice. The prompt's event records each file's name, kind and size. The hub keeps the bytes as files in its data directory rather than in the database, which it copies before every migration. Before the prompt reaches the agent, the worker writes each file into the worktree, and then the hub lets go of every one that isn't an image. A client reads an image with `attachment_read` when it draws one, so the transcript doesn't need the worker, and still has its images after the worktree is archived.
- **A file waiting in a composer is added to its session as it's attached, so the hub keeps it with the chat's draft,** which names it by its ID. The hub leaves out a file it hasn't got, so a client adds each before the draft that names it, on the thread that keeps drafts, and reads them back with `attachment_read` when it next opens the chat. A client names a draft's files only by their IDs, and the hub reads what each is from its own record. Setting a draft never lets go of a file, so emptying it as a prompt is sent can't take a file the prompt is about to carry. A client that takes a file off asks the hub to let go of it after the draft that stopped naming it. Closing a chat lets go of every file its draft named, along with the draft, and the client asks the hub to let go of any of its composer's that reached the hub after. The hub keeps a file anyway while the draft, a prompt waiting in the queue or a prompt that was sent names it, or once it's in the worktree, and it never lets go of an image from the agent, since it records whether a client added each file. A chat closed with nothing sent goes altogether, files and all. One left over otherwise, such as by a client that stopped before it asked, stays with the session. *Unconfirmed.*
- **An image a tool sends the agent is an attachment of the session too,** such as a screenshot it reads, so it's kept, read and drawn the way a prompt's image is, by the same code. The worker gives it an ID, since it's the first to have it, as a client is for a prompt's files, and sends its bytes beside the event whose result names it. The hub keeps them before it records the event, so a client never asks for an image before the hub has it. *Unconfirmed.*
- **An image the agent's text points to in the worktree is kept by the hub, as it was when the text came,** such as `![The board after](docs/screens/board-after.png)`. The worker reads each as the finished message passes through it, and only an image inside the worktree, since what an agent writes is untrusted: it follows every link before checking the file is in the worktree, and refuses anything that isn't an image the transcript draws. It gives each an attachment ID and sends its bytes beside the event, as it does a tool's, up to 128 MB for one event, since an event and what it carries travel in one frame. The text's block names each by the address it was written with, which is what a client looks it up by. So when the agent changes a file and points to it again, each reply keeps what it showed, and every client shows the same, after a restart and after the workspace is archived. One that wasn't there when the text came shows nothing, and so does one in a text recorded before the hub kept them. The agent's line doesn't say which images the worker read, so the event's body is their only record, and a rebuild from the raw lines has to carry them over from it. *Unconfirmed.*
- **A session's prompts are listed on their own, a line each,** with `session_prompt_list`: where each is in the log, and among the agent's own events, the start of its text on one line, and how many files it carries. A client holds only a window of a long session's events, so this is how it can show every prompt to jump to. It asks once, as soon as its subscription has started, and adds each prompt the subscription brings. Between them they miss none, since every prompt before where the subscription starts was recorded before the list was asked for. The list is best effort, since the chat matters more than its outline: a hub too old to list them isn't asked again, and its client shows only the prompts its window holds, and any other failure is reported as a page that fails to load is, and asked again on the next connection, while the chat goes on. Each line also says where the last event to take or drop its prompt is, since a chat draws the prompt there, so the outline can jump to one whose events aren't loaded, and one from a hub that doesn't say leaves the client to find that event in its window. The hub reads only prompts and the events that take or drop them, by their kind, and of each prompt only its place, its text and how many files it carries, so a long session costs no more than its prompts' text does. A chat's rows go by the agent's own events, so its outline puts a prompt at its place among them, or at its `seq` from a hub that can't read them apart, and a client that comes to a hub that can asks for the list again, for its places. A client tidies each line again as it reads it, as it does a title, so a hub that tidies differently can't put a second line, or one that reads backwards, in a row. *Unconfirmed.*
- **A session's compactions are listed the same way, a line each,** with `session_compaction_list`, so a chat's outline can mark every one, however far back. A line is a compaction of the agent's own conversation that compacted, since one that failed changed nothing: where it is in the log and among the agent's own events, who started it, and how many tokens the context went from and to. The hub reads only compactions, by their kind, and leaves out the summary each carries, which is long. A client asks for it as it does the prompts', once its subscription has started, and adds each compaction the subscription brings, but asks for each list on its own, since a hub can be new enough to list prompts and too old to list compactions. A hub too old leaves only the compactions the client's window holds. *Unconfirmed.*
- **Finding text in a long chat starts at the hub, and ends at the client,** with `session_find`: the hub says which of the events a view follows hold the text, the agent's own or one subagent's, by their place among them, as `protocol::find::Needle` matches it, and how far it looked. A client holds only a window of a long session, and only it knows what each event draws. So client-core's search asks the hub, and reads the stretch of those events around each one it named, by place as the log is, a stretch at a time, for a view to count what those rows draw and let go, and a view counts what the rows it holds draw itself, as they load and change, whatever the hub has said. The hub passes over an event's stored JSON when it can't hold the text, and reads the rest, on a read connection of its own, so a long look doesn't hold up the pages every client loads. A chat has one search at the hub at a time, and one typed over by its turn isn't asked, so typing doesn't queue looks through the whole chat. It looks past what Markdown marks text with and how much whitespace there is, so what it names is never less than what a client finds. One character isn't asked, since it's in nearly every event. A hub too old to look isn't asked again until there's a new connection, which may be to a newer one, and the client counts only what it holds. Nor is one followed by `seq`, which only a hub too old to read by place, and so to look, is. *Unconfirmed.*
- **A worktree's files are listed and read through the hub, and only inside the worktree.** All files lists them with `workspace_files`: tracked, new and ignored, with a folder git ignores whole, or that's a repository of its own, a submodule included, listed as a folder, since one such as `target` can hold hundreds of thousands of files, and so is a link that leads to a folder, which git lists as a file. `workspace_folder_read` lists what's directly in such a folder when it's opened, `workspace_file_read` opens a file, and `workspace_file_read_at` opens one as a commit held it, which is how the file tab shows the side of a change the diff was taken from. For the lines a diff leaves out, the diff opens the file as the commit held it with `workspace_file_open_at` instead, and reads it a page of lines at a time with `workspace_file_pages`, which asks for pages with as many lines as the open said, so a page is the same lines whichever build of the worker reads it. A file small enough to send whole comes whole when it's opened, none of its lines cut, and one too big is read as its lines are to show, a line over 16 KB cut short there and saying so. A commit named by its full object ID holds the same file for good, so what's read of it never goes stale. client-core's `OpenFile` opens it, fetches the pages a view wants on a thread of its own and says when they've come, opens it again on a new connection if it couldn't before, and doesn't ask a hub too old to open files again, and its `FileText` holds what's been read and says which pages to fetch, asking for each once. So every client reads a file the same way. The worker keeps nothing between reads: each streams the file from git, keeps only the pages asked for, and stops once it has them, and opening one streams it to its end, to count its lines. Each says in the worker's log how much it streamed and how long it took, so whether the worker should keep an index of the files it opens can be decided from there, as `performance.md` says. *Unconfirmed.* These take a commit only by its full object ID, so it can't be read as an option or name a branch that's moved since, and find the file by its name alone, never as a pattern. The hub passes each to the worker, which takes only a path as a list gives it, relative, with names between single slashes and none of them `.` or `..`. In the worktree, it follows every link before checking the file or folder is in the worktree, as it does for an image, but reads any file there, since a person chose it rather than the agent's text. At a commit, it follows no link, so a link reads as the path it leads to, which is what the commit holds, and nothing outside the commit is read. It lists at most 50,000 files at once, leaving ignored ones out first and then new ones, so a file git tracks is never left out to make room, sends at most 4 MB of text, whole pages of it when it's some of a file's pages, and 64 MB of an image, which it knows by what the file starts with, reading only the start of a file bigger than text's limit to tell, and says when a file is bigger, or is neither, rather than sending it. *Unconfirmed.*

### Changing the protocol

These rules let peers on different versions keep working together. They hold for all three protocols that cross between processes: the client protocol, between clients and a hub, the worker protocol, between a hub and its workers, and the provider protocol, between a hub and its providers' adapters. All three meet the same problem, so one set of rules covers them, and nobody has to remember which applies where. *Not built:* the provider protocol.

- **Each shape has one form.** It's the serde form in `protocol`, on the wire and in the hub's SQLite columns, so changing a type also changes how old rows read.
- **A new field is `Option` or `#[serde(default)]`,** so a message from an older peer still decodes. The same goes for old rows.
- **Every enum read as data has `#[serde(other)] Unknown`:** statuses, kinds, events and blocks. Without it, one new value fails the whole frame, which `client-core` drops, failing the call if it was a reply. Code that receives `Unknown` skips it or shows something neutral. It never panics.
- **Other envelopes have no `Unknown`.** That covers `HubFrame`, `ClientResponse` and the like, since there's nothing sensible to do with one. A client only gets a new response by making a new request.
- **A new request doesn't need a bump, and whoever calls it has to expect a refusal.** A hub, a worker or a provider's adapter answers a request it doesn't know with `ErrorCode::Unsupported`, and carries on. That includes a known request with a value in it the reader doesn't know, since either comes from a newer peer, and its caller handles both the same way. A client checks `is_unsupported()`, and hides or disables whatever needed it. A hub does without it, or passes the refusal on to whoever asked. There's no list of capabilities until something needs one. Each reads a frame's `id` before its request, so it can refuse one it can't read as a whole, once it has checked what it checks of any request, such as that the hello came first. A frame that names no call closes a client's connection. A reply the reader can't read ends the call it was for with an error, rather than leaving it to wait until the connection closes. *Unconfirmed:* refusing a known request with a value the reader doesn't know, and ending the call a reply that can't be read was for.
- **A version bump means a real break,** meaning a change that a peer on the last version can't read under these rules. The rules above cover most changes, so it should be rare.
- **Each protocol has its own version,** so a break in one doesn't break the other.
- **A hello says which versions its side speaks, and both sides use the newest they share.** It names the newest and the oldest, and the reply names the one chosen. A hello that names only one speaks only that one, as a peer from before ranges does, so that peer still gets an answer. A side whose hello is answered with a version it doesn't speak goes no further. *Unconfirmed:* going no further.
- **The hub speaks the current and the previous version of each protocol, and clients, workers and provider adapters speak only their own.** The hub is the one party that meets skew in both directions, since clients only talk to hubs, a worker only to the hub that started it, from that hub's build, as "Providers" says, and a provider adapter only to the hub that runs it. So the code for an old version lives in one place, and only until the next break. *Not built.*
- **A protocol breaks again only once its last break has been out for 30 days.** With the hub speaking the previous version, that means a client or a worker keeps working with any hub built in the 30 days after it, which is a promise people can plan around. It matters most for clients that can't all be updated at once, such as an iPhone app waiting on App Store review, or the apps of everyone sharing a hub.
- **The hellos, `hub_status`, `hub_shutdown`, `hub_restart` and refusals can't change form, even in a real break.** The hellos are how two versions find one they share, and the rest let a client see a hub, and stop or restart it, across a break. `crates/protocol/tests/compatibility/` spells them out, so changing one fails it. *Unconfirmed:* the hellos, and `hub_restart`.
- **A break is tested against the version before it.** The change that makes it keeps the previous version's wire form of each message it changes, spelled out as `crates/protocol/tests/compatibility/` does, and tests that the hub still reads and answers it. CI also runs a hub through a turn with the workers of two older releases: the one before it, and the one published a week before it. A worker lives through every update made while its workspace is at work, and a hub can come to rely on something recent workers send, which a worker from before them doesn't, so testing only against the release before would miss it. *Unconfirmed:* a week. *Not built.*

Between them, these rules give each pairing this:

| Pairing | An additive change | A break |
|---|---|---|
| Older client, newer hub | Works. The client ignores what it doesn't know | The hub speaks the client's version until its next break |
| Newer client, older hub | Works. The client hides what the hub refuses | The client says the hub is too old. The desktop app replaces a local hub it started, through `hub_status` and `hub_shutdown`, as "Managing a hub" says |
| Newer hub, older worker | Works. The hub does without what the worker refuses, and replaces the worker with its own build once the worker's workspace is idle | The hub speaks the worker's version, and replaces the worker with its own build once the worker's workspace is idle, so updating a hub never stops an agent |
| Older hub, newer worker, after a rollback | Works, and the hub replaces the worker with its own build once the worker's workspace is idle | The hub stops the worker, and its agents with it |

A worker's hello names its build, and a hub that carries on with a worker of another build replaces it once two looks in a row, five seconds apart, find nothing at work in its workspace: no session in a turn, waiting on an approval or with work in the background, no setup script, and no call to the worker under way. Two looks, so a moment with nothing at work, as just before an agent picks up again by itself after its work in the background, isn't taken for the workspace being idle. Whatever starts work records it before it asks for the worker, as a prompt is recorded before it's sent, so once the hub has decided, whatever wants the worker gets none, and waits for the worker of the hub's own build that the next request starts. Each session lets go of its agent before the worker stops it, so the agent's exit changes nothing, even with a prompt just sent, and a chat says nothing of the exit. The next prompt resumes the conversation on the new worker. Each agent's start records the build it runs on, and the build the chat's agent last ran on when that's another, so a chat says it was updated where its agent next starts, however many updates came before then, and a worker started again on the same build says nothing. While the hub carries on with a worker of another build, the workspace's record says which build it is, so every client can say which build its agents are on. A worker the hub starts is always its own build, so that's the only time the two differ, and a starting hub forgets what the last one recorded before it carries on with any. Builds are told apart by their build version, older or newer, so a rollback moves a worker too, and two builds that say `-dev` are taken for one. *Unconfirmed.* On Windows a worker still stops when it loses its hub, as "Providers" says, so a hub there never meets an older worker.

- **Not everything works with everything.** Clients and workers don't carry old versions, and a rollback past a break stops agents. Doing better would put old code in more places, for cases that are rare or that updating fixes.
- **The wire format stays as it is.** A schema format such as Protobuf has the same rules for additive changes that serde has with the ones above, and neither helps with a change of meaning, which is what a break is.

## The worker's tools

Agents call tools of Roundhouse's own, such as one that says where the workspace's pull request stands, and the hub answers them.

- **The worker serves them over MCP, on 127.0.0.1,** as protocol `2026-07-28`'s Streamable HTTP, with each request answered as JSON. The CLI reconnects to an HTTP server by itself, and there's no process of its own to die, as `docs/claude-cli.md` says. A server on the CLI's stream ends with the agent's process, and a stdio server that the CLI starts strands what waits on it when it dies. *Unconfirmed.*
- **Only the worker's own agents reach them.** Each request carries a token that the hub gave the agent, which says whose it is, and one without a token of the worker's is refused. So is one sent to another name than the worker's address, or from a web page, which says where it's from, since a page can reach 127.0.0.1 under a name of its own that leads there. *Unconfirmed.*
- **The hub keeps the port each workspace's worker serves on, and each session's token,** so every launch of an agent gets the same, since a resumed CLI picks up a call it left waiting only from the same address with the same token. A worker the hub starts again listens on the port its workspace's was on, whose connections can still be closing, so it reuses the port unless something else answers there, and listens on another if it can't have it. Neither is on a record, since no client is shown them. *Unconfirmed.*
- **An agent's CLI is told of them in a file of the run's own,** given to `--mcp-config`, which keeps the token off the command line, where any process on the machine can read it. It's in the worker's state directory rather than the worktree, where the agent and git would see it, and on Unix only its user can read it. It goes once the agent exits, or with the records of a killed worker's agents. An agent whose file can't be written, or whose worker doesn't serve the tools, goes without them. *Unconfirmed.*
- **A worker asks its hub, as well as answering it.** For a tool, it sends an ask, numbered apart from the hub's calls, naming the agent's session, and the hub answers it. The hub knows which workspace a worker is for, so it answers only for that workspace's sessions, and a tool reaches that workspace and nothing else unless it's given more. A hub refuses an ask it doesn't know as `Unsupported`, one it can't read as a whole included, as it does a request, and the worker gives up on one with no answer after a minute, or ten for one that makes or removes a worktree, which is all a hub from before asks gives it. A worker that outlives its hub asks each hub that connects whatever is still waiting for an answer, since the last hub may not have heard it, or went before answering, so every ask has to be safe to ask twice, as reading the pull request is. *Unconfirmed.*
- **A wait on a pull request is the hub's.** An agent asks for one through the worker's tools, and waits on one at a time, so starting one replaces the one before, but for one that ends as it starts, which never waits, and a call that asks again, as a CLI does when it reconnects, gets the one it started. It starts from a read of its own, of the pull request it then waits on, and is refused when that read fails, rather than start from what was known before the agent pushed. It's refused too when the read doesn't finish well within the minute a worker waits for the answer, so none is left that its agent never heard of. So is one while the worktree has commits that aren't pushed, since what GitHub says would be of an older commit, which ends nothing, and the wait could end only once the pull request is done, unless it ends as it starts, or the merge queue has it, which merges what's on GitHub. No other read of the workspace's goes until it's recorded, so the next judges it. The hub keeps it until a read ends it, by rules written once: merged or closed, or the branch's pull request isn't the one it waits on any more; leaving the merge queue without merging; a review asking for changes; for a wait until it's done, a draft, which can't merge; conflicts, or a failed check that holds the merge back; and for a wait until the checks, their passing. What GitHub records, leaving the queue and reviews, counts when it's newer than what GitHub had recorded as the wait started, both by GitHub's clock, so a stay in the queue too short for any read to see counts, and what came before the wait ends nothing, whatever the hub's clock says. Done comes first, then the queue, so a queued pull request that reads as conflicting for a moment, as a stack's upper one does while both merge, waits on. What GitHub says of a commit the agent has since replaced ends nothing until the agent's commits are pushed. Closing its chat or archiving its workspace ends it. A workspace with a wait is read at the soonest, even with no client connected, and reading one costs no call to GitHub, so an agent can ask how its wait stands as often as it likes. *Unconfirmed.*
- **A wait is an MCP task, whose ID is the wait's.** `wait_for_pull_request` starts one and answers with its task, so the call comes back at once and the agent's turn can end while it waits. The CLI asks `tasks/get` every 5 s, which the worker answers by asking the hub how the wait stands, which never reads GitHub, and `tasks/cancel` ends it. Once it has ended, the task has the tool's result, which says how, and where the pull request stands, and one called off is a cancelled task, which the CLI takes off its list as one that failed, then takes a turn by itself to tell the agent, but for one the agent stopped itself. So the task says who called it off: the person, who it asks the agent not to start another unless they ask, or a wait the agent started after it, which goes on. The person can call a chat's wait off with Stop on its line, which a running CLI hears as it next asks. With none running, as after the hub started again with its agent gone, the hub takes the wait off the chat's list itself, once the chat has none open, since the list's IDs are the CLI's own, which leaves it idle if that was all it had there, and the agent hears once it next starts. Closing the chat or archiving its workspace, which end its waits, do the same, and so does a wait's end that the hub won't start the agent to hear of, in a chat that was cut off or is held for the person. *Unconfirmed:* the hub taking it off the list. A wait that ended as it started is answered at once, with no task. A chat's record shows the wait it has open, as the hub keeps it, so a client shows a wait from that rather than from the CLI's list of its tasks, which still lists one that has ended until it next asks. A chat whose turn had ended with only a wait in the background stays at work in the background across a restart, with the wait still listed and its queue not held. A hub that restarts or dies leaves its agent running, as it does every agent, so the next hub carries on with it, and its CLI goes on asking after the task. One whose agent has gone as the next hub starts, since the last hub stopped, as `roundhouse hub stop` stops it, or went with its workers, as when the machine goes down, isn't marked interrupted, since nothing it was doing was cut off. When a wait ends with its agent not running, in a chat that's idle or at work only in the background, with its queue not held, the hub starts the agent, keeping the worker that read the pull request for it, and its CLI, which lists its tasks again, asks after the task and starts a turn by itself to say how it ended. A chat that was cut off, or is held for the person, hears with their next prompt, since its CLI lists its tasks again then too. Archiving a workspace calls off its waits before its archive script runs, so none ending meanwhile starts an agent in a worktree that's going. *Unconfirmed:* starting the agent without asking. The Claude adapter tells a wait's task from the agent's other work in the background by how the CLI describes it, as the tool that started it, `roundhouse/wait_for_pull_request`, which the list says each time, so it does after a `--resume` too, when the call was another process's. A chat whose only work is waits doesn't keep a hub asked to stop only if nothing would notice, as to update it, from stopping, since the next hub keeps them, though it's still at work meanwhile, and keeps the machine awake, so their pull requests go on being read. *Unconfirmed:* not keeping such a hub from stopping. A call is offered tasks only with `CLAUDE_AUTO_BACKGROUND_TASKS=1`, which the Claude adapter sets with the tools, though it also moves a subagent or another server's call to the background after 2 minutes, as `docs/claude-cli.md` says, which most subagents already are. A wait can only be answered with a task, so a call from a client that doesn't offer to take one is refused, as MCP's tasks extension says. *Unconfirmed:* 5 s, and setting the variable. *Not built:* answering such a call at once, and telling the agent how its wait ended as a prompt.
- **What a tool says is written for the agent,** in full, and apart from what the app shows, since an agent reads it as words and gets wrong what a person wouldn't, such as reading a pull request in the merge queue as merged. *Unconfirmed.*
- **An agent hears only what was read since it asked.** The hub reads the pull request for it at once, but no sooner than 10 s after the workspace's last read, and within the part of GitHub's limit that isn't kept for everything else. It fails rather than say what was known, which may be from before the agent pushed. So an agent asking in a loop reads at most six times a minute, and one asking again after it pushes waits 10 s at most. *Unconfirmed.*

## What agents are told

Every agent is told about working in Roundhouse, and so is each of its subagents, in text of the worker's own, `crates/worker/src/instructions.txt`. It's written for any agent and built into the worker, so it arrives and changes with the worker's build. It's plain text rather than Markdown, since the checks pass over a change that touches only Markdown. *Unconfirmed.*

- **It says only what holds whether or not the agent has the worker's tools,** such as where to keep what it makes for its own use, and how to show the person an image. What the tools are for is in the tool server's own instructions, which come with the tools. *Unconfirmed.*
- **Each adapter puts it in its agent's system prompt at every launch,** resumed ones included. The Claude adapter puts it after the CLI's own with `--append-system-prompt`, and gives it to subagents with `--append-subagent-system-prompt`, since they get none of the agent's own, as `docs/claude-cli.md` says. *Unconfirmed.*
- **A chat goes on with what it was first told until it's compacted,** since the Claude CLI keeps a conversation's first system prompt when it's resumed, so new text reaches new chats, and older ones once they're compacted. *Unconfirmed.*
- **What an agent makes for its own use goes in the worktree's `.context/tmp/`,** which the worker makes before each agent starts, with a `.gitignore` that ignores everything in it, as it makes `.context/attachments/` for a prompt's files. So nothing there shows as a change, whatever the repository ignores, and an image there can show in what the agent writes. It's deleted with the worktree when the workspace is archived. Agents otherwise reach for the system's temporary directory, where the person can't see what they made. The exception is something that mustn't be inside the repository, such as a throwaway project that would pick up the repository's own settings. The rest of `.context/` is left alone, since a repository can keep things of its own there. *Unconfirmed.*

## When a process dies

Any process can die at any point, so nothing depends on a clean exit. Whatever survives works out what happened from the records.

- **A hub is a separate process that outlives its clients,** so closing the app doesn't stop its agents. A client connects, or starts a hub if there's none, and a lock keeps each data directory to one hub.
- **A prompt is recorded before anything else is tried,** and the client gets its reply at that point. Later failures go in the log, where every client can see them.
- **A client that quits finishes sending what it was asked to do first, and briefly waits for the replies.** The hub carries out each request it receives on its own, so one received runs to the end whether or not its client is still there, and a prompt sent just before quitting is still recorded. The app waits at most GPUI's 200 ms. *Unconfirmed.*
- **A hub that starts connects again to the workers the last one left running, and cleans up after the rest.** Each worker says which agents it's running and what they're doing, and sends what it kept while there was no hub, so their sessions carry on as they were, with their open approvals and the prompts they haven't taken, and so do agents that were idle. Only a session whose worker has gone has its open approvals closed, and is marked `Interrupted`. So is one whose worker can't be reached, such as one that's stopping, and the hub ends that worker and its agents, as it does a worker that nothing carries on with. But one whose only work was a wait, which is the hub's, is still at work in the background, as "The worker's tools" says. It does this before it serves, so no client finds a session half carried on, and gives each provider five seconds to list its instances and to say how to reach each worker, so a slow one can't keep every client waiting. The hub also fails setups that were cut off, and discards half-made workspaces. A workspace it was archiving or restoring stays recorded as that until the hub is serving, and its worker is kept, even with no session to carry on with. Then the hub asks that worker whether the worktree is there, and records the workspace as ready if it is and archived if it isn't, whichever it was doing. The worker answers once it has finished any removing or putting back it was still doing, which is why it has to be the same worker. If it can't say, the workspace goes back as it was before. An archived workspace's worker is then stopped. *Unconfirmed:* five seconds, ending a worker that nothing carries on with, and settling such a workspace from its worktree once the hub is serving. *Not built:* on Windows, where workers exit with their hub, it treats every active session as one whose worker has gone. Once it's serving, it destroys the instances the last run was making or destroying, and keeps the record of one it can't, for the next start.
- **A worker keeps its agents running when it loses its hub, and keeps what they say until a hub has it.** A local hub restarts for every update, and a remote worker's hub can be away for as long as its Mac sleeps. The worker numbers what it sends, and its hub says what it has recorded, so nothing is lost, and the next hub drops what it's sent again that it has, so nothing is recorded twice. A hub says so as it goes, at most ten times a second, so a burst gets one answer, and as it leaves the worker for the next hub. Each session records the last number it took in with what it records, which is how the next hub knows. A local worker keeps it in memory, since the worker itself lives through its hub's restart, and a remote one on disk, since its hub can be away for hours. *Unconfirmed:* memory for a local worker, and a hub saying what it recorded as it goes, rather than the next hub saying it as it connects, since a session's record says what it took in, and a worker has no one number for every session. *Not built:* a remote worker, and one on Windows, which stops its agents when it loses its hub, so nothing runs unrecorded, and the next prompt resumes the conversation.
- **A worker also keeps what each agent is still writing, for the next hub.** A delta isn't recorded, so it isn't kept, but the tail the deltas so far make is, with the subagents the agent runs in the background and its compaction under way, whether or not a hub was there to be sent them, and it goes once nothing is being written. A hub that connects gets the tail of each run after what was kept for it, and takes it in place of its own tail of that run, so a message the agent was writing as the hub went carries on whole, rather than from the next delta. A compaction the hub before had only asked for isn't in it, since only a hub knows of one. *Unconfirmed.*
- **A worker with no hub stops in time.** A local one that has had no hub for ten minutes stops its agents and exits, as stopping its hub would have, so a hub that was killed doesn't leave them running unrecorded for good. That's longer than a restart takes, a migration included. A remote one waits for as long as its provider says, since its hub's Mac can sleep. *Unconfirmed.* *Not built:* a remote one.
- **When a worker goes, the hub stops its instance and tells its sessions,** which close their open approvals and record that the agent exited. The next prompt starts a new worker and agent.
- **Workers, agents and setup scripts each start in their own process group,** so stopping one reaches everything it started, and a signal to the hub's terminal doesn't reach them directly. Signalling a group, and recording a PID with its start time, each have one implementation, in `crates/process`.
- **On Windows, stopping a group ends its leader and everything the leader started, at once.** It doesn't ask first with Ctrl-Break, the nearest thing Windows has to `SIGTERM`, so nothing gets a chance to stop by itself. Windows has no process groups to stop, so what a leader started is found from each process's parent, which misses a process whose own parent has exited. A job object that ends its processes when its last handle closes would hold those too. *Unconfirmed.*
- **On Windows, what a process starts gets its own input and output only when it's given them.** A child there gets a copy of every handle its parent can pass on, so a hub would hold the input and output of the client that started it for as long as it runs, and something an agent left running would hold its worker's pipes to the hub, which learns that the worker has exited when its output ends. So the daemon, and a client starting a hub, keep theirs from what they start, through `crates/process`. For the same reason a hub or a worker that has stopped waits only a second for what's left on tokio's blocking threads before it exits, since tokio reads a child's output on one of them, and such a leftover can keep that read waiting for ever. *Unconfirmed.*
- **A worker that gets killed can't stop its agents, so it records them.** Each agent's PID and start time go in a file in the instance directory, and the local provider stops anything still recorded before the next worker starts. Otherwise an orphan and its replacement would both be working on one conversation and worktree. The provider removes the rest of each run's files there too, such as the one holding its token for the worker's tools.
- **An archived worktree's files are deleted by a process of its own,** since the hub closes the worker as soon as archiving is done. The worker moves the worktree into `.deleting` beside it, or beside the workspace's own for another of the workspace's worktrees, so every archive in the repository clears it, has git forget it, then starts the daemon's hidden `delete` command on what's there, which makes read-only directories writable if they're in its way. Whatever is left in `.deleting` when the next workspace beside it is archived, such as what a shutdown cut short, is deleted with it, and so is a worktree whose worker stopped before git forgot it, once its archive is tried again. A lock in `.deleting` keeps a worktree that git refuses to forget, which goes back where it was, from being listed by another worker meanwhile, and one that can't go back is kept beside it, where nothing deletes it. What can't be deleted goes in the worker's log. *Unconfirmed.*
- **Each launch of an agent has a run ID,** and its events carry it. A late event from a replaced agent still goes in the log, but can't change the status of the session its replacement is running, or clear its replacement's tail.

## Managing a hub

Who starts, updates and stops a hub is a separate role from the hub itself, and what fills it depends on where the hub runs. The app replaces an older local hub as soon as it finds one, when it connects or while it stays open. It asks the hub to restart, which leaves its workers running for the next hub to connect to again, so that stops nothing, and the hub restarts once no setup script is running. A hub from before agents could outlive it refuses the restart, as it does any request it doesn't know, and since stopping one of those stops its agents, the app replaces it only once nothing is running on it. So does a hub on Windows, whose workers stop with it, as "Providers" says, and whose status says so. With a setup script running, the app goes on using the hub until it has gone, and then connects to the next one. *Unconfirmed.* An agent whose only work is waits on its pull request doesn't count, since the next hub keeps the waits and starts it again once one ends, as "The worker's tools" says. For a hub that waits for its agents, the hub has the last word on whether nothing is running: the app asks it to stop only if nothing would notice, and the hub decides as it stops, because a prompt can be sent between the app seeing it idle and stopping it. A hub that's busy after all refuses and carries on. One from before hubs could decide is stopped on what it last said was running.

| | Local hub started on demand | A hub you run yourself, here or on a server | Hosted, if one is ever run |
|---|---|---|---|
| **Starts it** | Whichever client needs it | You, systemd or Docker | The service |
| **Updates it** | The desktop app, as soon as it has updated. *Not built:* when nothing is running or when you choose to restart it | You or your package manager | The service |
| **When versions differ** | Keeps working, and the app replaces the hub | Keeps working, and the app says the hub is older | Keeps working |

- **A hub knows nothing about what manages it.** It offers its status and stops cleanly on `SIGTERM`, which is what systemd and Docker use. There's no desktop mode, and it doesn't exit when the app closes.
- **Stopping a hub stops its agents, and restarting it doesn't.** `roundhouse hub stop` stops each workspace's worker, and the agents it runs, before the hub exits, and says how many agents that stopped, so nothing is left running with no hub to record it. So does `SIGTERM`, since systemd and Docker send it to stop a hub, and can't say whether another is coming. A restart, which the app asks for when it updates, leaves the workers running, and the next hub connects to them again within moments. *Unconfirmed:* that `SIGTERM` stops agents.
- **A client never needs one exact hub version.** It hides or disables what an older hub doesn't support, as "Changing the protocol" describes, and only a real break stops it. This stays as simple as it can, and gets revisited if it turns out complicated.
- **A client only replaces a hub that says it's replaceable.** A hub started on demand reports that in its status, and one you started yourself gets left alone, even on the same Mac. Only the desktop app replaces a hub, and only an older one, so two versions can't keep replacing each other's.
- **Only a local on-demand hub that's older than the client can be restarted from it.** A client's own hub might not be able to open what a newer one has written. The app offers to restart one that's waiting on its agents, so nobody has to wait for it to be idle. A remote mismatch only gets an explanation. Stopping a shared hub is for its admins, not for any client whose version differs.
- **The app ships a default hub, and that's the only link between them.** The hub doesn't depend on the app.
- **`tools/install.sh` copies release binaries into `roundhouse-builds/<version>/`,** and a `current` link names the one to start. Keeping versions gives rollback by moving the link, and past a migration, the database goes back to the copy the hub saved before it, as the README says. A client resolves the link when it starts, so it stays on its version when the link moves, and rebuilding or archiving the worktree it was built in can't touch it. Its hub stays on one build through its own copy, as "Updating the app" says.
- **A package stamps its published version through `ROUNDHOUSE_BUILD`, and an install its commit,** and any other build says `0.1.0-dev`. The app and `roundhouse hub status` show it, and say so when the app and hub differ, because a bug report has to say which code it came from, and the version is the name of what people download. Version `0.1.N` is the Nth commit on `main`, which `git rev-list --reverse main | sed -n Np` prints. With uncommitted changes, the build also says when it was built, so two different builds never show the same. A build script would rebuild the crates above it on every commit, for builds nobody needs to identify.
- **An install or a package also stamps an order through `ROUNDHOUSE_BUILD_NUMBER`:** when its commit was made, or when it was built if it has uncommitted changes. Any other build has no number, so it's never replaced. Replacing only an older hub needs an order, and a commit hash has none. Install time would let installing an older commit replace a newer hub, whose database it might not be able to open, and commit counts disagree across branches. Rolling back keeps its older number, so the app leaves the newer hub alone until it's stopped.
- **Only a binary reads the stamp, and its `main` passes the build down,** so every library compiles the same whatever the stamp, and the next install or package recompiles only the crates its commit changed, and the binaries. A library that read it would be recompiled for every build, with every crate above it. `tools/check-stamp.sh` checks it, in CI's lint job. *Unconfirmed.*

What someone using the app sees during an update is in `docs/spec/updates.md`. Workers outlive their hub, as "When a process dies" says, which lets the app replace a hub without stopping its agents, and "Changing the protocol" says how a hub works with the older workers that leaves it.

### Updating the app

The app is signed and notarized, you download it, and it updates itself as changes land on `main`, so staying current needs no checkout or toolchain. `tools/install.sh` stays the way to install a build of a checkout, as above, for working on Roundhouse.

- **Velopack packages, installs and updates the app.** One tool packages the app and makes its updates for macOS, Windows and Linux, and an update downloads only what changed. Sparkle signs its updates but covers only the Mac, and an updater of our own would have to redo what Velopack does on Windows.
- **The Windows app is an installer you download once, which then updates itself as the Mac app does.** Its binaries are built on Windows, and `vpk` packages them on Linux, which it can for Windows, so the keys stay in the one kind of job that publishes. It has a feed of its own, `releases.win-amd64.json`, in the same bucket and signed with the same key, and jobs of its own, so neither platform's release waits on the other's or fails with it. It installs for one user, in `%LOCALAPPDATA%\Roundhouse`, without an administrator. Nothing signs it, so Windows warns whoever downloads the installer. ARM64 Windows gets the same, built on an ARM64 runner and published under a channel of its own, `win-arm64`. An app looks for updates in the channel it was packaged for, so each gets its own processor's. One packaged while amd64 Windows' channel was `win` still looks there, so each amd64 release also signs `releases.win.json`, offering only its own full package. Such an app takes it as an update, and since that package was made for `win-amd64`, it looks there from then on. *Unconfirmed.*
- **The Linux app is an AppImage, which updates itself as the Mac app does.** It's one file that runs on most distros without installing, and the one package Velopack updates on Linux. Flatpak's sandbox would keep the app from the host's git, shells and agents, which it runs all the time, and a `.deb` or `.rpm` would hand its updates to a package manager. Its binaries are built in Ubuntu 22.04, so they need no glibc newer than 22.04's 2.35, and the app runs there and on every distro since. It can't be wholly static, since GPUI loads the system's Vulkan driver, which is built against the system's glibc. `vpk` packages it on Linux, in jobs of its own, with feeds of its own: `releases.linux-amd64.json` for amd64 and `releases.linux-arm64.json` for ARM64. Velopack moves the new AppImage over the old one, and where this user can't change the folder it's in, asks for an administrator's password through `pkexec`, so the app says it can't update there instead, as "Nothing about updating is a native dialog" in `docs/spec/updates.md` needs. Velopack would keep downloads in `/var/tmp`, which every user on the machine shares, so the app has it keep them in the data directory. *Unconfirmed:* that check, and where downloads go.
- **CI builds, signs and publishes every merge to `main`.** The merge queue has already run the checks on Linux by then.
- **A published build is versioned `0.1.<commits on main>`,** such as `0.1.50`, which is what Velopack orders updates by. It's short and readable, every merge adds one, it leaves 0.2 and 1.0 free to mean something later, and each part fits the 16 bits of a Windows version field. A count can't be the build number, because counts differ across branches, but only `main` publishes, and its history only grows.
- **The update feed is signed, and the app checks the signature before trusting anything in it.** Velopack only checks each package against a checksum in the update feed, so without a signature, whoever controls the host controls the app.
- **A hub a client starts runs from its own copy for each build, outside the app's install directory.** An update replaces that directory, so a hub running from it would start its next workers from different code, and on Windows Velopack first kills everything running from it, which would stop the hub and its agents. On Linux the AppImage's files are only there while the app runs, which keeps the mount, the variables and the `PATH` entry its launcher left it out of what it starts, the hub included. Velopack's updater is the exception: it runs from inside the mount and finishes after the app quits, so the app lets it hold the mount up. *Unconfirmed.*
- **A client that starts a hub removes the copies nothing runs from anymore,** once they're a day old, but its own build's, since every update leaves one behind. Each process of the daemon marks the file it runs from with a shared lock for as long as it runs, and a copy is removed only under a lock that shuts out the shared one, so a worker that outlived the hub of its build keeps that build's copy. The day is for what marks nothing, a process of a build from before processes marked their files, since a worker outlives as many hubs as its workspace stays at work through. A client that can't start its hub, as when another removed the copy it was about to start, joins the hub that's up if there is one. *Unconfirmed.*
- **The copy is named `Roundhouse Hub`,** so that's what its hub and the workers it starts are called wherever a process is named for its file, such as `ps`, Activity Monitor and 1Password's prompt to use an SSH key. The daemon in the app's install directory is still `roundhoused`, and so is one started where it is. The copies of builds from before the name are `roundhoused` too, and are removed the same way. The copy isn't an app that registers itself with macOS, though that would put the app's icon on the prompt too, because 1Password holds back the prompt of an app that isn't in front, as a hub never is, so an agent's push would wait unseen and then fail.
- **On Windows a hub keeps its data in `%LOCALAPPDATA%\roundhouse-data`,** not `roundhouse`. Velopack installs an app in `%LOCALAPPDATA%\<its name>`, with its updater and packages, and Windows ignores case, so the two would be one directory. *Unconfirmed.*
- **The app decides when an update installs,** so an update doesn't interrupt what someone is doing.

## Providers

Every provider has an adapter: a program the hub runs, which makes and ends the provider's instances. The hub talks to it over the provider protocol:

| Operation | Purpose | Required |
|---|---|---|
| `create` | Make an instance, from a base image and at a size where the provider takes them, and place the worker binary in it | Yes |
| `start`, `stop` | Wake and sleep. Stopping also ends anything the worker left behind | Yes |
| `kill` | Like `stop`, without giving a worker that isn't responding time to finish | Yes |
| `connect` | Return the command that opens a byte stream to the worker | Yes |
| `destroy` | Remove the instance | Yes |
| `list` | Say which instances exist, so a hub that starts finds those that outlived it | Yes |
| Base images | Build one with a repository's script, list them, and delete one | Optional, declared by the provider |
| `snapshot`, `restore` | Preserve or roll back the filesystem | Optional, declared by the provider |

An adapter also tells the hub, unasked, when an instance is about to end or has gone, such as when a cloud takes back a spot instance or a host goes down, rather than leaving the hub to find out when the worker's stream breaks.

- **Workers only need a byte stream.** `connect` answers with a command, and the hub runs it, with its stdin and stdout as the worker's stream. That can be `incus exec`, SSH or anything else, including the adapter's own program where it has to carry the stream itself. The hub dials out, so workers don't need to reach the hub, and an adapter that carries no streams can stop without taking its workers with it.
- **An adapter is a separate program, over stdio.** The hub runs each as one long-lived child, beside itself, and starts it again if it stops. Every request names its instance and is safe to repeat, so a restart loses nothing. Adapters can be written in any language without rebuilding the app, and one written in Rust implements the `Provider` trait and has `providers` serve it. A gRPC API may come later, so the contract is defined as messages, independent of the transport.
- **The local provider's adapter is the daemon's own `provider local`,** so it ships with every hub, and its instances are directories and its workers processes on this machine.
- **A local worker runs on its own, so it can outlive its hub.** The local provider's `connect` answers with the daemon's own `worker --attach`, which connects its stdin and stdout to the worker serving `worker.sock` in the instance directory, and first starts that worker if none is serving it. The worker is in a session of its own, so nothing that ends the hub, or the command the hub runs, reaches it. It runs in the instance directory, and it and the command name the socket relative to it, since a socket's path can be at most 103 bytes on macOS and an instance directory's can be longer. A worker that's stopping removes its socket first, and while it still holds the instance the command fails rather than starting another, since it may be stuck, and the hub ends it, as it ends whatever it finds on an instance it doesn't know of. On Windows, which has no Unix sockets in tokio, a worker still runs on its hub's pipes, so it stops with its hub. *Unconfirmed.*
- **An adapter keeps its own access to where it runs instances,** such as the Incus client's remotes or the usual AWS credentials, so the hub holds no secrets for it. The hub's settings name each provider, the command that runs its adapter, and which one new workspaces go to. *Not built:* until they do, `providers.json` in the hub's data directory names them, and the hub reads it as it starts.
- **Stopping a worker is split between the hub and the adapter.** The hub closes the worker's stream and gives it time to stop its agents, which works the same over any transport. The adapter then ends the instance and anything the worker left behind: for the local provider, the worker's process group and the agents recorded in its instance directory, and for Incus, the VM.
- **A worker always runs its hub's build.** Starting a worker puts the hub's worker binary in the instance first, if it holds a different one, so an instance that slept through an update doesn't wake with an old worker. The only older worker a hub meets is then one that outlived the hub before it, which it replaces once nothing in its workspace is at work, as "Changing the protocol" says. The local provider has no copy to replace, since it starts the hub's own executable. *Unconfirmed.*
- **Providers declare their capabilities,** such as which systems and architectures they run, whether the filesystem survives a stop, and whether they build base images or take snapshots. Persistent instances don't need snapshots to sleep, while ephemeral sandboxes do.
- **A remote workspace runs in a VM of its own, made from its repository's newest base image, and destroyed when it's archived.** A VM is as flexible as a real machine: an agent can run containers in it, and the services and kernel features its project needs, which are hard to get from inside a container. It's also a stronger wall between workspaces whose agents run unattended with credentials, and nothing one workspace leaves behind reaches another. A base image is a VM that a script of the repository's own has set up, with its tools installed and its caches warm, so a workspace made from it starts with a warm build rather than a cold one. *Not built.*
- **Availability follows the hub.** A hub on an intermittently available machine, such as a Mac, is only reachable while that machine is awake. Agents on remote workers keep running and catch up later. Persistent mobile access needs a hub on an always-on machine.
- **Each workspace gets its own worker process and provider instance,** so a crash in one doesn't touch the others. This matches sandboxes, where each workspace has its own machine. A worker uses about 8 MB, so this is cheap on a Mac.
- **The local provider is inside the hub for now,** which calls it directly, through the `Provider` trait, while it reaches the others through their adapters. The trait has the protocol's requests, one method each, with their rules. `snapshot` and `restore` come with the first provider that uses them.
