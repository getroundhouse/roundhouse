# Architecture

How the system fits together, and why. This is the agreed design, so it includes parts that aren't built, and those are marked. Where the code does something simpler for now, this says what.

## State ownership

Each piece of state has one owner, and every other copy is a cache.

**What every client shows alike is the hub's, recorded rather than worked out or fetched live.** The test: should a second client, or this one after a restart, show the same thing? Then the hub owns it, and a client only draws it. So decide who owns the state before choosing where a change goes: a bug in what a client shows often comes from a client keeping or working out what the hub should record. When the cause is an *Unconfirmed* design, question the design, not just the bug. A client keeps or works something out only when it's about its own device, as the table says. A fix that finds a client doing more than that moves the state to the hub, even when that's the bigger change. A protocol change is the normal way to do it, and `docs/principles/protocol.md` says how to make one, mostly without a version bump.

The dialog's copy goes with the connection, since the dialog is the same place on every hub. *Not built:* a local hub has one user, so how far a session is read, and what's typed and attached in its composer, are kept on the session. A client asks the hub to make the workspace from what it says is in the dialog, and the hub starts its first chat on the agent the dialog says, or else on the first kind of agent it describes, as a client does, and gives the chat copies of the files with the prompt, so no client sends them again. The hub lets go of one nothing has named for a day too, such as one a client took out without the hub hearing, counting the day again as a workspace is made from it, and of bytes with no file as it starts. *Unconfirmed:* that record, that it keeps the repository, model, effort and plan mode as well as what's typed and attached, that the hub makes the workspace and gives the new chat the files, that a client asking for that chat first gets one of the dialog's agent, that it empties the dialog only once the chat has the prompt, and the day. A client keeps and shows it as it does a chat's draft, and reads back its files. *Unconfirmed:* that the hub lets go of an answer being typed as its question is answered or cancelled, and of a comment being written as it's saved. The hub keeps it as a draft of the decision, by what the request asks: for questions, each one's answer so far, by position, leaving out what's typed for a secret one, and for a request to use a tool, which a client asks as a question whose answers client-core gives, as `ToolUseAnswer`, whether it's to be allowed or denied, by name, and the words being written to deny it in, so a client that draws the answers in another order reads the same draft. A choice the client doesn't know, from a build to come, is kept as unknown, and read as nothing chosen. *Unconfirmed:* what's kept for a request to use a tool |
| Instances | Which instances the hub asked each provider for, and whether each is being made, made or being destroyed | The hub, which records each before it asks for it, so it knows which are its own whatever a provider lists, and destroys one that a crash left part way, whether it was being made or destroyed. Whether an instance exists, and whether it's running, is its provider's |
| Live processes | Running agents, terminals, run scripts | The worker |

- A session has one writer, so events get a simple sequence number and no merge logic is needed.
- A prompt or approval only becomes real once it's recorded. Until then, the UI shows it as pending.
- **Which approvals the agent is waiting on is on its session's record,** changed in the same transaction as the event that asks or answers one, so a client reads them rather than finding them among the events it has loaded, which can miss one whose answer is in a page it hasn't loaded. What it has loaded after the copy of the record it has says what has changed since, until the feed brings a newer copy. A record from a hub too old to say says nothing rather than none, and a client of that hub finds them among what it has loaded, as before.
- **A tool's use the hub is set to allow itself is allowed by the hub, as the agent asks.** An agent with full access asks about what its CLI won't do unasked, and the hub's setting can have it allow that for the person. The hub answers it, rather than a client, since the agent waits on the hub whether or not any client is open, and rather than the adapter, since every agent's requests reach the hub and the setting is the hub's. The request and its answer are recorded in one transaction, and leave the session's status and the approvals open as they were, so no client is told the agent waits, and none shows it waiting or tells the person. The answer says the hub's setting allowed it, so the log tells it from the person's, and it isn't something the person did. The agent's word that it needs something, such as Claude's `requires_action`, which comes before its request, waits on the person only while a request is open. *Unconfirmed.*
- **A project holds one or more repositories,** each with its address, a checkout on the hub's machine where one is linked, and what GitHub says of it, since a change can span repositories, even of different owners. A workspace has a worktree of every repository of its project, under its folder, on one branch name and one worker. What's of a repository, such as whether the default can push to it and its pull requests, is keyed on the repository, not on its project or a workspace, so it holds as a project takes more. A repository's record says where it is, as `RepoOrigin`: its checkout on the hub's machine, its address, or both, never neither, so no code takes a checkout for granted. Its address is the record's, and the truth, what a worker with no checkout of its own clones and fetches from. A linked checkout's is read from its `origin` by a worker on the hub's machine, never by the hub, which runs no git: as the checkout is added, by a worker running there then, or else by the next one there to link, which making the repository's first workspace starts. One recorded before addresses is read by the first worker there to link. Until one has said, as a worker from before can't, the record has its checkout alone. It's read again only when the checkout is added again, so a change to the checkout's `origin` reaches the record only then. The worker cuts out any credential an address holds, such as a token in an `https://` one, and the hub keeps none that still has one, so an address is kept, sent and logged without it. A record goes to a client from before addresses with its checkout beside where it is, as that client reads it. *Unconfirmed:* asking a worker that's running there rather than starting one, reading it again only as the checkout is added again, taking `origin`'s first URL, where it fetches from, as `git remote get-url origin` gives it with the person's own git config, so their `insteadOf` counts and the git credential's rewriting of GitHub's addresses for workers doesn't, and keeping an SSH address's user. *Not built:* a project of more than one repository, and a repository with no checkout on the hub's machine, added by its address alone. Until then, a project is one repository, in one record, `Repo`, added by its checkout on the hub's machine.
- **A workspace is the hub's record from the moment it's asked for.** The hub records it before it fetches and makes the worktree, which can take a while, and announces it then, so every client can show it on its way, in the place it will have, and none has to work out which new workspace is the one it asked for. The hub asks the workspace's worker which names git has: the first part of each branch's name, here and among `origin`'s as last fetched, each remote's name, `HEAD` where there's a remote, and each directory where the repository's workspaces go. The hub counts them whatever their case. A name git has is refused before anything is made, and the next name skips all of them, so the record takes it in place and keeps its ID. Its instance is destroyed and made again under the new name, since a provider's own tools call it by the name it was made with, and it's recorded again first, as any instance is. One that can't be made is removed, which is announced too. *Unconfirmed.*
- **Whether a workspace is being archived or restored is on its record,** from the moment it's asked until it's done, and announced, so every client shows it on its way out or back, wherever it was asked for. The hub records it before anything else, and only one request can, so a second is refused. One that's refused or fails part way, as when archiving would lose work, puts the record back as it was, which is announced too. Meanwhile the workspace isn't ready, so the hub refuses what needs it to be, such as a prompt or a read of its worktree, which is about to go or isn't back yet.
- **A workspace's other worktrees are the hub's records, and their files the worker's.** The hub chooses each one's branch and where it goes, numbering a name that's taken, and the workspace's worker makes it there, refusing a path that isn't a directory of its own in the workspace's folder of `.children/`, and what git can't make. The hub records it as being made before it asks, under the key the worker gave the ask, so a hub that stops meanwhile, or loses the worker before it answers, leaves a record of what may be there. Asked again, the next hub asks the worker for it where it was to be, and the worker answers with what's there on its branch, waiting for an add of it that's under way, rather than making another. A worker waits ten times as long for an ask to make or remove one as for others, since either can take minutes. A record is forgotten when the worker answers that it couldn't make it, and one stays once its worktree is removed, with its branch. Each one's branches are watched as the workspace's own are, and kept on its own record. Whenever the hub has a worker watch the workspace's branches, as when it connects to one again, starts one, or has put the workspace's worktree back, it settles the others' records from what's there, as it settles a workspace left part way through being archived. One recorded as there that has gone is recorded as removed. One being made is recorded as there if the worker has it, on its branch, and forgotten if nothing is there, or the worker says something else is. A worker that can't say what's there settles nothing. Making one waits while one is removed, the records are settled or the workspace is archived, and those wait for any being made, so nothing is removed or forgotten as it's made and left there unrecorded. Archiving records that it's under way first, as it does for every client, and then waits for those, so one asked for meanwhile waits too, and is refused once it can look, as everything that needs a ready workspace is, unless archiving was put back. Then archiving checks every worktree for work it would lose before anything changes, and refuses with all of it, naming each other worktree, so forcing past one's doesn't lose another's untold. It removes the others before the workspace's own, so a hub that stops part way leaves the workspace's own worktree until last, and the next, which settles the workspace from whether that one is there, finds an archived workspace's others gone. One that can't be removed, such as a directory that's no longer a worktree, refuses as work that would be lost does, since forcing goes on past it, as past a failing archive script, and leaves it recorded as there. The worker does one thing at a time to each worktree: making another of the workspace's, removing any, or putting the workspace's own back. Each worktree is apart from the others, so removing one waits for an add of it, and the question of whether one is there waits for either. *Unconfirmed.*
- **A repository's clone is its workers'.** A worker told to make a workspace's worktrees from a repository's address, rather than from a checkout on its machine, clones the repository the first time a workspace needs it, keeps the clone, fetches it from then on, and makes each worktree from it as from a checkout, so branches, archiving and other worktrees work the same. There's one for each address on the machine, in the clones directory the worker's provider names, which every worker the provider runs there shares, and whichever worker wants it first makes it. It's never the hub's, which runs no git. Every request that names, makes, restores, removes or sets up a workspace's worktrees says which they're from, as a `RepoSource`, and a clone's git goes through the git credential the hub sets, as every git the worker runs does. The local provider's clones directory is `clones/` in the hub's data directory. Each clone there is bare, with the whole of the repository's history, and named for the repository, by the end of its address, and for the address, by its UUID, as `rails-32c5b9a70a5f50d8b81edaaa133969f3.git` is, so a person can tell which is which and no two addresses share one. Before each workspace is made from a clone, the workspace's base is fetched, as it is from a checkout, and a fetch that fails makes the workspace from what the clone has, with a warning. A clone has no local files or local settings for setup to copy into a worktree. Removing a repository leaves its clone, since the branches of its archived workspaces are only there, until a person deletes it. *Unconfirmed:* the local provider's clones directory, each clone's name, a bare clone of the whole history, fetching only the base before each workspace, making one from what's there when that fails, and leaving a removed repository's clone. *Not built:* removing a repository.
- **When the person last did something in a workspace, and in each of its chats, is on their records,** by the hub's clock. A chat's moves when the person sends its agent something: a prompt, as it's sent or queued, or an answer to a question or an approval. A workspace's moves when it's made, when a chat is made in it, and with each of its chats', in the same transaction as the event, the queue or the chat that moves it, and the feed announces each. A queued prompt counts once, as it's queued, so the hub sending it later, with nobody there, doesn't count again, which a client couldn't tell from the log. Every client sorts workspaces by the workspace's, and so agrees, rather than each working it out from whichever chats it has. *Unconfirmed.*
- **Whether the agent went on without a call's result is recorded too.** Nothing an agent sends says so, and telling takes knowing how that agent behaves, which only its adapter does. So the adapter records a `ToolCallDropped`, and a client reads it rather than working it out from what came next. The adapter only sees what came next itself, so a result recorded afterwards stands. *Unconfirmed.*
- **Whether the person denied a tool's use is said on its call's result, by its adapter.** A denied call's result is what the agent was told, which a client can't tell from a failure, and only the adapter can read where its agent says so. client-core's `Returned` reads a denied call as one that didn't fail, so every client says the same of it. A request to make a call names the call, as Claude's, Codex's and Antigravity's adapters do, since a typed request doesn't, so a client finds the call's result from the record that closes the approval, and says a denial once. It goes on the result, rather than on the record that closes the approval, since every place a call is drawn reads its result, and a subagent's work, apart in its own tab or in its record of what it did lately, has no way back to the request. The result says what the person said, if anything, apart from the adapter's own words for a denial. A request a stop cancelled isn't a denial, so its call's result says nothing of it, and its approval's record says what became of it. *Unconfirmed.*
- **What an approval asks is said by its adapter, not worked out from the agent's tool, and so are the words the agent is told of what the person decided.** Only the adapter knows its agent's tools, so it says of each request, as a `Request`, whether it asks to make a call, typed as "Wire format and event log" says of a call, asks questions, each with its text, its header, the options it offers, whether several can be chosen and whether it can be answered in words, which may be secret, or asks to approve a plan, with the plan and the file it's in. It also says which rules the agent suggests keeping, so the same use isn't asked again, and whether the agent asks in every mode, as Claude's does for a safety check. A decision on a call keeps only a rule the agent suggested, wherever the person keeps it, so none keeps a wider rule than the agent asked for. What adapters recorded before they typed their requests is typed by the hub's `untyped` module, once, in the `typed_requests` migration, as Claude's adapter types a request now, from what was recorded of it, so none is asked in every mode, since whether one was went unrecorded. The record that closed each is typed with it: an allowed use as allowed once, a denied one as denied in the words its call's result says the person gave, a plan approved as approved, its conversation kept, one refused as one to keep working on, answers given by text as the options they name, by position, or as typed where they name none, and questions denied as none answered. A client decides with a `Decision`, through `session_decide`, and the hub checks it against what the request asks, as `Decision::answers` says, and against what the run that asked claims, as `Decision::allowed` says, before it records it and passes it on, so a decision the agent can't take is refused, rather than lost on its way. Each adapter's tests hold it to taking every decision those checks pass on each kind of request it makes, so a claim wider than what the adapter can tell its agent fails a test. A call is allowed as it was asked, and never changed first: a person who would have the agent do something else denies the call, saying what in the words that deny it where the agent takes words, which leaves the agent to make the call it should, rather than the person writing it for the agent. Questions are answered by position, the way a draft keeps them: for each question in turn, the options chosen, by their place among its options, and what was typed. The adapter tells the agent in the agent's own form, such as Claude's, which keys each answer by its question's text. The hub records the decision as it came, but for what was typed for a secret question, which reaches only the agent, so the transcript says what was decided from the request, and the record that closes a request says nothing was decided where it was cancelled, by a stop, the agent's going or the agent itself. A client that says no sends no words of its own unless the person wrote some, and the adapter tells the agent as fits what was asked: a tool not to be used, a plan to keep working on, or questions the person chose not to answer, which is said one way, an empty answer to each, which every adapter takes. A plan approved names no mode to go on in, since each adapter goes on in the one its agent has besides plan mode, so a mode named would say nothing. A worker of the build before needs one named, so a Codex or Antigravity plan that waits through an update can't be approved, and its agent has to be stopped, which is accepted, since it takes a plan waiting just as the app updates. client-core's `Approval` says what a request asks and makes the decision that answers it, approving or refusing as fits what it asks, `claims_of_the_asker` finds the claims of the run that asked, or its kind's, which say whether a refusal can carry words, and `Answered` says what the record that closed it keeps of the answers, so every client reads them the same way. The client protocol's version stayed the same through the change, so a client from before reads the requests, which it read typed already, but not what closed them, and the hub refuses how it answers, and a client of this build reads a request a hub from before didn't type, as it didn't Claude's, as one it can't ask, and what closed any as cancelled. Nothing yet asks the person for network access, wider access to files, or a tool server's request, though a request can say it asks them. A request also says why the agent asks, in the agent's own words, when the agent says, and which subagent asks, by its ID, since only the adapter knows what the agent's request names. It stays among the agent's own events whichever asks, so a chat, which reads only those, has every request that waits on the person. client-core's `ToolUseAsked` says what a request to use a tool says of the use, the tool, what it's for, what the tool was given, why, and who asks, so every client shows the same of it, and a client only words and draws it. *Unconfirmed:* why, which subagent, `ToolUseAsked`, the migration's decisions, questions denied as none answered among them, the one way to choose not to answer, a kept rule held to those suggested, and what clients and hubs from before make of the change.
- **Which subagent an event is from is recorded, not worked out, and so is what each subagent has done.** The hub records with each event the subagent it's from, or none for the agent's own, and its place among the events from the same agent or subagent, which has no gaps. A subagent is named by the ID its agent gives it, such as Claude's `agent_id`, Codex's thread or Antigravity's conversation, since that names the same subagent for as long as it lives, and a message to it can start more of its work after the call that started it has come back. One recorded before subagents had IDs of their own is named by the call that started it, so that's its ID, and the hub finds a subagent by its call as well as by its ID, so a client from before still reads and follows its work. Such a client may miss which subagent asks, and where a message to one goes. A client reads and follows the agent's own events or one subagent's by that place, and recovers as it does by `seq`, so the chat never pages through a subagent's work. The hub also keeps a record of each subagent, changed in the same transaction as the event that changes it: its ID, the call that started it, which its line in the chat is drawn for, what it's for, what it was asked, whether it's working, when it started and ended, the model its newest reply came from, how many calls it's made, about how many tokens the agent last said its conversation holds, its report, and while it works, what it's done lately: its newest few calls, typed, with what came back and what it wrote just before each, the texts cut short, since every change to a record goes to every client. A session's subagents are listed apart from the other records, since a session can have many, and the feed says when one changes. A subagent that never said it ended went with its agent, so the agent's exit ends it. One the agent says started again after it ended, as Claude's does when it's messaged, and Codex's with a follow-up turn, works again, under the call that first started it and with what it was first asked, and has no report until it ends again. So the chat draws a subagent's call from the record that keeps that call, without reading its work, and opens its tab by its ID, and every client shows the same. The chat follows the agent's own events, and the subagent tab one subagent's. From a hub that can't read by place, the agent's own events are every event, read by `seq`, and there are no records, so the chat gathers each subagent's work into its call from the events it has loaded, as it did before, until a new connection reaches a hub that can. The agent says what a subagent's conversation holds unasked, on a line of its output, which the log keeps anyway, so that's an event, which changes the record as the others do, where what the agent's own context holds is an answer the worker asks for. *Unconfirmed:* the tokens, and a subagent that starts again working again.
- **A compaction is asked of the hub, and what it answers is recorded, not worked out.** A client asks the hub, which records a `CompactionAsked` and passes it on, and the agent's adapter asks the agent in its own way, since that's the agent's to know, such as Claude's `/compact`. The hub refuses one while the agent is on a turn or has a prompt it hasn't taken, since the agent would only compact once that's done, and before the agent has had a turn, since there's nothing to compact. The agent takes it or drops it as it does a prompt. Only the adapter knows which recorded request each line it sent is, and whether the turn that followed did anything else, so it names the request on the compaction, with what it said to keep, and marks the end of a turn that was only that compaction. A client draws each from its own record, rather than searching the events around a prompt for the compaction that answered it. What the hub refuses one on is on the session's record: the prompts the agent has yet to take, a compaction asked for included, and whether it has had a turn, so a client can tell whether one can be asked without asking.
- **What the API's cache holds of a chat's conversation is on its record, and a prompt that found it expired is in its log.** Only the adapter knows its agent's format, so it says of each of the agent's own requests what it read and wrote, for how long, how long ago it was sent, and whether it's the first request for a prompt. The hub times it by its own clock and keeps what the newest left on the session's record, which moves the record's revision. The feed announces it with the turn's end rather than with each request, since a turn makes many, and at once when the agent isn't working. The hub records a `CacheExpired` when the first request for a prompt read less than half of what the request before it left in the cache, since only the hub knows what that was and when it was sent, whichever process sent it. A compaction, choosing another model, or a launch under a login the hub holds for another account than the session last named, or a move to one, leaves the record with nothing cached, since another account's cache may not hold the conversation, as one in another organization doesn't. A launch under a machine's own login, whose account the hub learns only after, isn't seen to change account. A client works out from the record only how long is left by its own clock, as the working line counts a turn. *Unconfirmed.*
- **Why the agent picked up by itself is recorded as the turn starts, when the agent's adapter can tell then.** Only the adapter hears what its agent took in, so it records an `OwnTurn` after the start of a turn the agent started with no prompt, naming each of its own background tasks it heard had ended that no request had taken in, and how. A turn whose reason the adapter can't tell as it starts, such as one started by what a monitor watches for happening, has none, rather than one it guessed. The hub adds what it keeps of each wait among them, what it watched and how it ended, since the agent hears only the tool's answer, and not the whole wait, whose snapshot of every pull request would become part of the log's stored form. A client draws what started the turn from it, rather than working out from the log which task's end came before. *Unconfirmed.*
- **How a chat's newest turn ended is on its record,** beside where it ended, and changed in the same transaction as the turn's end, so a client tells a chat whose turn failed from one that finished by its record, without its log, as the sidebar does for every chat. A chat stopped short when its agent went away mid-turn or its newest turn failed, until a turn starts again, and every client shows it the same. The adapter says of a turn that failed on the agent's own failed request to its model that it did, since only it knows how its agent says one, so the chat draws the request's card and nothing more for the turn.
- **That a failed request repeats the one before is recorded, not worked out.** As the hub records one of the agent's own failed requests, it says in `again` that it's the same failure as the agent's own failed request before it, which that was and how many times in a row it has failed, when nothing between them ended the row. A subagent's events don't, since its tab shows them, and neither does what the agent does by itself that comes to nothing else, such as a turn it started as a task ended that failed too or said nothing. What the log records of the person ends the row, a prompt or Retry among them, and so does anything the agent says or does, and the agent going or starting. A client holds a chat's log in pages, so one counting failures in a row would count them again as each page loaded, and every client would have to count them the same way. The hub works it out from the log alone as it records, so a session started again, as when the hub starts again, reads where the row stands from the log, rather than from a copy kept beside it. *Unconfirmed.*
- **A queued prompt belongs to the hub, on its session's record,** so it's sent when a turn ends with no client there, and every client shows the same queue. The hub sends it once the agent is idle and has taken every prompt it was sent, because one sent sooner folds into the turn the agent is about to start. Whether the queue is held is on the record too, so a restart neither sends what the person stopped for nor holds what they didn't, and a starting hub sends any queue left ready. A queued prompt's files are added to the session as it's queued, and the hub keeps them until it's sent, as it does any prompt's. *Unconfirmed.*

## Wire format and event log

Details are in `crates/protocol/`.

- **Newline-delimited JSON over any byte stream,** with a Unix socket or Windows named pipe for local clients, TLS for paired remote clients, and stdio for workers. It works over anything, it can be read by hand, and agent output is already JSON.
- **Versioning:** both sides say hello first and agree on a protocol version. `docs/principles/protocol.md` says how, and what needs a bump, which is rare.
- **`hub_status`, `hub_shutdown` and `hub_restart` work without a hello,** so a client of any version can see a hub, and stop or restart it. That's how `roundhouse hub status`, `roundhouse hub stop` and the app's `Restart the hub` work across a real break, and how the app restarts a hub to update it, and it's why the app can say how many agents would stop. Anyone who can reach the socket is this user. A connection from elsewhere, once there are any, shouldn't get this. *Unconfirmed:* `hub_restart`.
- **On Windows a client's byte stream is a named pipe,** since neither tokio nor stable Rust has Unix sockets there. A pipe has no place in a directory, so it's named for the hub's data directory, one for each, and a checkout's hub stays out of an installed app's reach. The name comes from the path as it's spelled, so the data directory has to be an absolute path there. It has the permissions Windows gives a pipe by default, which let this user, administrators and the system send requests, and anyone else only read. Another user on the machine can make a pipe of that name first, and a client takes it for its hub and sends it prompts, so this isn't safe on a machine with other users. A client checking who serves the pipe would close that. *Unconfirmed.*
- **The database only migrates forward.** Migrations run in order, each in its own transaction, and a database from a newer build is refused rather than damaged.
- **A hub saves a copy of the database before migrating it,** and doesn't start if it can't. Any update can bring a migration without anyone choosing it, and the build before can't open what it leaves. The copies are in `backups/` in the data directory, and each of the last three schema versions copied keeps its newest, so retrying an update that stopped part way can't push out the copy from before it. *Unconfirmed.*
- **The agent's adapter says what each line its agent writes is, and what leaves nothing in the record isn't stored.** Only the adapter knows its agent's protocol. Each line it knows becomes an event, live output such as a delta, or nothing: a heartbeat, a notification of what a finished item says whole, or state the agent keeps for its own interfaces. It names each kind it drops, with why, rather than dropping by a pattern, since a dropped line is gone. A line it doesn't know is an `AgentOther`, with its raw line, for a later build to translate, so `AgentOther` is what isn't understood yet, not a place for what is. The hub records what it's sent, and an event's place says whose it is, not whether it's worth showing. Whether an event draws anything is the client's to say.
- **Each event has a normalized body, plus the agent's raw line in a separate column.** Agent output is untrusted input, so `agents::claude::normalize` takes any line without panicking. Clients read the normalized form. The raw line means views can be rebuilt if normalization was wrong, and range reads don't load it. An image a tool sent back is the one thing left out of it: the adapter puts the ID of the attachment that keeps the image wherever its base64 was, so a rebuild finds the image among the session's attachments rather than in the line. The CLI sends a read screenshot twice in one line, as about a megabyte, so kept whole, a few dozen reads can outweigh every other line in the database. *Unconfirmed.*
- **The agent's adapter types each tool's use,** as a `Call`, such as a command, a read, an edit, a search or handing work to a subagent, since only the adapter knows the agent's tools, and what came back for it as a `CallOutput`. It does so for the call, its result and a request for approval, and the hub copies them onto a subagent's record of what it did lately. A client draws kinds of call rather than tools, and needs no agent's names for its tools: a tool of no kind of its own is a `Call::Other`, by the agent's name for it and with its input, and one from an MCP server a `Call::Mcp`. A result holds what came back alone, with how a command exited beside it rather than in its text. Claude's adapter reads a result for a call it no longer knows, such as one the agent answers after it was started again, as a command's when it says how one exited, and as the agent's words otherwise. What Claude's adapter recorded before it typed its calls is typed by the hub, by its `untyped` module, as Claude's adapter would have typed it: once in the `typed_calls` migration, and each such event a worker of a build from before sends, as it comes. So no client reads a call in an older form, and that module is the only place that knows the forms from before, which it reads and never writes. *Unconfirmed:* which kinds there are, in `protocol::capability::calls`, their stored form, and typing what was recorded before in the hub, once, rather than in every client.
- **How full an agent's context is isn't an event.** The worker asks the agent as it works and sends each answer in a frame of its own, with its run, and the hub keeps the newest on the session's record, if it's from the run going and says something new. Only the newest matters, nothing in the log would read it, and the answer it comes from holds much that's personal, so there's no raw line worth keeping. *Unconfirmed.*
- **An agent trying a failed request to its model again isn't an event.** Its adapter sends which try comes next, of how many, the status the last try failed with and how long it waits, as live output, which the worker and the hub keep in the session's tail beside what the agent is writing, and send to each client with it. Only the newest matters, and only until the agent writes again, its request fails for good, or its turn or run ends, which `protocol::tail` says, so the hub and every client agree when it's over. A hub sends the tail whole to each subscriber when it changes, since no delta says it.
- **What an agent hears of its account's limits is an event, and the newest is on the account's record.** The agent was told it as it worked, so it goes in the log, and the hub also keeps the newest by account, which the feed announces whenever what's left or when it resets changes. Claude's CLI says it only once a process, so the worker also asks it while it works, at most every five minutes, and sends the answer in a frame of its own, as it does how full the context is, and the hub keeps it the same way. Hearing the same again isn't a change to the record, though the hub keeps when it was heard, so something heard earlier never replaces it. The line doesn't name the account, so as each launch starts, the hub learns which account the agent runs under. For a launch it gave a login, its own record says. For any other it asks the session's worker, and keeps who it is on the account's record. Either way, the session's record names the account. So limits are kept and read under one name, and every client sees them as soon as any agent under the account hears them. *Unconfirmed.*
- **Live deltas aren't stored.** The finished message arrives as a durable event and replaces them. A client attaching mid-message gets a snapshot of the streaming tail, then deltas, and `protocol::tail` holds the rules so the hub and clients can't disagree. A worker applies them too, to what its agents are writing, and a hub that connects to it gets a snapshot of that in the same way. *Unconfirmed.*
- **Subscribers read from the log, and live updates only say that it moved.** A slow client can fall behind and catch up without losing anything, and it holds back only itself.
- **A status change commits in the same transaction as its event,** so a client reading status after an event can't see an older value.
- **Prompts carry an optional `client_msg_id`,** and the same ID is only recorded once, so a client can retry safely after a disconnect.
- **A prompt's files go to the worktree, and the hub keeps only what the transcript draws.** A client adds each file to the session with an ID it chose, then sends the prompt naming them, so a retry sends nothing twice. The prompt's event records each file's name, kind and size. The hub keeps the bytes as files in its data directory rather than in the database, which it copies before every migration. Before the prompt reaches the agent, the worker writes each file into the worktree, and then the hub lets go of every one that isn't an image. A client reads an image with `attachment_read` when it draws one, so the transcript doesn't need the worker, and still has its images after the worktree is archived.
- **A file waiting in a composer is added to its session as it's attached, so the hub keeps it with the chat's draft,** which names it by its ID. The hub leaves out a file it hasn't got, so a client adds each before the draft that names it, on the thread that keeps drafts, and reads them back with `attachment_read` when it next opens the chat. A client names a draft's files only by their IDs, and the hub reads what each is from its own record. Setting a draft never lets go of a file, so emptying it as a prompt is sent can't take a file the prompt is about to carry. A client that takes a file off asks the hub to let go of it after the draft that stopped naming it. Closing a chat lets go of every file its draft named, along with the draft, and the client asks the hub to let go of any of its composer's that reached the hub after. The hub keeps a file anyway while the draft, a prompt waiting in the queue or a prompt that was sent names it, or once it's in the worktree, and it never lets go of an image from the agent, since it records whether a client added each file. A chat closed with nothing sent goes altogether, files and all. One left over otherwise, such as by a client that stopped before it asked, stays with the session. *Unconfirmed.*
- **An image a tool sends the agent is an attachment of the session too,** such as a screenshot it reads, so it's kept, read and drawn the way a prompt's image is, by the same code. The worker gives it an ID, since it's the first to have it, as a client is for a prompt's files, and sends its bytes beside the event whose result names it. The hub keeps them before it records the event, so a client never asks for an image before the hub has it. *Unconfirmed.* An agent that names an image only by its file, as Codex does one it looks at or makes, has its adapter read the file, wherever it is, and keep it the same way, if its bytes are an image of no more than 32 MB, as the worker reads an image an agent's text links to. The chat then draws what the model saw or made after the file has gone, and from another machine. Codex saves an image it makes in its own home, which moves only with its login and threads, so the image is read from there.
- **An image the agent's text points to in the worktree is kept by the hub, as it was when the text came,** such as `![The board after](docs/screens/board-after.png)`. The worker reads each as the finished message passes through it, and only an image inside the worktree, since what an agent writes is untrusted: it follows every link before checking the file is in the worktree, and refuses anything that isn't an image the transcript draws. It gives each an attachment ID and sends its bytes beside the event, as it does a tool's, up to 128 MB for one event, since an event and what it carries travel in one frame. The text's block names each by the address it was written with, which is what a client looks it up by. So when the agent changes a file and points to it again, each reply keeps what it showed, and every client shows the same, after a restart and after the workspace is archived. One that wasn't there when the text came shows nothing, and so does one in a text recorded before the hub kept them. The agent's line doesn't say which images the worker read, so the event's body is their only record, and a rebuild from the raw lines has to carry them over from it. *Unconfirmed.*
- **A diagram the agent writes in Mermaid is drawn by each client from the text, and nothing of it is kept but the text.** A client draws a code block written in `mermaid` in a reply, a plan or a proposal as a picture, on another thread, so the hub, the worker and the protocol carry nothing for it, and a client that doesn't draw them shows the code. The desktop app draws one as SVG with `merman`, in Rust, with no browser or JavaScript, within 2 seconds, in the app's colours, and measures its words with the font GPUI draws them in, and then draws the SVG as it draws an image the text points to. *Unconfirmed:* `merman`, the 2 seconds and the colours.
- **A session's prompts are listed on their own, a line each,** with `session_prompt_list`: where each is in the log, and among the agent's own events, the start of its text on one line, and how many files it carries. A client holds only a window of a long session's events, so this is how it can show every prompt to jump to. It asks once, as soon as its subscription has started, and adds each prompt the subscription brings. Between them they miss none, since every prompt before where the subscription starts was recorded before the list was asked for. The list is best effort, since the chat matters more than its outline: a hub too old to list them isn't asked again, and its client shows only the prompts its window holds, and any other failure is reported as a page that fails to load is, and asked again on the next connection, while the chat goes on. Each line also says where the last event to take or drop its prompt is, since a chat draws the prompt there, so the outline can jump to one whose events aren't loaded, and one from a hub that doesn't say leaves the client to find that event in its window. The hub reads only prompts and the events that take or drop them, by their kind, and of each prompt only its place, its text and how many files it carries, so a long session costs no more than its prompts' text does. A chat's rows go by the agent's own events, so its outline puts a prompt at its place among them, or at its `seq` from a hub that can't read them apart, and a client that comes to a hub that can asks for the list again, for its places. A client tidies each line again as it reads it, as it does a title, so a hub that tidies differently can't put a second line, or one that reads backwards, in a row. *Unconfirmed.*
- **A session's compactions are listed the same way, a line each,** with `session_compaction_list`, so a chat's outline can mark every one, however far back. A line is a compaction of the agent's own conversation that compacted, since one that failed changed nothing: where it is in the log and among the agent's own events, who started it, and how many tokens the context went from and to. The hub reads only compactions, by their kind, and leaves out the summary each carries, which is long. A client asks for it as it does the prompts', once its subscription has started, and adds each compaction the subscription brings, but asks for each list on its own, since a hub can be new enough to list prompts and too old to list compactions. A hub too old leaves only the compactions the client's window holds. *Unconfirmed.*
- **Finding text in a long chat starts at the hub, and ends at the client,** with `session_find`: the hub says which of the events a view follows hold the text, the agent's own or one subagent's, by their place among them, as `protocol::find::Needle` matches it, and how far it looked. A client holds only a window of a long session, and only it knows what each event draws. So client-core's search asks the hub, and reads the stretch of those events around each one it named, by place as the log is, a stretch at a time, for a view to count what those rows draw and let go, and a view counts what the rows it holds draw itself, as they load and change, whatever the hub has said. The hub passes over an event's stored JSON when it can't hold the text, and reads the rest, on a read connection of its own, so a long look doesn't hold up the pages every client loads. A chat has one search at the hub at a time, and one typed over by its turn isn't asked, so typing doesn't queue looks through the whole chat. It looks past what Markdown marks text with and how much whitespace there is, so what it names is never less than what a client finds. One character isn't asked, since it's in nearly every event. A hub too old to look isn't asked again until there's a new connection, which may be to a newer one, and the client counts only what it holds. Nor is one followed by `seq`, which only a hub too old to read by place, and so to look, is. *Unconfirmed.*
- **A worktree's files are listed and read through the hub, and only inside the worktree.** All files lists them with `workspace_files`: tracked, new and ignored, with a folder git ignores whole, or that's a repository of its own, a submodule included, listed as a folder, since one such as `target` can hold hundreds of thousands of files, and so is a link that leads to a folder, which git lists as a file. `workspace_folder_read` lists what's directly in such a folder when it's opened, `workspace_file_read` opens a file, and `workspace_file_read_at` opens one as a commit held it, which is how the file tab shows the side of a change the diff was taken from. For the lines a diff leaves out, the diff opens the file as the commit held it with `workspace_file_open_at` instead, and reads it a page of lines at a time with `workspace_file_pages`, which asks for pages with as many lines as the open said, so a page is the same lines whichever build of the worker reads it. A file small enough to send whole comes whole when it's opened, none of its lines cut, and one too big is read as its lines are to show, a line over 16 KB cut short there and saying so. A commit named by its full object ID holds the same file for good, so what's read of it never goes stale. client-core's `OpenFile` opens it, fetches the pages a view wants on a thread of its own and says when they've come, opens it again on a new connection if it couldn't before, and doesn't ask a hub too old to open files again, and its `FileText` holds what's been read and says which pages to fetch, asking for each once. So every client reads a file the same way. The worker keeps nothing between reads: each streams the file from git, keeps only the pages asked for, and stops once it has them, and opening one streams it to its end, to count its lines. Each says in the worker's log how much it streamed and how long it took, so whether the worker should keep an index of the files it opens can be decided from there, as `docs/reference/performance.md` says. *Unconfirmed.* These take a commit only by its full object ID, so it can't be read as an option or name a branch that's moved since, and find the file by its name alone, never as a pattern. The hub passes each to the worker, which takes only a path as a list gives it, relative, with names between single slashes and none of them `.` or `..`. In the worktree, it follows every link before checking the file or folder is in the worktree, as it does for an image, but reads any file there, since a person chose it rather than the agent's text. At a commit, it follows no link, so a link reads as the path it leads to, which is what the commit holds, and nothing outside the commit is read. It lists at most 50,000 files at once, leaving ignored ones out first and then new ones, so a file git tracks is never left out to make room, sends at most 4 MB of text, whole pages of it when it's some of a file's pages, and 64 MB of an image, which it knows by what the file starts with, reading only the start of a file bigger than text's limit to tell, and says when a file is bigger, or is neither, rather than sending it. *Unconfirmed.*

## The worker's git credential

Agents push and open pull requests with whatever git and `gh` find, so the hub sets what every process a worker starts uses for github.com, from the default GitHub account, rather than leave it to each machine's own login.

- **It's worker state the hub sets on each worker's link, with `GitCredentialSet`,** not a field of each launch, since a workspace's worker needs it without any launch, for its clones and fetches, its reads of pull requests and its scripts, and a token that ends has to be renewed under an agent that's running.
- **The hub works out what every worker is sent in one place, from its own state, under the GitHub logins' lock, as each change to them is made:** the machine's own while the default is, the default's username and token, read from its file, a sign-in's access token as a token's, while its login can be used, with its commit identity, and otherwise a block, whose reason says why and what to do in Settings: renew the account, connect it again, sign in with GitHub again, or choose another default. So connecting, renewing or disconnecting the default, a sign-in approved as it or making it, the hub renewing its sign-in's token, or asking GitHub again who it is, choosing another, and the default's token ending each change what every worker is sent. A default that's an app's installation is sent as `x-access-token`, with the app's bot as its commit identity, as below, and blocks once its token ends, saying the hub is making the next, and once it's uninstalled there, saying to install the app again. A default that's a sign-in's blocks once its access token ends, saying the hub is renewing it while what renews it hasn't ended, as after a Mac wakes from a sleep past the token's end, until a check renews it, and once it needs signing in again, saying to sign in again. A default whose record or file the hub can't read blocks too, never the machine's own in its place, and so does one whose file is in a form only a newer build reads. *Unconfirmed:* a default the hub can't read blocking.
- **The hub sends it as each link opens, queued right behind the hello, before the hello's answer, and waits for the set's answer before the link is used,** so nothing reaches the worker before it, not even what answers the worker's first ask, which can come with the hello's answer. After that, each link follows it on a task of its own, through a `watch` that every change writes under the lock, and sends each it sees once the worker has answered the last, so each link gets the sets in the order they were made, a slow worker holds up only its own link, and one that's applying a set when two changes come is sent only the newer after it. Nothing is sent to a worker under the lock, and nothing that changes the logins waits on a worker. *Unconfirmed:* the `watch`, and queueing the set before the hello's answer, which a worker whose hello then fails is sent too.
- **A worker has ten seconds to answer each set, and one that doesn't, or that answers anything but `Unsupported` or `Unavailable`, is ended, as one that doesn't answer its hello is,** so it can't go on pushing as a default that's since been disconnected. As when any worker goes, its sessions are told, and the next worker started there is sent the credential as its link opens. One that answers `Unsupported`, as a worker from before `GitCredentialSet` does, is said in the hub's log once a link, one that answers `Unavailable` each time, with why, and both are used on, with the machine's own.
- **The hub checks the GitHub logins by the wall clock, as it starts and every minute after: whether the default's token has ended, and which sign-ins to renew,** rather than waiting until a token's end, since tokio's timers don't count the time a Mac sleeps, so a wait would come late by as long as the Mac slept. So a token's end reaches every worker within a minute of it, or of the Mac waking, and a sign-in slept past its token's end is renewed then. Each check also makes the next token of each app's installation that's due, looks for where each app is installed, and asks GitHub who each token's and sign-in's account is that it last asked a day before or more, or never, all at once with its renewals. Each check waits for the renewals it starts, each within the call's time limit, before the next. *Unconfirmed:* once a minute.
- **The worker applies each set on its connection's own loop, as it handles a hello and a stop, before it reads the next frame,** so sets apply in the order sent, a link's last applies before the worker serves the next link, and what's asked after a set is answered has it.
- **It's the machine's own, an account, or a block.** Under the machine's own, the worker writes nothing that changes what git or `gh` use. An account is a username and a token, and a commit identity, a name and an email, which the git config sets as git's own in a repository on github.com, so `git commit` works there on a clean machine or VM with no git config of its own, and commits are by that GitHub account rather than whoever the machine's own git config says. Any added account can carry one, however it was connected. For an app of your own's installation it's the app's bot, with the address GitHub links to it, `<bot's number>+<slug>[bot]@users.noreply.github.com`, so commits, pushes and pull requests all say the bot, and its username is `x-access-token`, as GitHub's docs give git for an installation's token, which is the user `gh`'s `hosts.yml` names too. For a token's or a sign-in's it's the name the account's user goes by on GitHub, or its username when it has none, or one git won't commit as, such as one of only `<` and `>`, as the owner decided, and the email its profile shows everyone, or else `<number>+<username>@users.noreply.github.com`, which GitHub links to the user whatever it's named later, as GitHub said when the hub last asked. The email is as the owner decided too, and is never the primary email a sign-in's `user:email` reads, since GitHub refuses a push of commits by it when the person keeps it private and has GitHub block pushes that expose it. One the hub hasn't asked about carries none until it has, so it commits as the machine's own git config says. An older worker reads past the commit identity, so it pushes and opens pull requests as the account, and commits as whoever the repository's or the machine's own git config says. *Unconfirmed:* `x-access-token` for `gh` too. A block has a reason that says what to do, and is what the hub sends while the default was disconnected or its token ended, so agents push as nobody rather than as the machine's own. One of a kind the worker doesn't know, from a newer hub, blocks too, saying the hub is newer, and is refused as `Unsupported`, as a value a reader doesn't know is. *Unconfirmed:* refusing one it blocked for.
- **The worker hands it on with files it rewrites, in `git-credential/` in its state directory, which only its user can open:** a git config file, given to every process as `include.path` in `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_0` and `GIT_CONFIG_VALUE_0`, which git reads again on every run; `identity`, beside it, which says who commits are by, for a credential with a commit identity; a `gh` config directory, given as `GH_CONFIG_DIR`, whose `hosts.yml` has the account logged in, as `gh` writes it with the token in the file, or, for a block, a login whose token GitHub refuses, since `gh` takes a token in the file before its own in the system's keychain and goes on to that one when the file holds none, as `gh` 2.103.3 does; and what the worker's credential helper answers with, which is the credential as the hub sent it. Each is replaced whole, by renaming a new one over it, so a process reading one meanwhile reads the last or the next. None is synced, since the worker removes them all as it starts, so nothing reads what a power cut leaves. *Unconfirmed:* the helper's file of its own, which keeps the token out of git's config, where `git config --list` would print it, and not syncing.
- **The git config resets the machine's credential helpers for `https://github.com`, then names the worker's own, and sends `git@github.com:` and `ssh://git@github.com/` to `https://github.com/`,** so a remote over SSH goes through the helper too, rather than push with the machine's key. It's the same for an account and a block, since what the helper answers says which, and whether `identity` is there says whether commits are by anyone.
- **A credential's commit identity is only for a repository on github.com, as the credential is,** since a repository that isn't on GitHub uses the machine's own login, and a commit by the wrong author takes rewriting history to undo once it's pushed. So `identity` holds `user.name` and `user.email`, and the git config includes it only in a repository with a remote on github.com, with `includeIf "hasconfig:remote.*.url:…"`, and a repository elsewhere, such as on GitHub Enterprise or GitLab, or with no remote, commits as its own config or the machine's says. Any remote counts, not only `origin`. git matches each remote's address as the repository's config has it, before any `insteadOf`, so the include names each address the helper is given for: `https://github.com/`, with a user in it or without, and the two SSH addresses the git config sends there, each followed by `*/**`, an owner and then the rest, since `*`, and `**` but after a `/`, take no `/`, so `git@github.com:**` would take none of GitHub's addresses. ## Updating the app

The app is signed and notarized, you download it, and it updates itself as changes land on `main`, so staying current needs no checkout or toolchain. `tools/install.sh` stays the way to install a build of a checkout, as above, for working on Roundhouse.

- **Velopack packages, installs and updates the app.** One tool packages the app and makes its updates for macOS, Windows and Linux, and an update downloads only what changed. Sparkle signs its updates but covers only the Mac, and an updater of our own would have to redo what Velopack does on Windows.
- **The Windows app is an installer you download once, which then updates itself as the Mac app does.** Its binaries are built on Windows, and `vpk` packages them on Linux, which it can for Windows, so the keys stay in the one kind of job that publishes. It has a feed of its own, `releases.win-amd64.json`, in the same bucket and signed with the same key, and jobs of its own, so neither platform's release waits on the other's or fails with it. It installs for one user, in `%LOCALAPPDATA%\Roundhouse`, without an administrator. Nothing signs it, so Windows warns whoever downloads the installer. ARM64 Windows gets the same, built on an ARM64 runner and published under a channel of its own, `win-arm64`. An app looks for updates in the channel it was packaged for, so each gets its own processor's. One packaged while amd64 Windows' channel was `win` still looks there, so each amd64 release also signs `releases.win.json`, offering only its own full package. Such an app takes it as an update, and since that package was made for `win-amd64`, it looks there from then on. *Unconfirmed.*
- **The Linux app is an AppImage, which updates itself as the Mac app does.** It's one file that runs on most distros without installing, and the one package Velopack updates on Linux. Flatpak's sandbox would keep the app from the host's git, shells and agents, which it runs all the time, and a `.deb` or `.rpm` would hand its updates to a package manager. Its binaries are built in Ubuntu 22.04, so they need no glibc newer than 22.04's 2.35, and the app runs there and on every distro since. It can't be wholly static, since GPUI loads the system's Vulkan driver, which is built against the system's glibc. `vpk` packages it on Linux, in jobs of its own, with feeds of its own: `releases.linux-amd64.json` for amd64 and `releases.linux-arm64.json` for ARM64. Velopack moves the new AppImage over the old one, and where this user can't change the folder it's in, asks for an administrator's password through `pkexec`, so the app says it can't update there instead, as "Nothing about updating is a native dialog" in `docs/spec/updates.md` needs. Velopack would keep downloads in `/var/tmp`, which every user on the machine shares, so the app has it keep them in the data directory. *Unconfirmed:* that check, and where downloads go.
- **CI builds, signs and publishes every merge to `main`.** The merge queue has already run the checks on Linux by then.
- **A published build is versioned `0.1.<commits on main>`,** such as `0.1.50`, which is what Velopack orders updates by. It's short and readable, every merge adds one, it leaves 0.2 and 1.0 free to mean something later, and each part fits the 16 bits of a Windows version field. A count can't be the build number, because counts differ across branches, but only `main` publishes, and its history only grows.
- **The update feed is signed, and the app checks the signature before trusting anything in it.** Velopack only checks each package against a checksum in the update feed, so without a signature, whoever controls the host controls the app.
- **The update feed keeps the newest 10 releases, and, for good, the last release before each break in the worker protocol.** Each release's full package says there which versions of the worker protocol its hub speaks, which only the build can say, so `tools/build.sh --package` asks the daemon it has built, with its hidden `worker-versions` command, on the platform it was built for. A hub speaks no worker version older than the one before its own, so the last release before a break is the newest whose hub speaks the workers from before it. That's the release an app steps to while workers that old are at work, so the update ends none of them. The release workflow can pass over a build for a newer one, so a change whose hub doesn't speak the workers of the newest release published for each platform whose apps step waits in the merge queue until it does, which `tools/update-steps` checks, reading each one's feed, for a change to the worker protocol. A Windows hub's workers stop with it, so its apps take the newest, and its feeds aren't checked. Should such a change get past the check, `tools/package/publish.py` refuses it, and each release after it, on a platform without the step, and only reverting it gets that platform publishing again. Velopack reads only the fields it knows, so an app from before stepping reads the feed as before. *Unconfirmed:* the hidden command, and which changes the check runs for.

## Providers

Every provider has an adapter: a program the hub runs, which makes and ends the provider's instances. The hub talks to it over the provider protocol:

| Operation | Purpose | Required |
|---|---|---|
| `create` | Make an instance, from a base image and at a size where the provider takes them, and place the worker binary in it | Yes |
| `start`, `stop` | Wake and sleep. Stopping also ends anything the worker left behind | Yes |
| `kill` | Like `stop`, without giving a worker that isn't responding time to finish | Yes |
| `connect` | Return the command that opens a byte stream to the worker | Yes |
| `open_preflight` | Return the command that opens a byte stream for preflight in the prospective launch environment | Optional |
| `destroy` | Remove the instance | Yes |
| `list` | Say which instances exist, so a hub that starts finds those that outlived it | Yes |
| `make_base_image` | Turn a stopped instance into a base image, which other instances are copied from and which can't start again | Optional, declared by the provider |
| `snapshot`, `restore` | Preserve or roll back the filesystem | Optional, declared by the provider |

An adapter also tells the hub, unasked, when an instance is about to end or has gone, such as when a cloud takes back a spot instance or a host goes down, rather than leaving the hub to find out when the worker's stream breaks.

- **Workers only need a byte stream.** `connect` answers with a command, and the hub runs it, with its stdin and stdout as the worker's stream. That can be `incus exec`, SSH or anything else, including the adapter's own program where it has to carry the stream itself. The hub dials out, so workers don't need to reach the hub, and an adapter that carries no streams can stop without taking its workers with it.
- **Every worker has a state directory, which its provider names in the command `connect` answers with.** The worker claims the instance there, so it has one worker, and keeps there what has to be outside the worktree, where the agent and git would see it: the record of each agent, setup script and one-off call it runs, the log of the setup and archive scripts, and the files each run's CLI reads. So the daemon's `worker` takes `--state-dir` however it reaches its hub. A local instance is a directory, and is its worker's state directory. *Unconfirmed.*
- **An adapter is a separate program, over stdio.** The hub runs each as one long-lived child, beside itself, and starts it again if it stops. Instance operations name their instance. A request to open preflight names the project and the kind of agent. The provider can relay the stream using its own transport. The hub and the process at the other end speak the preflight protocol. Both are safe to repeat after a restart. Adapters can be written in any language without rebuilding the app, and one written in Rust implements the `Provider` trait and has `providers` serve it. A gRPC API may come later, so the contract is defined as messages, independent of the transport.
- **The local provider's adapter is the daemon's own `provider local`,** so it ships with every hub, and its instances are directories and its workers processes on this machine.
- **A local worker runs on its own, so it can outlive its hub.** The local provider's `connect` answers with the daemon's own `worker --attach`, which connects its stdin and stdout to the worker serving `worker.sock` in its state directory, and first starts that worker if none is serving it. The worker is in a session of its own, so nothing that ends the hub, or the command the hub runs, reaches it. It runs in its state directory, and it and the command name the socket relative to it, since a socket's path can be at most 103 bytes on macOS and a state directory's can be longer. A worker that's stopping removes its socket first, and while it still holds the instance the command fails rather than starting another, since it may be stuck, and the hub ends it, as it ends whatever it finds on an instance it doesn't know of. On Windows, which has no Unix sockets in tokio, a worker still runs on its hub's pipes, so it stops with its hub. *Unconfirmed.*
- **An adapter keeps its own access to where it runs instances,** such as the Incus client's remotes or the usual AWS credentials, so the hub holds no secrets for it. The hub's settings name each provider, the command that runs its adapter, and which one new workspaces go to. *Not built:* until they do, `providers.json` in the hub's data directory names them, and the hub reads it as it starts.
- **Stopping a worker is split between the hub and the adapter.** The hub closes the worker's stream and gives it time to stop its agents, which works the same over any transport. The adapter then ends the instance and anything the worker left behind: for the local provider, the worker's process group and every process recorded in its state directory, such as its agents, each with its group, and for Incus, the VM.
- **A worker always runs its hub's build.** Starting a worker puts the hub's worker binary in the instance first, if it holds a different one, so an instance that slept through an update doesn't wake with an old worker. The only older worker a hub meets is then one that outlived the hub before it, which it replaces once nothing in its workspace is at work, as `docs/principles/protocol.md` says. The local provider has no copy to replace, since it starts the hub's own executable. *Unconfirmed.*
- **Providers declare their capabilities,** such as which systems and architectures they run, whether the filesystem survives a stop, and whether they build base images or take snapshots. Persistent instances don't need snapshots to sleep, while ephemeral sandboxes do.
- **Providers also declare their workers' environment at hello, apart from their capabilities:** whether workers share the hub's filesystem (`WorkerFilesystem::Hub` when they do, `Separate` when they don't) and whether a repository's clone survives archiving a workspace (`ClonePersistence::Persistent` on a single host, `Ephemeral` on VMs, sandboxes or a pool of machines). Omitted defaults to `Separate` and `Ephemeral`, so an adapter that doesn't declare one never receives a path on the hub's disk. At workspace creation, the hub settles the workspace's `RepoSource` and `WorkerEnvironment` and records them on the workspace in SQLite (not on the client-facing record), so later launches, terminals, setup, archiving, restoring and child worktrees never contact the adapter or flip between a checkout and a clone if the repository or adapter changes. On `Separate` compute, the hub sends `RepoSource::Clone` with the repository's remote address (never a hub checkout path), sets `CONDUCTOR_IS_LOCAL=0` and omits `CONDUCTOR_ROOT_PATH`. On `Hub` compute, a checkout is used when the repository has one (with `CONDUCTOR_ROOT_PATH` pointing to it) and `RepoSource::Clone` otherwise (omitting `CONDUCTOR_ROOT_PATH`).
- **An archived workspace on ephemeral compute keeps its unpushed commits in a capped hub bundle.** Before removing the worktree and destroying an `Ephemeral` workspace's instance (when its repository source is a `Clone`, never for a hub checkout), `CaptureArchive` captures every local branch and a git bundle of commits not reachable from `origin`'s default branch (`--branches --not refs/remotes/origin/HEAD`), capped at 128 MiB raw (`MAX_ARCHIVED_BUNDLE_BYTES`). Above the cap, archiving refuses with `NeedsForce` (combined with any uncommitted-work losses before touching the worktree) unless forced, in which case the oversized bundle is omitted (`bundle_omitted: true`). The hub writes the raw bundle to `bundles/<workspace_id>.bundle` and hub-owned metadata to `bundles/<workspace_id>.json` atomically before calling `RemoveWorkspace`, closing the worker and destroying the instance, and completes archiving even if `provider.destroy` transiently fails (leaving the instance `Destroying` for startup or restore to finish). Restoring creates a fresh instance (or restores in place if an older build archived the workspace without a bundle and left its instance `Ready`), passes the saved payload in `RestoreWorkspace` so the worker ensures a bare clone exists, unbundles the commits, creates missing branch refs without overwriting existing ones (falling back to `origin/<branch>` or `origin/HEAD` if an oversized bundle was omitted) and checks out the worktree, and deletes both files once `Ready` is committed in SQLite. On hub startup, each interrupted ephemeral move settles its own unfinished instance (`Creating` or `Destroying`) without holding up local workspaces, and stale bundles are tidied once moves settle.
- **A remote workspace runs in a VM of its own, made from its repository's newest base image, and destroyed when it's archived.** A VM is as flexible as a real machine: an agent can run containers in it, and the services and kernel features its project needs, which are hard to get from inside a container. It's also a stronger wall between workspaces whose agents run unattended with credentials, and nothing one workspace leaves behind reaches another. A base image is a VM that a script of the repository's own has set up, with its tools installed and its caches warm, so a workspace made from it starts with a warm build rather than a cold one. *Not built.*
- **Availability follows the hub.** A hub on an intermittently available machine, such as a Mac, is only reachable while that machine is awake. Agents on remote workers keep running and catch up later. Persistent mobile access needs a hub on an always-on machine.
- **Each workspace gets its own worker process and provider instance,** so a crash in one doesn't touch the others. This matches sandboxes, where each workspace has its own machine. A worker uses about 8 MB, so this is cheap on a Mac.
- **The local provider is inside the hub for now,** which calls it directly, through the `Provider` trait, while it reaches the others through their adapters. The trait has the protocol's requests, one method each, with their rules. `snapshot` and `restore` come with the first provider that uses them.
