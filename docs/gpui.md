# GPUI

How code that uses GPUI is written. `docs/architecture.md` says which crates may use it, `docs/rust.md` covers everything else about how Rust is written here, and `docs/ui.md` covers why GPUI and gpui-kit were chosen.

- **Where the kit doesn't do what's needed, the app builds that piece itself, rather than working around the kit.** A workaround keeps the kit's behaviour and adds code that fights it, and each one makes the next one harder to see. The signs are code that keeps the kit's state alive past where it would let go, a test that pins how the kit behaves inside, something drawn twice to get what the kit won't draw, and a fix that works only while what it fixes is on screen. A piece that's had one workaround is weighed again before it gets a second. The chat's text had all four: it kept the kit's text views alive so rows kept their heights, pinned how much text the kit reads at once, laid each tool's output out twice to draw find's matches under the kit's selectable text, and still lost a selection whenever the row it started in left the window.
- **What's built starts from the lowest layer that does the job, found by reading the kit's source, and stays behind one module.** The kit is pinned, and its source is in Cargo's registry, so what it makes public below its views is there to read, and it's often enough. Below its text view, `editor_host` parses Markdown and draws its blocks for an app that keeps its own selection, and says where each character was drawn. The chat's list is built from GPUI's elements, since GPUI's list couldn't keep the heights it was given. Kept behind one module, a piece can go back to the kit if a later version does what's needed.
- **State that has to outlast its element being drawn is the app's, not the kit's.** The kit keeps a view's state, a transition and a text's selection with the element that draws it, or with the window, over what it painted in that frame. So anything drawn in a list that draws only what's in sight loses that state as it scrolls out of sight. A selection, what's found, a row's height and a place in a list are held by whatever owns the list.
- **`render` does no I/O or blocking.** It reads state the view already holds.
- **Calls on a `client-core` `Client` never run on the main thread,** because they block. Reading or updating what client-core keeps, in a `RecordsFeed` or an `OpenSession`, is fine there, because neither holds its lock while it waits on the hub.
- **A call that changes something goes through `Client::start`, and one that only reads through `cx.background_spawn`.** `start` sends the call at once, on a thread of its own, and returns a `Reply` for a task to await, and the app waits for what it started before it quits. A task only starts on a later turn of the main loop, which quitting doesn't give it, so a prompt sent from one just before quitting never arrives. A read lost that way costs nothing. What's typed and attached in a composer is the exception: `client_core::Drafts` keeps each chat's on a thread of its own, newest first and in order, since a change comes with every key, and quitting waits for it as it does for `start`. *Unconfirmed.*
- **What quitting waits for doesn't need the main thread,** because quitting holds that thread while it waits, for at most GPUI's 200 ms. So it waits on a channel that another thread answers, as `Client::start` and saving settings do, rather than on a task. Quitting from the app, and restarting to update, first wait longer, up to two seconds, for the same, then ask about whatever would still be lost, as `menus.md` says. *Unconfirmed.*
- **A long `render` splits by region of the screen,** into functions that return elements.
- **Focus stays on something that's drawn.** An element left out of a frame keeps the focus, and the window's keys then reach none of the app's shortcuts, so a view that stops drawing what has focus focuses something it draws. *Unconfirmed.*
- **The app binds its keys with `secondary-`, which is Cmd on a Mac and Ctrl elsewhere, through `KeyBinding::load`, which reads it for the platform the app runs on,** as `keys.rs` does, so where it binds an action the kit binds too, such as copy or select all, the two agree. `KeyBinding::new` reads a binding without the platform and panics on `secondary-`. What only one platform has is bound by the platform `cx.platform_info()` says. A test presses `secondary-`, which the kit's test helpers read for the platform they run on, since a test that presses `cmd-c` copies nothing on Linux, where only CI runs it. *Unconfirmed.*
- **A view shown in a dialog asks the view that opened it for things with events, and is told what to show.** It doesn't hold the opener and update it, because what the opener does in its own updates, such as handling a hub's reply, can reach the dialog, and the dialog then updating the opener panics, as it's already being updated. GPUI delivers an event after the update that emitted it. *Unconfirmed.*
- **What can be pressed asks for the hand with `look::Hand`, and what can be greyed out is turned off with `look::Off`,** rather than with the kit's `disabled`. The kit's buttons keep the arrow, and the kit lays a button's own style over its disabled one, so a hand set apart from `disabled` would stay on a button that's off. `docs/spec/look.md` says what gets which pointer. *Unconfirmed.*
- **What shows only while the pointer is over something that takes a click shows with `group_hover`, rather than with state the clickable thing's `on_hover` sets.** Once it's pressed, its `on_hover` says the pointer has left at the first move, and a quick press moves. A button drawn from that state goes before the press is let go, and the release lands on what was under it. `group_hover` asks only whether the pointer is over the group, which a press doesn't change. Where the button has to be left out rather than hidden, as a sidebar row's archive button is so the name keeps its room, the button stops a left press from reaching what's under it, and lets a right press through to any menu there. *Unconfirmed.*
- **What follows a held pointer in the strip along the window's top hides the strip from the pointer with `occlude`,** as Home's search does. On Windows the strip is a title bar to Windows, so a press on it is one on the window's frame: GPUI doesn't capture the mouse for it, and while the pointer is over the strip, every move says no button is held, so a text field there couldn't select by dragging. Over what hides the strip, Windows sees an ordinary part of the window. *Unconfirmed.*
- **What moves follows a value, with its timing from `look::motion`.** It goes from where the value is to where it's set to go, so something turned back partway doesn't jump, it skips the motion under Reduce Motion, and it asks for frames only while it moves. Only something drawn in a loop for as long as work goes on, as a status mark is, asks for frames itself.
- **A value one view draws by follows the kit's `transition`, and one that several views lay out by, or that a view can first ask for partway, is a `look::motion::Sliding`, kept by whatever owns the value and read once for each frame.** The kit keeps a transition with the view that asks, and starts a view that hasn't asked before at the end, so two views asking would disagree, and a view shown partway would jump. A row that a list draws only once it's scrolled into sight is one: it can first be drawn partway through a slide. A value read by each view as it's drawn is read at a slightly later moment by each, so the window reads it as it starts a frame, and the views go by that, as `sides::place` does, and as `reorder::Places` does for the rows of the sidebar and Home.
- **A scroll to somewhere that can move on the way, such as a chat's latest row, is a `look::motion::Scrolling`,** which says on each frame what share of what's left is still to go, rather than where to be. Whatever scrolls moves by all but that share of what it finds is left, so it arrives wherever the place has got to, passing rows at the heights they turn out to have. *Unconfirmed.*
- **Whatever moves comes to rest, and then asks for no frames,** so an idle window draws nothing. A test of something that moves checks that.
- **What a moving value lays out is laid out on every frame it moves, so that's kept to what has to move with it.** Something that only has to look as if it moves is moved, clipped or faded where it's drawn. `docs/performance.md` has what a frame costs.
- **Nothing imports `gpui_kit::*`.** A glob brings in GPUI's `test` attribute, which makes `#[test]` recurse. The lint against glob imports catches it.
