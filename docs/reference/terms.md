# Terms

What this project's words mean. Code, docs and the interface use each word only in the sense given here. A new term, or a new sense of one, goes here in the change that introduces it.

Start with "Easily confused" and "Ending things", which cover the words most likely to go wrong.

## Parts

| Term | Meaning | In code |
|---|---|---|
| Roundhouse | This product: the desktop app, the CLI, and the hubs and workers behind them. Capitalized as a name, and lowercase for a binary, but for the hub's copy of the daemon, `Roundhouse Hub` | `roundhouse`, `roundhoused`, `roundhouse-desktop` |
| Hub | The server that clients connect to. It owns workspaces, sessions and their logs, and leaves the work itself to workers | `hub` |
| Hub installed as a service | A hub on a machine of its own, such as a server, that `roundhouse hub install` registered with the machine's service manager, from the hub's archive. A client updates it when someone says. Not a hub a client starts, which the app updates, nor one someone runs themselves, which nothing updates | `roundhouse hub install`, `Paths::service_current` |
| Worker | The process that does a workspace's work: its agents, git and scripts. It reports to its hub. There's one per workspace | `worker` |
| Provider | A kind of place a hub can run workers, such as this machine, an Incus instance or a cloud sandbox. The local provider runs workers on this machine, and it isn't special, but that Roundhouse always leaves GitHub on it to the machine. Each provider sets up GitHub or leaves it to its machines | `Provider`, `LocalProvider`, `Entry.set_up_github`, `GithubSettings.left_to_machine`, `ProviderSet::leaves_github_to_machine` |
| Instance | Where a provider runs one workspace's worker | `instance_id` |
| State directory | Where a worker keeps its own files, outside the worktree: its lock and its record, its socket when it listens on one, the record of each agent, setup script and one-off call it runs, the setup log, and each run's files. Its provider names it. A local instance is a directory, and is its worker's state directory | `--state-dir`, `worker::Config.state_dir` |
| Provider adapter | The program that makes and ends a provider's instances. The hub runs it and talks to it over the provider protocol, and the local provider's is the daemon's `provider local`. Not built | `Provider` |
| Worker environment | What the compute a provider's workers run on looks like to the hub, declared at hello apart from the provider's capabilities: whether workers share the hub's filesystem (`Hub` or `Separate`), and whether a repository's clone survives `destroy` then `create` (`Persistent` or `Ephemeral`) | `WorkerEnvironment`, `WorkerFilesystem`, `ClonePersistence`, `HelloReply.environment` |
| Client | A program that talks to a hub, such as the desktop app or the CLI. Clients only talk to hubs | `client-core` |
| Agent | The coding agent a worker runs as a child process: the Claude, Codex or Antigravity CLI | `AgentKind`, `AgentProcess` |
| Subagent | An agent that the agent starts inside its own process to do part of the work, such as a search, with a tool call. It isn't one the worker runs. It's named by the ID its agent gives it, apart from the call that started it | `SubagentId`, `parent_tool_use_id`, `SessionEvent::subagent`, `SubagentStarted`, `SubagentContext`, `SubagentEnded`, `Subagent`, `Subagent::lately`, `CallKind::Subagent`, `calls::Recorded::hands_off`, `client_core::calls::agent` |
| Advisor | A stronger model the agent can ask for advice, which reads the whole conversation. The API runs it rather than the agent, and asking it is a tool call | `CallKind::Advisor`, `ToolCall::Advisor`, `agents::claude::normalize::advisor`, `Call::Advisor`, `CallOutput::Encrypted`, `EventBody::ToolCallDropped` |
| Adapter | The code that runs one kind of agent and turns its output into events | `agents::claude` |
| Capability | Something an agent does, for the person or for Roundhouse, whose behavior is specified once for every agent, such as taking a prompt mid-turn | `capability::Capability` |
| Claim | A run's saying, through its adapter, that it delivers a capability, with what the hub or a client needs to know of it, such as whether a rewind puts files back. A claim can need another, as a fork needs resuming | `Capabilities`, `Claims`, `Capabilities::unmet_needs` |
| Report | What a run says that the log has no event for, such as how full its context is, which names the capability it needs and says who keeps it: the log, the session, the account, or nothing | `capability::Report`, `Keeper`, `AgentOutput::Report`, `WorkerFrame::AgentReport` |
| Contract | What a capability promises once it's claimed, whatever the agent does underneath, which its variant's doc says | None |
| Law | A contract a session's log can be checked against by itself, such as a prompt being settled once | `capability::laws::Law` |
| Agent's description | What a kind of agent is called and offers, as its adapter describes it: what the interface calls it, what login a hub can hold for it, and what a run of it claims, such as the models, efforts and approval modes a chat can be given | `AgentDescription`, `AgentDescription::defaults`, `settings::Models`, `ModelCatalog`, `LoginDescription`, `agents::descriptions`, `ClientRequest::AgentList`, `client_core::Agents`, `Snapshot::agents`, `roundhouse agents` |
| Conformance | Whether a version of an agent's CLI does what Roundhouse needs of it, as scenarios played through its adapter check | `agents::conformance` |
| Scenario | Steps a driver takes with an agent, and checks of what its adapter made of them, in Roundhouse's terms, the same whatever it's played against. Each agent's binding gives it a script for the scripted model | `conformance::scenario::Scenario`, `conformance::scenarios` |
| Trial | One playing of a scenario, against the scripted model or the real one, or replayed from a capture. It can span several runs | `conformance::trial::Trial`, `Played`, `Report` |
| Driver | What plays a scenario's steps through `AgentProcess`, as the worker does, and keeps what the adapter said | `conformance::driver::Driver`, `Launcher` |
| Scripted model | A stand-in for the model's API on this machine, whose every reply a scenario's script makes. The real model is the real API, which costs money | `claude::conformance::messages::ScriptedModel`, `Script`, `Against` |
| Capture | What crossed a real agent CLI's stdio, kept as lines, such as what `tools/smoke/capture_claude_fixture.py` captures. A trial's capture is what its adapter did with the CLI, in order. One kept for tests is a fixture, such as a scripted trial's | `conformance::capture::Entry`, `Tap`, `tools/smoke/capture_claude_fixture.py` |
| Replay | A trial that plays a scenario again through the adapter from a capture, with a stand-in for the CLI that writes what the CLI wrote, and fails where the adapter writes otherwise | `claude::conformance::replay`, `conformance::stand_in` |

## Work

| Term | Meaning | In code |
|---|---|---|
| Repository | A git repository added to a hub, whose record says where it is: its checkout on the hub's machine, its address, or both | `Repo`, `RepoOrigin` |
| Address, of a repository | Where a repository lives, as git names a remote's URL, such as `https://github.com/ada/roundhouse.git`, which a worker with no checkout of its own clones and fetches from. A checkout's is its `origin`'s. It never holds a credential | `RepoUrl`, `RepoOrigin::url`, `ReadRepoUrl` |
| Project | What the interface calls a repository added to a hub: the entry that holds a codebase's workspaces and settings, with one git repository behind it, added by that repository's checkout on the hub's machine | `Repo` |
| Workspace | The unit of delegation: a name, a branch and a worktree in one repository, with its sessions and diff comments | `Workspace` |
| Worktree | A workspace's git worktree, the files on disk | `Workspace.path` |
| Repository source | What a worker is told to make a workspace's worktrees from: a checkout of the repository on its machine, or the repository's address, which it clones | `RepoSource` |
| Repository's clone | A worker's own copy of a repository it's told of by its address, which it makes the repository's worktrees from, as from a checkout. There's one for each address on a machine, in the clones directory the worker's provider names. It's never the hub's | `RepoSource::Clone`, `worker::git::Clones`, `--clones-dir`, `worker::Config.clones_dir`, `Paths::clones_dir` |
| Child worktree | Another worktree of a workspace's repository, made for its work, in `.children/` beside the workspaces. The interface says "other worktree". Not built | `ChildWorktree`, `CreateWorktree`, `AddChildWorktree` |
| Title | What a workspace or a chat is called on screen. It's generated from the first prompt, generated again from every prompt when someone asks, or typed by hand, and one typed by hand is replaced only by one someone asks for | `Workspace.title`, `Session.title`, `TitleSource` |
| Base ref | What a workspace's branch was created from. Diffs are taken against it | `base_ref` |
| Branches | What a worktree's git says of its branches, as its worker last read them: which is checked out, and each branch the worktree has had checked out, with its newest commit and where it's pushed | `Branches`, `Observation::WorkspaceBranches`, `Branches.had`, `WorkerRequest::WatchBranches`, `ChildWorktree.branches`, `WatchChildBranches`, `WorkerFrame::ChildBranches` |
| Change summary | What a worktree changes against its base ref, file by file, with no patch: each file's status, its lines added and removed, and a version that changes when its content does, and the lines added and removed in all. Its worker works it out when asked, or as files change while it watches | `ChangeSummary`, `ChangedFile`, `FileVersion`, `SummarizeChanges`, `WatchChanges`, `worker::git::ChangeSummaries` |
| A workspace's pull request | The one GitHub has from the branch the workspace's branch is pushed to, its upstream's, in the repository its remote names. Not any from a branch of the same name elsewhere, and not the workspace's to own, since workspaces on the same branch have the same one | `own::judging::wanted`, `own::judging::chosen` |
| Base image | An instance that a repository's own script has set up, with its tools installed and its caches warm, then turned into one that others are copied from and that can't start again. A remote workspace's VM is a copy of its repository's current one. Not built | None |
| Session | One conversation with one agent, with its log. A workspace can have several | `Session` |
| Terminal | A shell a workspace's worker runs in the worktree, which every client can watch and type into. The worker keeps what it shows, and a client that watches is sent that as rows, a whole picture and then what changes. The hub keeps its record while its shell runs. Not a session, which is a chat's | `Terminal`, `TerminalId`, `TerminalPicture`, `TerminalUpdate`, `terminal_state::Mirror`, `WorkerFrame::Terminal`, `HubFrame::Terminal`, `OpenTerminal`, `terminal_view::TerminalView`, `Showing::Terminal` |
| Row number | Where a row of a terminal is among its history and its screen, in one numbering. A number never moves to another row as lines scroll, so a row of history is asked for by its number. The worker counts them, and numbers a program's own screen, such as a pager's, apart from the shell's | `RowNumber`, `TerminalRow`, `TerminalRows`, `terminal_state::Mirror::history_rows` |
| Numbering | Which row numbers a terminal's are, which starts again when it's resized, its history cleared or it's reset, and whenever its worker loses count, so a number from before names no row | `Numbering` |
| Picture | What a terminal shows at one moment, sent as the rows its receiver lacks, with the cursor and what else changed. One too big for a frame goes in several, and only the last is whole. The worker sends the hub one while it watches, at most about 60 a second, and the hub keeps the newest whole one | `TerminalPicture`, `WorkerFrame::TerminalPicture`, `HubFrame::TerminalPicture`, `PictureSending`, `Shown` |
| Watch | What a client does to a terminal it shows, and for 30 seconds after, so the hub sends it what it lacks of the hub's copy, the newest whenever its last frame is written. The hub watches the terminal while any client does, and only the hub that asked is sent pictures | `Follow::Terminal`, `Watcher`, `HubConnection` |
| Pressed | What a client sends of a key, a paste, a turn of the wheel or text as it is, for the worker to turn into what the program reads by the modes it set, which only the worker's copy knows | `Typed`, `TerminalTyped`, `KeyPress`, `terminal_state::Mirror::typed` |
| Point | A cell of a terminal by its row's number and its column. A client selects from one to another, asks the worker for the ends of the word or the line at one, and for the text between two, a page at a time, as Ghostty copies it | `TerminalPoint`, `TerminalRange`, `TerminalBounds`, `TerminalText` |
| Fit | A new size a client gives a terminal, naming the points it wants kept, such as its view's top and its selection's ends. The worker says where each went in the numbering the new size starts | `TerminalFit`, `TerminalFitReply`, `terminal_state::Tracked` |
| Run | One launch of an agent. A session can have many, because an agent can exit and be started again. Its ID never repeats, even across hub restarts | `RunId`, `AgentSpec.run` |
| Turn | From a prompt until the agent finishes responding. A run can have many. A prompt sent mid-turn folds into the running one if the agent has more to do, and otherwise starts the next. The agent starts one by itself whenever one of its background tasks finishes, to take in how it ended | `TurnEnded`, `Session.turn_started_at_ms`, `SessionStatus::in_turn`, `SessionStatus::between_turns` |
| Own turn | A turn the agent starts by itself, with no prompt, such as to take in how its background tasks ended. The agent's adapter records why as the turn starts, when it can tell then, naming each task, and the hub adds what it keeps of each wait among them | `EventBody::OwnTurn`, `capability::turns::OwnTurn`, `EndedTask`, `EndedWait` |
| Background task | Work an agent started that carries on after its turn ends: a command, a subagent, a monitor, or a wait on pull requests | `AgentTasks`, `AgentTask`, `AgentTask::part_of`, `TaskKind`, `TaskTool`, `client_core::tasks::Says`, `SessionStatus::Background`, `CallOutput::Backgrounded` |
| Monitor | A background task that watches for something, such as a check failing, and wakes the agent each time it happens. It does nothing meanwhile, and may never end | `TaskKind::Monitor` |
| Task group | The background tasks of one kind: subagents, commands or monitors. With more tasks than have a line each at the chat's end, a group with several has one line, which opens to theirs | `TaskGroup`, `TaskLine`, `transcript::task_lines` |
| Reply | What the agent said in a turn, as of the event that ended it, and how that turn ended. A turn the agent was cut off from isn't one | `Session.reply_seq`, `Session::has_reply`, `Session.reply_outcome` |
| Failed request | One of the agent's requests to its model that failed, as on a usage limit, which its CLI says in a message of its own in the model's place. The chat shows it as a red card, and those in a row as one card | `EventBody::RequestFailed`, `RequestFailure`, `FailureKind`, `TurnEnded.request_failed`, `Again`, `transcript::rows::around::failures` |
| Stopped short | What a chat is when its agent went away mid-turn, or its newest turn failed, until a turn starts again. Its mark's turntable is red, it notifies, it holds its queue, and it needs the person | `Session::stopped_short`, `Session::turn_failed`, `Signal::Failed` |
| Prompt | What a person sends to an agent: what it says, and the files it carries. It's pending until the hub has recorded it | `protocol::prompt::Prompt`, `UserPrompt`, `client_core::Written`, `SessionLog::pending` |
| Attachment | A file a prompt carries, of any kind, or an image a tool sent the agent, such as a screenshot it read. The worker puts a prompt's files in the worktree's `.context/attachments/`, and the hub keeps every image. The interface says "file" or "image" | `Attachment`, `AttachmentId`, `AttachmentFile`, `NewAttachment`, the `attachments` table |
| Context folder | The worktree's `.context/`, where what isn't the repository's goes: the files prompts carried, and what an agent makes for its own use while it works, such as notes, logs and screenshots. Not an agent's context, which is what its model holds | `worker::context_dir::Folder::Context` |
| Draft | What's typed or attached in a chat's composer, or chosen and typed toward a decision on the request its agent waits on, and not sent. In code, so are a comment being written on a diff and what's in the new-workspace dialog, which no screen calls a draft. Not a pull request that's a draft, which is GitHub's | `Draft`, `DraftToKeep`, `Session.draft`, `SessionDraft`, `DecisionDraft`, `SoFar`, `UseChoice`, `Session.decision_draft`, `client_core::ToolUseAnswer`, `SessionDecisionDraft`, `CommentDraft`, `Workspace.comment_draft`, `WorkspaceCommentDraft`, `NewWorkspaceDraft`, `NewWorkspaceDraftToKeep`, `Records.new_workspace_draft`, `NewWorkspaceDraftKeep`, `NewWorkspaceDraftFileAdd`, `NewWorkspaceDraftFileRead`, `NewWorkspaceDraftFileRemove`, `NewWorkspaceCreate`, `NewWorkspaceMade`, the `new_workspace_draft_files` table, `AttachmentRemove`, `client_core::Drafts`, `client_core::DraftKey`, `client_core::DraftChange`, `client_core::FilesFor`, `client_core::KeptDraft`, `client_core::ReadBack`, `Client::read_back`, `new_workspace::Keeping`, `WorkspacePane::has_unsent` |
| Tool call | An agent using one of its tools, such as running a command or editing a file, and the result it got back. Its kind is what the call does, such as a command, an edit or handing work to a subagent, which is apart from a subagent's kind of agent | `ContentBlock::Call`, `ContentBlock::CallResult`, `Call`, `CallOutput`, `CallKind`, `calls::Returned`, `ToolUseId`, `Asks::Call`, `client_core::calls`, `calls::Recorded`, `ToolCall`, `ToolCall::summary`, `Denied`, `ContentBlock::CallResult.denied` |
| Tool server | An MCP server over HTTP that the hub has of its own, which a person added, in every project. The interface says "MCP server". Agents call it what `ToolServerName::for_agents` makes of the name the person gave | `ToolServer`, `ToolServerId`, `ToolServerName`, `ToolServerUrl`, `ToolServerHeader`, `ToolServerAuth`, `ToolServerPlace`, `ToolServerAuthGiven`, `ToolServerAuthEdit`, `ToolServerKey`, `Record::ToolServer`, `tool_server_add`, `tool_server_edit`, `client_core::tool_servers::ToolServerNames`, `client_core::tool_server_edits`, the hub's `tool_servers`, `ToolServers`, `SentToolServers`, `ToolServerSecret`, the `tool_servers` table, the `tool-servers` directory |
| Check, of a tool server | Asking a tool server with a key, or with neither, for its tools before it's added or edited. A save does it inside. | Save, of a tool server | Adding a tool server, or saving an edit of one, as one request, in which the hub first checks it, unless the person has it done anyway, and refuses one that lists no tools with why. Its client lets go of it by an ID of the save's own, which no other client is told | `ToolServerSave`, `tool_server_save`, `SaveWhen`, `ToolServerSaved`, `ToolServerSaveId`, the hub's `Saves`, `save_or_ask` and `save_asked` |
| Sign-in to a tool server | Having a tool server know the person by what its authorization server gives the hub once they approve it on that server's page. The hub keeps its tokens and renews them, and one it can't renew, or whose server wants more access, needs signing in to again. One in progress is in the hub's memory alone | `ToolSignInId`, `tool_sign_in_start`, `tool_sign_in_finish`, `ToolSignInTo`, `ToolSignInBegun`, `ToolSignInStatus`, `SIGN_IN_WAITS`, `Hub::tool_sign_ins`, `KeptSignIn`, `tool_servers::Due`, `tool_servers::Wanted`, `ToolScopes`, `protocol::worker::TokenNumber`, the `tool-sign-in` crate, the desktop's `tool_sign_in`, with `ToolSigningIn`, `SignInTo` and `Stands` |
| Plug | What's beside Send for a chat's MCP servers, and opens the card that lists them: the hub's, then the ones its agent's CLI has of its own | `WorkspacePane::plug`, `client_core::tool_servers`, `ChatToolServers`, `Stands`, `SignIn`, `SignInFor`, `ToolServerState`, `Region::ToolServersCard` |
| Reload | Having a chat's running agent connect again to one of its MCP servers, which a person does from the plug's card, and the hub as one is signed in to or edited | `session_reload_tool_server`, `Control::Reload`, `Control::Reconnect`, `tool_server_reload`, `tool_server_reconnect`, `LiveSession::connect_again`, the hub's `HadServers` and `ServersAsSent`, `ToolServerState::connects_again`, `client_core::tool_servers::Reloads` |
| The worker's tools | Tools of Roundhouse's own, which a worker serves its agents over MCP on 127.0.0.1, and which the hub answers, such as `get_pull_request`. Each agent reaches them with a token of its session's. | Tool server proxy | What a worker's agents reach the hub's tool servers through: a path for each on the listener that serves the worker's tools, whose calls the worker passes on with the server's own header, which no agent is given. The hub sets them on each worker's link, and is told of one that refuses its access token or wants more | `worker::tools::Proxy`, `WorkerRequest::ToolServersSet`, `ProxiedServer`, `ServerSignIn`, `RenewToolServer`, `AskForToolAccess`, `ToolAccess`, the hub's `Following` and `Servers` |
| Wait | An agent waiting on explicit pull requests and their lower stack dependencies to reach a condition or need attention, which the hub keeps and ends once. A chat can have several independent waits at once. Not a watch, since a monitor watches and wakes the agent each time | `Wait`, `WaitEnd`, `WaitUntil`, `hub::waits`, the `waits` table |
| Ask | What a worker asks its hub, for one of its tools or a call it passes on to a tool server, which the hub answers as a worker answers a call | `WorkerFrame::Ask`, `protocol::worker::Ask`, `Answer`, `WorkerAsk`, `AskAnswer` |
| Ask key | What a worker gives an ask that makes a worktree, so a hub that hears the ask again, as each new hub does what the last didn't answer, makes it once. A UUID, or the agent's ID for the tool call that asked, and unique within its session. Not built | `AskKey`, `CreateWorktree.key` |
| Job | Work the hub does on its own, which no request waits on, as `Jobs` runs it, such as reading a pull request nobody asked for. Not a background task, which is an agent's, nor a Windows job object, which holds a group of processes | `jobs::Jobs`, `JobKind`, `Limits`, `Ended`, `jobs::step`, `jobs::uncut` |
| Steer | Send a prompt while the agent works, which it reads at its next chance, such as when a running tool finishes. Until then the prompt is waiting, and a stop drops it. | Queue | Prompts waiting for the agent to finish, on the session's record, each sent as a turn of its own. | Approval | An agent asking before it uses a tool, asking the person questions, or asking to have its plan approved. | Question | An approval where the agent is asking a person something, so it needs an answer rather than a yes. | Approval mode | How much an agent may do without asking. Every agent has full access, except in plan mode. | Word | The senses | What to write |
|---|---|---|
| Tool server | One of the hub's own, `protocol::model::ToolServer`, and how an agent reaches the worker's tools and the hub's, `agents::ToolServers` | "Tool server" for the hub's, and "the worker's tools" for the other |

| Note | A prompt added to an agent's conversation without starting a turn, and what the app's `--note` says of why a copy is open | "Note" alone for the prompt in code about agents, and the flag by its name, `--note` |

A session is ours, a chat is what the interface shows, and a conversation is the agent's own record, which is what it resumes | "Session" in code and docs, "chat" in text people read, and "conversation" only for the agent's side, or for talking with it out loud, in conversation mode, as in `agent_session_id` (even when an agent's wire protocol, such as ACP's `sessionId`, calls its side a session) |
| Workspace | Ours, or another tool's, such as a Cargo workspace | A bare "workspace" means ours. Always qualify the others |
| Project, repository | The same record. A project is what people see, and a repository is the git codebase behind it | "Project" in the desktop app and its spec, and "repository" in code, the CLI and the other docs, and wherever git itself is meant, as in "repository settings" |
| Claude, Claude Code | The agent, and Anthropic's own product, whose CLI it runs | "Claude Code" in the interface, as the agent's description names it, such as for its own login on a machine, and "Claude" where it's short, as in Skip Claude's safety checks. "Claude CLI" for the `claude` binary in docs |
| Antigravity | The agent, and Google's product, whose `agy` CLI it runs | "Antigravity" in the interface and docs, and "`agy`" or "Antigravity CLI" for the binary in docs |
| Checkout | A copy of this repository that the app is built from, and a repository's checkout on a worker's machine, which the repository's worktrees are made from unless it's a clone, such as the one on the hub's machine that a project is added by | "Checkout" alone for this repository's, as the app's sidebar names it. "A repository's checkout" for the other, as `RepoSource::Checkout` and `RepoOrigin::Checkout` are |
| Workspace, worktree, instance | The record, the files, and where its worker runs | The one you mean. Archiving removes the worktree, not the workspace |
| State directory, instance directory, data directory | Where a worker keeps its own files, a local instance, and where a hub or a client keeps its records and settings | "The worker's state directory", or "state directory" where whose is clear. "Instance directory" only for a local instance as the local provider makes, finds and removes it: what a worker keeps there is in its state directory. "Data directory" only for a hub's or a client's. Another program's own directory, such as Codex's, is named with its owner |
| Frame | A message on the wire, one line of JSON, or what a terminal shows, painted for a view to draw | The one you mean. In code that draws a terminal, `frame` is what it shows, which is `client_core::drawn::Frame`, and elsewhere it's the wire's. In docs and comments, say "a terminal's frame" for the other. GPUI's frame, each time it draws the window, is a third, which only says "frame" where nothing else could be meant |
| Terminal | A workspace's, which its worker runs, or a terminal app, such as Terminal or Ghostty, on someone's own machine | Say "a terminal app" for the other wherever a workspace's could be meant |
| Name, title | A workspace's name, such as `euston`, is its directory and the folder its branches go in, which is the part of a branch's name before its first slash, so it starts on `euston/start`, and never changes once it's made. Its title is what the sidebar shows | "Name" only for the directory and the folder of branches. Renaming a workspace changes its title |
| Record, process record | A record is something the hub owns that clients keep, such as a terminal's. A process record is a file holding a process's PID and start time, which a worker writes for each process that would outlive it, such as a terminal's shell, so the provider can stop it after a killed worker | "Record" alone for the hub's, and "process record" for the other, which is `process::ProcessRecord` |
| Worker, agent | A worker is our process, and an agent is the CLI it runs | The one you mean. A worker can outlive its agents, and agents can outlive a killed worker |
| Model, dictation's model | Which model an agent runs, against the model dictation hears with, whose files are downloaded to this device | "Model" alone means the agent's, as `ModelName`. Say "dictation's model" where it isn't clear, as `models`, `ModelFiles` and `ModelDownload` are |
| Model name, model label | What an agent is asked to run, such as `fable` or `claude-fable-5-1`, and how the model's provider names it for people, such as `Fable`, which a model's own limit is named by | "Model" for either where it's clear. `ModelName` and `ModelLabel` in code, which can't be mixed up |
| Agent, harness | What other tools call a harness, the program that runs a model with its tools, such as the Claude CLI, is an agent here | "Agent". "Harness" only as another tool's word |
| Guide | The guide is `docs/guide`, how to use the product, published as the site's `/docs/` pages. A guide is one of its pages under Guides, named for what someone gets done | "The guide" for the whole, and "a made-up guide" for one a test builds. Otherwise "a guide" only for one of those pages, and "a page" for any other |
| Hub, daemon | `roundhoused` is one binary that runs as a hub or as a worker. A stamped build's hub runs from its copy of it, `Roundhouse Hub`, and so do the workers that hub starts | "Hub" or "worker". "Daemon" only for the binary |
| Run, turn | A run is a process's lifetime, and a turn is one exchange within it | The one you mean. Counting turns can't give a session's status, as a prompt mid-turn adds none |
| Row | A row of the transcript's list, which an event is drawn in, and failed requests in a row, one after another with nothing between them that ended the row | "A row" alone for the list's. For failures, "in a row", or "the row" only where the failures are what's being said, as in "ends the row" |
| Approval mode, permission mode | The same setting. `--permission-mode`, `permissionMode` and `bypassPermissions` are the CLI's names | "Approval mode" in docs and interface text, and `ApprovalMode` and `mode` in code. Roundhouse's own CLI keeps `--permission-mode`, `plan` and `bypassPermissions`, and names its agent's mode of each kind with them |
| Status | `SessionStatus`, `WorkspaceStatus`, `SetupStatus`, `ChildStatus` or `GitStatus`, and the box that says how something stands, such as dictation under its setting, `StatusBox`, which a `Setting` gives as its `status_box` | Say which |
| Adapter | An agent's adapter runs one kind of agent and turns its output into events. A provider's adapter makes and ends its instances | "Adapter" alone means an agent's, except where only a provider's can be meant, as in "Workers and providers" in `docs/principles/parts.md`. Otherwise "provider adapter" |
| Base | A workspace's base ref is what its branch was created from. A base image is what a remote workspace's VM is made from | "Base" alone means the base ref. Always "base image" for the other |
| Provider, model provider | A provider is where a hub runs workers. A model provider is who serves an agent's model | "Provider" alone only for the first. Always "model provider" for the second, in code and in the interface |
| Account | An agent's account is the login its CLI runs under. A GitHub account is one the hub holds a login for, which agents push as. A hub's accounts, once a hub serves several people, are who may use it | "Account" alone means the agent's, until hubs have their own. Then say which. Always "GitHub account" for the second, and `Github*` in code |
| Notice | `EventBody::Notice` is a message in a session's log. `HubNotice` is on the feed, and says a record changed | "Log notice" or "feed notice" |
| Snapshot | `session::Snapshot` is what a subscriber starts from. A live snapshot is what something running shows now, which the hub doesn't store. A provider's `snapshot` saves a filesystem, and isn't built | Say which, and "live snapshot" in full |
| Frame, step, window | A protocol frame, one message on the wire, and, in `dictation`, a short stretch of audio measured as one, for finding pauses or for the model's features. The model's encoder makes out a step, which is decoded as one, and its live encoder takes a window at a time | "Frame" alone means the protocol's. In `dictation`, say what a frame is of, such as "the features' frames", and "step" and "window" for the encoder's |
| Record, recording | A hub's record, such as a session's, and the hub recording something, against a recording of what's said to dictate a prompt | "Record" and "recorded" for the hub's, and "recording" only for dictation's, as `dictation::Recording` |
| Restore | `workspace_restore` recreates an archived worktree from its branch, and the workspace's record says `WorkspaceStatus::Restoring` meanwhile. A provider's `restore` rolls back a filesystem, and isn't built | "Restore" alone means the workspace's |
| Log | A session's log, or a log file such as `hub.log` or the setup log | A bare "log" means a session's. Name the file otherwise |
| Position | Where an event is in a session log a client holds, as `session_log::Position`, or where a question is among those asked together, or an option among a question's, by which a client answers them, as in `QuestionAnswer` | "Position" alone means an event's, in a client's log. Say "a question's position" or "an option's position" for the others |
| Reply | What the agent said in a turn, or what a hub, a worker or a provider's adapter answers a request with | "The agent's reply" or "the hub's reply", unless only one can be meant. In code, the agent's is `Session.reply_seq`, and a request's is the protocol's, as in `protocol::client::Reply`, `HelloReply` and `HubFrame::Reply` |
| Settings | The app's own, chosen in Settings and kept on this Mac, a hub's, chosen there too and kept by the hub that carries them out, or a repository's, in its `.conductor/settings.toml` files | "Settings" alone means what's chosen in Settings. Say "hub settings" for the ones a hub keeps, `HubSettings`, and "repository settings" for a repository's |
| Setting, preference | A setting is what a person chooses in Settings, and a preference what an app remembers on its device from how it's used, such as the workspace it was left on | "Preference" never for what's chosen in Settings, though macOS once called that Preferences. `Preferences` in code |
| Stand-in | A program a test runs in place of another, in `tools/stand-ins/`, such as the fake agent, `fake_claude`, and a stand-in for a part that a test makes in its own process, such as `client_core::stand_in_hub`, which answers a client as a hub would. The program `stand_in_hub` is a hub of another build | "Stand-in" for either, with the program or the type by its name where both could be meant. "The fake agent" for `fake_claude` |

## Ending things

These sound alike, and do different things.

| Word | Applies to | What it does | Afterwards |
|---|---|---|---|
| Cancel, a save | A save of a tool server | The hub lets go of one whose server is still being asked, as it does when the save's connection closes, so nothing is added or saved. `tool_server_save_cancel`, `ToolServerSaved::Cancelled` | One the hub had begun to save is saved all the same |
| Cancel, a sign-in | A sign-in to a tool server | The hub forgets one that isn't finished, and keeps nothing it's given for it. `tool_sign_in_cancel` | It's gone, and a finished one stays |
| Cancel, a sign-in | A sign-in with GitHub | Ends a sign-in that's waiting, so the hub stops asking GitHub after it and keeps nothing GitHub gives for it. `github_sign_in_cancel`, `GithubSignInStatus::Cancelled` | Its record says so until another sign-in starts |
| Cancel | A turn | Ends the current turn and any setup still running. The agent's process stays up. `session_cancel`, `Control::Cancel` | It takes the next prompt |
| Stop, in the interface | A turn | The Stop button and `Cmd-.` mean cancel, not a process stop. On a wait's line, Stop calls the wait off | As for cancel |
| Call off | A wait | Ends a wait before its condition: by its agent, by the person, or by closing its chat or archiving its workspace. Starting another wait leaves it alone. `session_call_off_wait`, `WaitEnd::Cancelled`, `CalledOffByPerson`; `Replaced` is a historical ending from older hubs | The agent hears, in a turn of its own, unless it called it off itself, or its chat or workspace went with it |
| Interrupt | A turn | What the agent CLI calls a cancel. Only the adapter says this, as Claude's does for the `Control::Cancel` it's sent | As for cancel |
| Interrupted | A session | A status, not an action: the agent went away mid-turn rather than ending the turn, whatever the reason, as when it exits by itself, its worker goes, or it's stopped by closing its chat, archiving its workspace or stopping the hub. A cancel ends the turn first, so it doesn't cause it | The next prompt resumes the conversation |
| Stop, in code | A process | Ends it, and gives it time to finish. `AgentStop`, `WorkerLink::stop` | The next prompt starts a new one |
| End a worker | An instance's worker | Ends whatever runs on the instance, and gives it time to finish, leaving the instance awake. Never what a provider's own tools call stopping an instance, which sleeping it will be. `Provider::end_worker` | The next worker can start there |
| Hang up | A terminal's shell | Ends it as closing a terminal app's window does. The shell and the job it runs in front are sent a hangup, and whichever hasn't ended two seconds later is killed. `TerminalStop`, `Signal::Hangup` | The terminal closes, and its tab goes |
| Kill | A process | Like stop, without the time. For a worker that isn't responding. `WorkerLink::kill`, `Provider::kill_worker` | The next prompt starts a new one |
| Close | A session | Stops its agent and hides it from the tabs. The history stays. `session_close`, `Session::is_open` | It can be reopened with `session_reopen` |
| Close | A terminal | Hangs up on its shell, and the hub drops its record. Nothing of it is kept. `terminal_close`, `TerminalClose` | It's gone, with what it showed, and can't be reopened |
| Archive | A workspace | Removes its worktree, and any others made for its work, and keeps their branches. Refuses if work would be lost, unless forced. Its record says it's being archived until it's done, or put back. `workspace_archive`, `WorkspaceStatus::Archiving` | It can be restored |
| Destroy | An instance | Removes it. `Provider::destroy` | It's gone |
| Remove | An app of your own | The hub forgets the app's key and each installation's login, then its record, and deletes nothing on GitHub. Remove app, in the menus of its rows on Git. `github_app_remove`, `GithubAppRemove` | Its installations' accounts stay, as disconnecting leaves one, and one that's the default stays the default, so agents can't push until another is. The app stays on GitHub, for the person to delete there |
| Remove | A tool server | The hub forgets its key or its sign-in, then its record. `tool_server_remove` | It's gone, and nothing changes at the server |
| Disconnect | An account's login, or a GitHub account's | The hub forgets the login it holds for the account, so no agent launched after runs under it. It doesn't revoke the token. `account_disconnect`, and `github_account_disconnect` | The account's record stays, and connecting a token to it gives it a login again. A default GitHub account disconnected stays the default, so agents push as nobody. An app's installation disconnected stays installed on GitHub |
| Discard | A half-made workspace | Removes a workspace that failed while being created, or was left by a crash, and destroys its instance. `discard_workspace`, `take_unfinished_workspaces` | It's gone |
